MISSION 8.4: MULTI-STEP PLANNING & MEMORY

Agents That Remember

Mission 8.2's agent figured out its next step one reasoning cycle at a time. Complex goals often benefit from a different approach: plan first — break the whole goal into an ordered list of subtasks before acting — then execute that plan, step by step. Real agents also need memory that outlives a single run: facts and preferences that should be remembered the next time you talk to it, not re-explained from scratch every conversation.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

There are two very different kinds of "the agent remembers something," and conflating them causes real bugs. Short-term (working) memory is Mission 8.2's history array — everything that happened during THIS run, gone the moment the run ends. Long-term memory is meant to survive across entirely separate conversations — "the user prefers metric units," learned once, remembered forever after, exactly like Mission 4.4's localStorage persisting data across a page reload.

2

Field Manual

Planning: Break the Goal Into Steps First

Instead of deciding one action at a time (Mission 8.2), a planning agent first produces an ordered list of subtasks for the whole goal, then works through that list — re-planning if a step reveals something that changes what's actually needed.

JAVASCRIPT
function planTask(goal) {
  // A real planner is itself an LLM call; this is a scripted stand-in.
  if (goal.includes("trip")) {
    return [
      "Check the weather forecast for the destination",
      "Look up transport options and book by the deadline",
      "Add a packing reminder to the calendar",
    ];
  }
  return ["Break down the goal further"];
}
WHAT JUST HAPPENED The plan itself is just data — an ordered array of subtasks. Executing it means running Mission 8.2's agent loop (or a single tool call) once per subtask, in order, tracking which ones are done. If a step's result reveals the plan needs to change (the destination turns out to already be booked), a real planning agent re-plans instead of blindly continuing the original list.

Long-Term Memory, For Real

Long-term memory needs actual persistence — Mission 4.4's localStorage or Mission 5.2's real database, not just a JavaScript variable that disappears when the page closes. The pattern is simple: remember(key, value) writes a fact; recall(key) reads it back later, even after a full page reload.

JAVASCRIPT
const AgentMemory = {
  remember(key, value) {
    localStorage.setItem("agent_memory_" + key, JSON.stringify(value));
  },
  recall(key) {
    const raw = localStorage.getItem("agent_memory_" + key);
    return raw ? JSON.parse(raw) : null;
  },
};
WHAT JUST HAPPENED This is genuinely real — data written with remember() is still there after you close and reopen the browser tab, exactly like Mission 4.4 taught. A real production agent usually stores long-term memory in a real database (Mission 5.2) instead of localStorage, so it's shared across devices and users — but the read/write pattern is identical.

Memory vs the Context Window

Mission 7.9 already warned against stuffing everything into the context window. Long-term memory makes this concrete: you don't dump a user's ENTIRE memory history into every prompt. Instead, you retrieve only the memories relevant to the current request — exactly Mission 7.5/7.6's semantic search and RAG pattern, applied to an agent's own memory store instead of a document collection.

⚠ COMMON MISTAKES

  • Confusing short-term run history with long-term persisted memory — they solve different problems and need different storage.
  • Storing long-term memory in a plain JavaScript variable that disappears the moment the page closes.
  • Dumping a user's entire memory history into every prompt instead of retrieving only what's relevant (Mission 7.9's lesson, applied here).
  • Never re-planning when a step's result reveals the original plan no longer makes sense.
