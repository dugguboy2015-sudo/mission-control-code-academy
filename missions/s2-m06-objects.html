MISSION 2.6: OBJECTS & STRUCTURED DATA

Modeling the Real World in Code

Arrays are great at one thing: ordered lists of similar stuff. But a starship isn't a list — it's a name, a fuel level, a crew roster, and a bundle of subsystems, all different kinds of information glued together. Objects are how you model that. Every real system you'll ever build — a user profile, a game character, an API response — is, underneath, just an object. This is the mission where your data starts looking like the things it represents.

🟡 OFFICER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Think of an array as a row of numbered cargo crates in the hold: crates[0], crates[1], crates[2]. It's fast and simple, but it only tells you a crate's position — not what's actually inside it. If you want to know the crew member's name, their role, and their clearance level, tracking three separate arrays and hoping the indexes line up is a bug waiting to happen.

An object is a labeled control panel instead of a numbered crate. Every switch on the panel has a name printed above it — fuel, name, online — and you flip or read a switch by its name, not by counting from the left. That's the whole idea: objects store key/value pairs, where each key is a label and each value is whatever data lives behind it — a number, a string, an array, even another object.

Most things worth modeling in the real world are exactly this shape: named attributes, not a numbered sequence. A ship has a name and a fuel level, not a "first thing" and a "second thing." Once you can nest objects and arrays inside each other, you can represent almost anything — a whole starship, a game character's inventory, a user's profile — as one connected structure you can pass around, save, and inspect.

One ship object, three kinds of nesting: a plain value (name), an array of objects (crew), and a whole sub-object with its own method (systems). Boxes inside boxes — that's structured data.
2

Field Manual

Object Literals & Property Access

An object literal is written with curly braces: a comma-separated list of key: value pairs. Each key becomes a named property you can read back out.

JAVASCRIPT
const ship = {
  name: "Voyager-9",
  fuel: 84,
  online: true
};

console.log(ship.name);   // "Voyager-9"
console.log(ship.fuel);   // 84

ship.fuel = 91;           // update an existing property
ship.destination = "Kepler-442b"; // add a brand-new property
WHAT JUST HAPPENED ship is declared with const — but that only locks the variable from being reassigned to a completely different object. The properties inside it are still fully editable, which is why ship.fuel = 91 works fine. Reading a property that was never set (like ship.captain here) doesn't crash — it quietly returns undefined.

Dot Notation vs. Bracket Notation

ship.name — dot notation — is what you'll write most of the time: short and readable. But dot notation only works when the key is a valid identifier typed literally into your code. Bracket notation, ship["name"], does the same lookup but takes the key as a string — which means the key can come from a variable.

JAVASCRIPT
const ship = { name: "Voyager-9", fuel: 84 };

// dot notation: key is typed literally
console.log(ship.fuel);

// bracket notation: key can be a variable
const field = "fuel";
console.log(ship[field]);       // still 84 — looked up dynamically

// bracket notation is REQUIRED for weird keys
const stats = { "hull integrity": 100, "2ndOfficer": "Kip" };
console.log(stats["hull integrity"]); // has a space — dot notation can't do this
console.log(stats["2ndOfficer"]);     // starts with a digit — same problem
WHAT JUST HAPPENED The key rule: use dot notation when you know the exact property name while writing the code. Switch to bracket notation the moment the key is stored in a variable, computed, or contains characters (spaces, a leading digit, dashes) that would make ship.hull integrity a syntax error. "Pick a property based on user input or a loop variable" is the single most common reason to reach for brackets.

Nesting Objects & Arrays

Values inside an object aren't limited to strings and numbers — they can be arrays, or other objects, nested as deep as you need. Chain . and [] together to drill down to whatever you're after.

JAVASCRIPT
const ship = {
  name: "Voyager-9",
  crew: [
    { name: "Nova", role: "Pilot" },
    { name: "Kip", role: "Engineer" }
  ],
  systems: {
    shields: true,
    engines: "warp"
  }
};

console.log(ship.crew[0].name);        // "Nova" — array index, then property
console.log(ship.systems.engines);     // "warp" — object inside an object
ship.crew[1].role = "Chief Engineer";  // update a property deep inside
WHAT JUST HAPPENED ship.crew is an array, so it needs an index ([0]) to pick one crew member — then .name reads a property off that object. Read it left to right: "go into ship, then crew, then item 0, then name." This is exactly how you'll model most real data — a whole ship in a single connected structure instead of a dozen loose variables.

Methods & this

When a property's value is a function, it's called a method — a piece of behavior that belongs to the object. Inside a regular (non-arrow) method, the special keyword this refers to "the object the method was called on," which lets the method read the object's own other properties.

JAVASCRIPT
const ship = {
  name: "Voyager-9",
  fuel: 84,
  systems: {
    shields: true,
    checkStatus: function() {
      return this.shields ? "SHIELDS UP" : "SHIELDS DOWN";
    }
  }
};

console.log(ship.systems.checkStatus()); // "SHIELDS UP"
WHAT JUST HAPPENED Inside checkStatus, this means "ship.systems — whatever object I was called on" — so this.shields reads that same object's shields property without needing to hardcode the name ship.systems.shields. The basic rule for now: use a regular function() {} for a method that needs this, because an arrow function doesn't get its own this the same way and will usually fail here. You'll go deeper on arrow-function this later — for now, "regular function for methods that use this" is a safe default.

Iterating: Object.keys(), Object.values(), Object.entries()

Objects don't have indexes, so you can't for-loop over them the way you loop over an array. Instead, JavaScript gives you three built-in helpers that turn an object's contents into arrays you can loop over.

JAVASCRIPT
const systems = { shields: true, engines: "warp", hull: 97 };

console.log(Object.keys(systems));    // ["shields", "engines", "hull"]
console.log(Object.values(systems));  // [true, "warp", 97]
console.log(Object.entries(systems)); // [["shields",true], ["engines","warp"], ["hull",97]]

for (const [key, value] of Object.entries(systems)) {
  console.log(key + ": " + value);
}
WHAT JUST HAPPENED Object.keys() gives you just the property names, Object.values() gives you just the data, and Object.entries() gives you both together as [key, value] pairs — perfect for a for...of loop when you need to know which property you're looking at, not just its value.
▸ DEEP DIVE: Objects and JSON

An object literal like { name: "Voyager-9", fuel: 84 } looks almost identical to JSON (JavaScript Object Notation) — the format nearly every API on the internet uses to send data around, which you'll meet properly in Sector 4. JSON is stricter, though: every key must be wrapped in double quotes ("name", not name), values can't be functions or undefined, and trailing commas aren't allowed. Think of JSON as "object literal syntax, but locked down enough that any programming language can read it" — which is exactly why it works as a universal format for shipping data between a server and a browser.

⚠ COMMON MISTAKES

  • Writing obj.2ndOfficer or obj.hull integrity — a key with a space or a leading digit needs bracket notation with quotes: obj["2ndOfficer"].
  • Using an arrow function for a method that needs this — arrow functions don't bind this to the object the way a regular function() {} does, so it silently reads the wrong value (or none).
  • Expecting a missing property to throw an error — obj.doesNotExist quietly returns undefined instead, which can hide bugs until you try to use that undefined value later.
  • Trying to for-loop over an object directly like it's an array — objects have no numeric index, so reach for Object.keys()/Object.values()/Object.entries() first.
  • Forgetting that copying an object with = copies a reference, not a duplicate — changing the copy changes the original too, since both variables point at the same object in memory.
