MISSION 7.4: STRUCTURED OUTPUT & TOOL CALLING

Making the Model Speak JSON

Most of what you've done in this sector produces prose — sentences meant for a human to read. But code needs data, not sentences: a specific date, a specific number, a decision about which function to run. This mission covers two ways to get an LLM to hand your code exactly the structured data it needs — asking for JSON directly, and the more powerful tool calling pattern, where the model doesn't just describe what to do, it tells your code exactly which function to call and with what arguments.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

Imagine asking an LLM to read a receipt and tell you the total. "The total was twenty-five dollars and fifty cents" is a perfectly good sentence for a human — and a nightmare to reliably parse in code. Every different phrasing ("came to $25.50", "twenty-five fifty", "$25.5") needs its own fragile parsing rule. Ask instead for {"total": 25.50}, and your code just reads data.total — no parsing fragile sentence structure at all.

2

Field Manual

Prompting for JSON Directly

The simplest approach: explicitly instruct the model to respond with ONLY valid JSON, and show it the exact shape you expect.

PROMPT TEXT
Extract the customer name and total amount from this text.
Respond with ONLY valid JSON in this exact shape, nothing else:
{ "customer": string, "amount": number }

Text: "Order placed for Priya, total came to $42.00"
WHAT JUST HAPPENED Showing the exact key names and types (Mission 7.2's few-shot principle, applied to a schema instead of an example) narrows the model toward one specific, parseable shape. Real APIs often also offer a dedicated "JSON mode" setting that further guarantees syntactically valid JSON — but even then, the values inside it aren't guaranteed correct, only the syntax is.

Always Validate What Comes Back

"Asked for JSON" does not mean "guaranteed valid JSON." The model can still occasionally produce malformed output, or valid JSON with a missing field or a wrong type. Treat every structured response the way Mission 5.1 taught you to treat a database write: verify it before trusting it.

JAVASCRIPT
function parseExtraction(rawText) {
  let data;
  try {
    data = JSON.parse(rawText);
  } catch (err) {
    throw new Error("Model did not return valid JSON: " + err.message);
  }

  if (typeof data.customer !== "string" || typeof data.amount !== "number") {
    throw new Error("JSON was valid but missing expected fields/types.");
  }

  return data;
}
WHAT JUST HAPPENED Two separate failure modes are checked here, deliberately: JSON.parse failing outright (syntactically broken), and parsing succeeding but the shape being wrong (a missing field, or amount coming back as the string "42" instead of the number 42). Skipping either check means a bad LLM response silently corrupts whatever your code does next.

Tool Calling — the Model Picks a Function, Your Code Runs It

Tool calling (also called "function calling") is a step beyond JSON extraction. You describe one or more functions your code actually has — name, description, and what arguments it needs — and the model, instead of writing prose, responds with which function to call and what arguments to call it with. Your code then genuinely executes that function; the model never runs anything itself.

JAVASCRIPT — DESCRIBING A TOOL
const tools = [
  {
    name: "get_weather",
    description: "Get the current weather for a city",
    parameters: { city: "string" },
  },
];

// The model, given "What's the weather in Paris?", responds with:
// { name: "get_weather", arguments: { city: "Paris" } }
// — not prose, a structured instruction for YOUR code to carry out.
WHAT JUST HAPPENED The model never actually checks the weather — it can't; it has no internet access of its own. It decides that a weather lookup is needed and what city, and hands that decision back as structured data. Your code is responsible for actually calling a real weather API (or database, or calculator) with those arguments. This exact loop — model decides, your code executes — is the foundation of every AI agent in Sector 8.

⚠ COMMON MISTAKES

  • Trusting a "JSON" response without wrapping the parse in try/catch — one malformed response crashes the whole pipeline.
  • Checking that JSON parsed successfully but never checking the field types match what you expected.
  • Assuming a tool call means the model actually performed the action — it only decided an action was needed; your code must genuinely perform it.
  • Writing a vague tool description ("does stuff with weather") instead of a precise name, description, and parameter list.

Quick check — after the model returns a tool call like {name: "get_weather", arguments: {city: "Paris"}}, what actually fetches the real weather?
