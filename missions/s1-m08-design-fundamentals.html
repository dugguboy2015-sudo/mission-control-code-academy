MISSION 1.8: DESIGN TRACK — VISUAL HIERARCHY & ACCESSIBILITY

Color, Type, Spacing, A11y Basics

You already know how to write CSS — selectors, the box model, Flexbox. This mission is different. It's not about new syntax; it's about judgment. Given a blank stylesheet, what type sizes do you actually pick? What colors are safe to put text on? How much space goes between things, and why? This is the layer of decisions that separates a page that merely renders from one that actually works — for everyone looking at it, not just you, on your monitor, in good light.

🟡 OFFICER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

A ship's dashboard doesn't label everything the same size in the same color and let the pilot sort it out. In an emergency, the hull-breach warning is enormous, red, and dead center. The current stardate is tiny, gray, and tucked in a corner. Nobody reads either label to know which one matters — the dashboard tells you before you read a single word, using nothing but size, color, weight, and position. That's visual hierarchy: the deliberate use of design properties to communicate importance before comprehension even starts.

Now imagine that same dashboard rendered in pale gray text on a slightly-less-pale gray background, because it looked "clean" on the design studio's calibrated monitor. Put a pilot in bright sunlight, or hand it to someone with low vision, and that dashboard has failed — not aesthetically, functionally. It doesn't matter how elegant the layout was in the mockup if the person who needs it can't actually read it under real conditions. That's accessibility, and it is not a separate, optional checkbox bolted onto "real" design — it's the same job. A design that only works for the designer, on the designer's screen, isn't finished.

Sectors 1.3 through 1.7 taught you the mechanics: how to select things, how the box model works, how to arrange boxes with Flexbox, how to animate them. All of that is how. This mission is about what — the small set of decisions (type scale, contrast, spacing rhythm) that, made well, quietly make every page you build from here on look and feel intentional instead of accidental.

A type scale with four steps and one consistent ratio (here, ×1.25) beats a dozen arbitrary font-sizes nobody could explain if you asked them.
Hierarchy isn't reading order — it's scan order. A bold cyan heading, a high-contrast button, then the subhead, then the body copy: four different visual weights pulling the eye in a deliberate sequence, not the order they happen to sit in the HTML.
2

Field Manual

Visual Hierarchy — Deciding What Gets Noticed First

Hierarchy is built from a small toolbox of signals, used together: size (bigger draws the eye first), weight (bold reads as "more important" even at the same size), color (a saturated accent against a muted background jumps out), spacing (isolated elements read as significant), and position (top-left, in most reading directions, gets scanned first). One signal alone is weak. Stack two or three on the same element, and the hierarchy becomes unmistakable — even to someone glancing at the page for half a second.

CSS
.card-title {
  font-size: 1.75rem;
  font-weight: 700;
  color: var(--accent);
}

.card-meta {
  font-size: 0.85rem;
  font-weight: 400;
  color: var(--text-muted);
}
WHAT JUST HAPPENED .card-title and .card-meta stack three signals in the same direction — the title is bigger, bolder, and more colorful, while the meta text is smaller, lighter, and muted. None of these properties do the job alone; together, they make the hierarchy obvious without a single word being read yet.

A Simple Type Scale

A page with a dozen different font-sizes — 13px here, 15px there, 22px somewhere else — usually didn't get designed; it accumulated. A type scale fixes that: pick a small handful of sizes (3-4 is plenty for most pages), related by a consistent ratio, and use only those. Every size on the page should be explainable — "this is a subheading, so it uses the subhead size" — not a one-off guess.

CSS
:root {
  --text-sm: 0.875rem;   /* 14px - captions, fine print */
  --text-base: 1rem;     /* 16px - body copy, the default */
  --text-md: 1.25rem;    /* 20px - subheadings */
  --text-lg: 1.75rem;    /* 28px - section headings */
  --text-xl: 2.5rem;     /* 40px - page title / hero */
}

h2 { font-size: var(--text-lg); }
p  { font-size: var(--text-base); }
WHAT JUST HAPPENED Five custom properties define the entire vocabulary of sizes available on the page. Every element references one of them by name instead of a raw number — so if you ever want to nudge the whole scale, you change five lines, not five hundred.

Color Contrast & WCAG AA

The Web Content Accessibility Guidelines (WCAG) define a "Level AA" standard most real products target, and its most important number for text is a 4.5:1 contrast ratio between text and its background for normal-sized text (large text — roughly 24px, or 19px bold — only needs 3:1, since bigger shapes stay legible at lower contrast). This isn't an arbitrary bureaucratic hoop: it's the difference between text that's readable for someone with low vision, an older monitor, or a phone screen in direct sunlight, and text that just isn't.

CSS
/* FAILS AA - ratio ~2.85:1, unreadable in bright light */
.bad-label {
  color: #999999;
  background: #ffffff;
}

/* PASSES AA - ratio ~4.54:1, the standard "safe gray" on white */
.good-label {
  color: #767676;
  background: #ffffff;
}
WHAT JUST HAPPENED Both grays might look "fine" side by side in a color picker. Only one of them actually clears the 4.5:1 bar. This is exactly why you check contrast with a real calculation instead of eyeballing it — your eyes, on a bright calibrated monitor, are the least representative test available. Try both pairs in the Contrast Checker in the Command Console below.
▸ DEEP DIVE: How is "contrast ratio" actually calculated?

Contrast ratio isn't a vibe, it's real math on real numbers. First, each color's relative luminance is calculated — a 0-to-1 number for how bright it is to the human eye. Each of the R, G, and B channels (0-255) is normalized to 0-1, then "linearized" with a gamma-correction formula (because sRGB values aren't stored in a way that's linear with perceived brightness), then combined with weights that reflect how sensitive human vision is to each color: L = 0.2126·R + 0.7152·G + 0.0722·B — notice green is weighted over ten times heavier than blue, because our eyes are simply far more sensitive to green light. Once you have both colors' luminance (L1 for the lighter one, L2 for the darker one), the ratio is: (L1 + 0.05) / (L2 + 0.05). The +0.05 accounts for a small amount of ambient light scatter even in "pure" black. Plug in pure black and pure white and you get exactly 21:1 — the maximum possible contrast on a screen, and the number the Contrast Checker's JavaScript computes for real, live, as you drag the sliders.

Spacing Rhythm

Spacing that "looks off" almost always turns out to be inconsistent — 13px here, 22px there, 7px somewhere else — with no relationship between the numbers. A spacing scale fixes this the same way a type scale fixes font sizes: define a small set of values, all multiples of a base unit (4px and 8px are the most common bases), and use only those everywhere. The eye can't consciously name why evenly-rhythmed spacing "feels" more polished, but it reliably notices when it isn't.

CSS
:root {
  --space-1: 4px;
  --space-2: 8px;
  --space-3: 16px;
  --space-4: 24px;
  --space-5: 32px;
  --space-6: 48px;
}

.card {
  padding: var(--space-4);
}
.card > * + * {
  margin-top: var(--space-3);
}
WHAT JUST HAPPENED .card > * + * is a neat trick: it selects any element that immediately follows another element inside .card, adding consistent space between siblings without touching the first or last child. Combined with the spacing scale, every gap on the page traces back to one of six numbers — never a one-off guess.

Hierarchy Needs More Than One Signal

The most common design mistake isn't picking bad values — it's changing only one property and expecting it to carry the whole hierarchy. Making a heading bigger without also making it bolder or a different color is a weak signal; making it bigger, bolder, and colored is unmistakable. The same logic applies to a primary action button: it should look important before anyone reads what it says.

CSS
.btn-primary {
  background: var(--accent);
  color: var(--bg-void);
  font-weight: 700;
  padding: var(--space-2) var(--space-4);
  border-radius: 8px;
}

.btn-secondary {
  background: transparent;
  color: var(--text-secondary);
  border: 1px solid var(--border-glow);
  padding: var(--space-2) var(--space-4);
  border-radius: 8px;
}
WHAT JUST HAPPENED Both buttons are the exact same size and shape — the padding values are identical. The entire hierarchy between "the important one" and "the other one" is carried by fill color, text color, and weight. That's the tell of a deliberately-designed UI: importance is signaled on purpose, not left to chance.

⚠ COMMON MISTAKES

  • Light-gray-on-white text that looks crisp on a bright designer monitor and fails 4.5:1 for everyone else.
  • Making a heading bigger without also making it bolder or recoloring it — size alone is a weak hierarchy signal.
  • Spacing values that "feel off" because they're copy-pasted one-offs (13px, 22px, 7px) instead of a defined scale.
  • Picking colors first and checking contrast never — treating accessibility as a last-minute pass instead of a design constraint from the start.
  • Using five or more font sizes on one page because nobody defined a scale before styling began — the "ransom note" effect.
