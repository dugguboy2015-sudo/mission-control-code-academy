MISSION 1.6: POSITIONING & RESPONSIVE DESIGN

Mobile-First, Media Queries

Your interfaces so far have assumed one screen. But the console you're building will get viewed on a cadet's phone in a docking bay, a tablet in a briefing room, and a full bridge display in the control center — and you don't get to pick which. This mission covers two tools that solve that problem together: the position property, for pulling an element out of normal flow on purpose, and responsive design, the discipline of writing layouts that reflow correctly no matter what size screen they land on.

🟡 OFFICER LEVEL ⏱ ~50 MIN 🛠 BROWSER ONLY
1

Briefing

Every layout you've built so far lives in normal flow — block elements stack top to bottom, inline elements sit left to right, and Flexbox/Grid arrange children within that system. Normal flow is predictable, but sometimes you need to break it deliberately: pin a status bar to the top of the screen no matter how far the cadet scrolls, float a tooltip next to a button, or dock a "return to bridge" button in the corner. That's what the position property is for — it's not a layout system like Flexbox, it's an escape hatch from one.

The second problem is older and bigger: your CSS doesn't know how wide the screen will be. A layout hardcoded to look perfect at exactly 1200 pixels wide looks broken at 375. For most of the web's history, this meant designing for a desktop monitor and then patching things up for smaller screens as an afterthought — usually badly. The modern approach flips that order entirely: mobile-first design means you write your base styles for the smallest, most constrained screen first, then use media queries to add complexity — extra columns, wider spacing, side-by-side layouts — only once there's room for it.

Think of it like designing your ship's console to work as a wrist display first. Once you've proven the core controls work in that cramped space, you scale up: add more readouts on a tablet, add a full sensor sweep on the bridge's main screen. You never design "big first, then cram it small" — that's backwards, and it's why so many old sites feel broken on phones.

Mobile-first: write the base layout for the phone, then use min-width media queries to progressively add complexity as more space becomes available.
2

Field Manual

The position Property

Every element has a position value, and it defaults to static — normal flow, no special behavior. Four other values pull an element out of that flow in different ways.

CSS
static    /* default — normal flow, top/left/right/bottom do nothing */
relative  /* stays in flow, but top/left/etc. nudge it FROM where it would be */
absolute  /* removed from flow, positioned against its nearest positioned ancestor */
fixed     /* removed from flow, positioned against the browser viewport */
sticky    /* relative until a scroll threshold, then behaves like fixed */
WHAT JUST HAPPENED The most important idea here is the containing block. An absolute element positions itself relative to the nearest ancestor that is not static — usually one you deliberately set to position: relative for exactly this reason. If no ancestor qualifies, it falls all the way back to the whole page, which is almost never what you wanted — that's the classic "why did my box jump to the top-left corner of the entire site" bug.
CSS
.card {
  position: relative; /* establishes the containing block */
}

.badge {
  position: absolute;
  top: 8px;
  right: 8px; /* positioned relative to .card, not the page */
}
WHAT JUST HAPPENED This is the single most common real use of positioning: a "NEW" ribbon on a card, a close button in a modal's corner, a notification dot on an icon. The parent opts in with relative (it doesn't even need to move — top/left are optional on it), and the child is pinned inside it with absolute.

Why Fixed Pixels Break

Screens vary enormously: a phone might be 375px wide, a laptop 1440px, an ultrawide monitor over 3000px. If you write width: 1000px on a container, that container is 1000px wide on every device — including phones, where it forces a horizontal scrollbar and cuts off content. Fixed pixel widths assume a screen size that doesn't exist for every visitor.

THE KEY IDEA It's not that px is bad — it's fine for things that should genuinely stay a fixed size (a 1px border, a 24px icon). The mistake is using it for anything that should adapt — overall widths, section padding, font sizes on a headline. Those need units that scale with the environment, not the ruler.

Mobile-First & Media Queries

A media query is a conditional block of CSS that only applies when the browser window matches a condition — most commonly a minimum or maximum width. Mobile-first design uses min-width queries exclusively: write the plain, unwrapped CSS for the smallest screen, then layer on rules that only activate once the screen is at least that wide.

CSS
/* base styles = mobile, no media query needed */
.nav-links { display: none; }
.cards { flex-direction: column; }

/* tablet and up */
@media (min-width: 600px) {
  .nav-links { display: flex; }
}

/* desktop and up */
@media (min-width: 900px) {
  .cards { flex-direction: row; }
}
WHAT JUST HAPPENED Every browser, even on a huge monitor, still loads and applies the base mobile styles first — the media queries only add or override on top. This is why mobile-first CSS tends to be shorter and less contradictory than desktop-first CSS, which usually needs max-width queries fighting to undo desktop styles on the way down. The exact pixel value where a layout changes (600px, 900px, whatever) is called a breakpoint — pick them based on where your own content starts to look cramped, not a "standard" list.

Relative Units

Alongside media queries, the units you size things in matter just as much. % sizes an element relative to its parent's size. rem sizes relative to the root (<html>) font size — so if a cadet bumps their browser's default text size up for readability, everything sized in rem scales with them. vw and vh size relative to the viewport itself — 1vw is always exactly 1% of the current window width, 1vh is 1% of its height.

CSS
.sidebar { width: 30%; }         /* 30% of its parent's width */
body { font-size: 1rem; }         /* the root size — 16px by default */
h1 { font-size: 2.5rem; }         /* scales with the root, not fixed at 40px */
.hero { min-height: 60vh; }       /* 60% of the visible viewport height */
WHAT JUST HAPPENED A good default rule of thumb: use rem for font sizes and spacing, % for widths inside a layout, vh/vw sparingly for "take up the whole screen" effects (like a full-height hero section), and reserve px for things that genuinely shouldn't scale — borders, small fixed icons, shadow offsets.
▸ DEEP DIVE: sticky's quirks, and the vh scrollbar gotcha

position: sticky looks like magic but has real rules: it only works within its immediate parent's box, and it needs a threshold to stick to — top: 0 means "stick when this element's top edge reaches the top of the viewport (or scrolling ancestor)." If the parent's height is exactly the same as the sticky child, there's no room to "scroll past" it, so it never appears to stick at all. It also silently stops working if any ancestor has overflow: hidden or overflow: auto — sticky is relative to the nearest scrolling container, and clipped overflow breaks that chain.

Separately: 100vh is defined as 100% of the viewport, but on many mobile browsers the viewport height changes as the address bar shows and hides while scrolling — so a 100vh element can be taller than what's visible, causing an awkward jump. On desktop, a vertical scrollbar can also eat into the width 100vw reports, causing a razor-thin horizontal scrollbar to appear. Neither is a bug in your CSS — they're both viewport-unit quirks worth knowing about before you're debugging them at 11pm.

▸ HINT

If your absolute-positioned element is landing somewhere unexpected, it's almost always the containing-block rule: it's looking for the nearest ancestor that is relative, absolute, fixed, or sticky, and if it doesn't find one, it keeps climbing all the way up to the page. Add position: relative; to the direct parent you actually want it pinned inside.

⚠ COMMON MISTAKES

  • Designing desktop-first, then fighting a wall of max-width media queries trying to undo styles for small screens instead of building up from them.
  • Using position: absolute without a relative ancestor, then being surprised the element lands in the corner of the entire page.
  • Hardcoding widths in px for containers that should flex with the screen, forcing a horizontal scrollbar on phones.
  • Expecting sticky to work while an ancestor has overflow: hidden or overflow: auto — it silently stops sticking.
  • Picking breakpoints from a "standard list" instead of the point where your own content actually starts looking cramped.

Quick check — you set position: absolute on an element, and its parent has no position value set at all (so it's static). Where does the element position itself against?
