MISSION 7.8: AI ECONOMICS & MODEL SELECTION

Token Math, Routing, Fallbacks

Mission 5.6 taught you to napkin-math a free tier's request limit before building. LLM APIs raise the stakes: nearly every provider charges per token, input and output priced separately, and the "best" model is often 10-50x more expensive per token than a smaller one. Choosing a model, and knowing roughly what a feature will cost per month before you ship it, is a real engineering skill — not an afterthought for when the bill arrives.

1

Briefing

Every LLM API call costs something measured in tokens (Mission 7.1) — almost always priced per million tokens, with input tokens (what you send) and output tokens (what comes back) billed at different rates, output usually costing more. A single request might cost a fraction of a cent — but multiply that by thousands of users making dozens of requests a day, and Mission 5.6's exact napkin-math habit becomes essential again, just with dollars instead of a free-tier request count.

2

Field Manual

Token-Based Pricing, Concretely

Pricing is usually quoted as a rate per million tokens, separately for input and output. Doing the math for one request looks like this:

JAVASCRIPT
const inputPricePerMillion = 0.15;   // dollars per 1,000,000 input tokens
const outputPricePerMillion = 0.60;  // output is often pricier than input

const inputTokens = 400;
const outputTokens = 150;

const cost = (inputTokens / 1_000_000) * inputPricePerMillion
           + (outputTokens / 1_000_000) * outputPricePerMillion;

console.log(cost); // cost of ONE request, in dollars
WHAT JUST HAPPENED Notice output is priced separately and higher — a chatty, verbose response costs meaningfully more than a terse one, even at the exact same input. This is a real, controllable lever: instructing a model to be concise (Mission 7.2) isn't just a style choice, it directly reduces cost.

Matching Model Size to Task Difficulty

Not every request needs the most capable (and most expensive) model available. Classifying a support ticket's category, extracting a date from text, or summarizing a short paragraph are all tasks a smaller, cheaper, faster model handles perfectly well. Reserve the expensive model for genuinely hard reasoning tasks. This is called model routing: automatically picking a cheaper model for easy requests and only escalating when the task actually needs it.

JAVASCRIPT
function chooseModel(taskComplexity) {
  // taskComplexity: "simple" | "moderate" | "complex"
  if (taskComplexity === "simple") return "small-fast-model";
  if (taskComplexity === "moderate") return "mid-tier-model";
  return "large-reasoning-model";
}
WHAT JUST HAPPENED A real production system often uses a cheap, fast model just to classify how hard a request is, THEN routes to the appropriate model based on that classification — spending real money on the expensive model only for the requests that actually justify it.

Fallbacks — When the Provider Fails

Every external API can go down, rate-limit you, or time out — Mission 4.6 covered this for a plain fetch, and it applies just as much here. A production AI feature needs a fallback: a backup plan for when the primary call fails, rather than the whole feature breaking.

JAVASCRIPT
async function callWithFallback(primaryFn, fallbackFn) {
  try {
    return await primaryFn();
  } catch (err) {
    console.warn("Primary model failed, falling back:", err.message);
    return await fallbackFn();
  }
}
WHAT JUST HAPPENED If your primary provider is down or rate-limited, this pattern automatically tries a second option — a different model, a different provider, or even a simpler canned response — instead of the user seeing a hard failure. This is the same try/catch structure from every earlier mission, applied to resilience instead of validation.

Mission Challenge

You're planning a study-helper chatbot for your class of 30 students.

▸ HINT

Output tokens are usually the bigger cost driver for a chatty assistant — if your estimate looks too high, check whether you're overestimating average reply length before assuming the model choice itself is the problem.

BONUS OBJECTIVE

Extend routeModel() so it also considers a cost budget: if the running monthly total (a number you track yourself) is already over a limit you set, force every request down to the cheapest model regardless of complexity. This is a real technique called a cost-based circuit breaker.

⚠ COMMON MISTAKES

  • Always reaching for the most powerful (and most expensive) model available, even for trivial tasks a cheap model handles fine.
  • Forgetting output tokens are usually priced higher than input — an unnecessarily verbose system prompt asking for long replies costs more than it needs to.
  • Building an AI feature with no fallback at all — a single provider outage takes the whole feature down.
  • Estimating cost using only a handful of test requests instead of realistic expected usage at real scale.
