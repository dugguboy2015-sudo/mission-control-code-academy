MISSION 7.7: AI IN THE UI

Streaming, Loading States, Guardrails

Mission 4.6 taught you to make a slow fetch honest with loading and error states. An LLM response is often slower still — sometimes many seconds for a long reply — and a real AI product doesn't make you stare at a blank spinner that whole time. This mission covers the UI patterns specific to AI features: streaming partial output as it's generated, managing a growing conversation history, and guardrails that catch bad input before it's sent and bad output before it's shown.

🔴 COMMANDER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Recall Mission 7.1's prediction loop: a model produces text one token at a time. Real LLM APIs let you receive those tokens as they're generated, rather than waiting for the entire response to finish before sending anything back. Displaying them the instant they arrive — a growing block of text with a blinking cursor at the end — is called streaming, and it's the difference between a chat feeling instant versus feeling stuck.

2

Field Manual

Consuming a Streamed Response

A real streaming API sends the response in small chunks over time instead of one single block. Your client code reads each chunk as it arrives and appends it to the visible text.

JAVASCRIPT
async function streamChat(messages, onToken) {
  const response = await fetch('/api/chat-stream', {
    method: 'POST',
    body: JSON.stringify({ messages }),
  });

  const reader = response.body.getReader();
  const decoder = new TextDecoder();

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    onToken(decoder.decode(value));
  }
}
WHAT JUST HAPPENED Instead of one await response.json(), streaming uses a reader that you pull chunks from repeatedly inside a Mission 6.3-style while loop, stopping only when done becomes true. Each chunk is handed to a callback (onToken) so the caller decides what to do with each piece — usually, appending it straight to the screen.

Managing Conversation History

Each turn of a chat appends both the user's message and the assistant's reply to the same messages array from Mission 7.2, and the entire array is resent on the next turn — the model has no memory of its own between requests, exactly as Mission 7.1 established.

JAVASCRIPT
const conversation = [{ role: "system", content: "You are a helpful assistant." }];

function addUserMessage(text) {
  conversation.push({ role: "user", content: text });
}

function addAssistantMessage(text) {
  conversation.push({ role: "assistant", content: text });
}

// Every call resends the WHOLE conversation so far — the model has no
// memory between requests.
WHAT JUST HAPPENED This array only grows — it never gets shorter on its own. Mission 7.9 covers exactly what happens once it grows too large to fit in the model's context window, and what to do about it.

Guardrails: Before You Send, and Before You Show

A production AI feature checks in both directions. An input guardrail validates the user's message before it's ever sent — rejecting an empty message, one that's absurdly long, or one containing something your app explicitly disallows. An output guardrail checks the model's reply before displaying it — catching an empty response, one that's suspiciously short, or one that failed to follow an expected format.

WHY BOTH DIRECTIONS MATTER Input guardrails protect your app (and your API bill) from obviously bad requests before they even cost you a token. Output guardrails protect your user from a broken or inappropriate reply reaching their screen. Skipping either one leaves a real gap — a users-only chat feature with no input guardrail is an open door for abuse; one with no output guardrail is one bad model response away from an embarrassing screenshot.

⚠ COMMON MISTAKES

  • Waiting for the entire response before showing anything, when the API actually supports streaming — a slower-feeling app for no real reason.
  • Forgetting to append the assistant's own reply back into the conversation history, breaking multi-turn context on the next message.
  • Only checking output for correctness, never checking input — leaves the app open to obviously bad or abusive requests.
  • A guardrail that just silently drops a bad request with no feedback, leaving the user confused about why nothing happened.
