MISSION 5.6: WHAT A BACKEND IS

Serverless Functions & a Tiny API

Every mission so far has drawn a line between "code running in the visitor's browser" and "code running somewhere else, on a server you don't personally manage." Supabase and Firebase are both examples of someone else's backend that you talk to through an SDK. This mission pulls back the curtain on what a backend actually is when YOU write it — and introduces the modern, lightweight way to do that without ever managing a physical server: the serverless function.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

Client-side JavaScript — everything you've written since Sector 2 — runs entirely inside the visitor's own browser. That means anyone can open DevTools and read every line of it, including any secret you accidentally left in there. A backend is code that runs somewhere else instead: on infrastructure only you control, where a visitor can send it a request and get a response back, but can never see the code itself or anything it's holding onto in memory (like a secret API key).

The browser never touches the secret key directly — it asks the serverless function to do the work, and only the response comes back.
2

Field Manual

What "Serverless" Actually Means

Despite the name, there's still a physical server somewhere — you just never manage it. Traditionally, running backend code meant renting a server that stays on 24/7, whether or not anyone's using it, and you're responsible for patching, scaling, and monitoring it yourself. A serverless function flips that: you upload a small function, the platform (Cloudflare Workers, in this Academy's own stack) runs it automatically the instant a request arrives, and it disappears again the moment it's done. You're billed for actual usage, not idle time — and it scales from zero requests to a million without you touching any configuration.

Anatomy of a Tiny Serverless Function

A serverless function is almost always the same simple shape: it receives a request, does something with it, and returns a response.

JAVASCRIPT (Cloudflare Worker)
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const name = url.searchParams.get('name') || 'Cadet';

    return new Response(
      JSON.stringify({ message: `Welcome aboard, ${name}!` }),
      { headers: { 'Content-Type': 'application/json' } }
    );
  }
};
WHAT JUST HAPPENED This is a complete, real, deployable backend — the entire "server." It reads a query parameter straight out of the incoming request's URL, builds a small JSON response, and sends it back with the right content type. Nothing here needs a database or a framework; a real API is built by adding more logic to functions shaped exactly like this one.

Environment Variables & Secrets

Some values are genuinely safe to ship in client code — this Academy's own SUPABASE_ANON_KEY in config.js is a public, deliberately-restricted key, safe by design. A secret API key for a paid third-party service is the opposite: if it leaks, anyone can rack up charges on your account. Secrets belong in environment variables — values configured on the server platform itself (Cloudflare's dashboard, in this stack) that your function can read at runtime, but that are never included in any file your browser ever downloads.

JAVASCRIPT (Cloudflare Worker)
export default {
  async fetch(request, env) {
    // env.SECRET_API_KEY was set in the Cloudflare dashboard, never in code
    const response = await fetch('https://api.example.com/data', {
      headers: { Authorization: `Bearer ${env.SECRET_API_KEY}` }
    });
    return response;
  }
};
WHAT JUST HAPPENED The Worker reads env.SECRET_API_KEY — a value that exists only inside Cloudflare's servers — and uses it to authenticate a request to another service on the visitor's behalf. The visitor's browser only ever sees the final response, never the key. This exact pattern is how Sector 7 will safely put an AI provider's API key behind your own backend instead of the browser.

Doing the Free-Tier Math Before You Build

Every serverless platform's free tier is shaped as a limit on some unit of usage — usually requests per day. Before committing to a design, it's worth doing simple napkin math: estimated users × actions per user per day = total daily requests. Compare that number to the free tier's daily limit, and you know, before writing a single line of code, whether a feature will stay free or start costing money at the scale you expect.

WHY THIS HABIT MATTERS This isn't about memorizing today's exact numbers — providers change their limits over time, so always check the current pricing page for a real project. The habit that matters, and the one Sector 7 leans on constantly once AI API costs enter the picture, is doing this multiplication before you build, not discovering the answer from a surprise bill afterward.

⚠ COMMON MISTAKES

  • Putting a real secret API key in client-side JavaScript "just for now" — anyone can view-source it immediately.
  • Assuming a serverless function stays "warm" and keeps state between requests — treat every single request as a fresh start.
  • Never estimating usage against a free tier's limit before building, then being surprised by a paused project or a bill.
  • Confusing "serverless" with "no server exists at all" — there's still a server, you just don't manage it yourself.
