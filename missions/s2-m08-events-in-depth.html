MISSION 2.8: EVENTS & INTERACTIVITY IN DEPTH

Bubbling, Delegation, Real Apps

Mission 2.1 taught you addEventListener as "attach a function, wait for a click." That's true, but it's the shallow version. Every event carries a full object of information, travels through the page in a very specific order, and can be caught by more than one listener at once. Understanding that mechanism is what separates a page that barely works from one that scales — because the professional pattern for handling lists, dynamic content, and forms depends entirely on it.

🟡 OFFICER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Picture an alarm going off on the lowest deck of a starship. It doesn't stay there. It echoes upward — deck by deck, through every level of the command structure — until it reaches someone (or something) positioned to actually handle it. Nobody had to wire a separate alarm line from that one deck straight to the bridge; the ship's structure itself carries the signal upward automatically. That's event bubbling, and it's not a special trick — it's simply how every event in the DOM behaves by default.

When a cadet clicks a button nested three layers deep in your page, the click doesn't just happen on that button and vanish. It fires there first — that exact element is called the target — and then the same event travels upward, layer by layer, through every single ancestor element, all the way up to document itself. Any of those ancestors can have a listener that hears it.

Once you really understand that, a hugely useful pattern falls out almost for free: instead of attaching a separate listener to every single button in a list (tedious, and impossible for buttons that don't exist yet), you can attach one listener to the parent and let bubbling carry every click up to it. That's called event delegation, and it's how real, professional interfaces handle dynamic lists, tables, and menus — including the DOM-manipulation techniques from Mission 2.7, where elements get added and removed constantly.

A click always fires on the exact element under the cursor first (the target) — then the identical event travels upward through every ancestor in order. Any ancestor with a listener can hear it, all the way up to document.
2

Field Manual

The Event Object

Every listener function automatically receives one argument: the event object. It's a detailed report of exactly what just happened, and it's how your code reacts precisely instead of guessing.

JAVASCRIPT
const panel = document.querySelector("#controlPanel");

panel.addEventListener("click", function(event) {
  console.log(event.type);          // "click"
  console.log(event.target);        // the exact element that was clicked
  console.log(event.currentTarget); // the element the listener is attached to
});
WHAT JUST HAPPENED event.currentTarget is always panel here — whatever element the listener is physically attached to. event.target is different: it's whichever element the cadet actually clicked, which might be a button, an icon inside that button, or a stray bit of text — anything nested inside panel. When those two are the same element, it's easy to miss the distinction. It stops being optional the moment you start using delegation, below.

Event Bubbling

Bubbling means an event doesn't just fire once on its target — it fires again on every ancestor, in order, as it climbs the tree. This is the default behavior for almost every event type, with no extra code required.

JAVASCRIPT
document.querySelector("#child").addEventListener("click", function() {
  console.log("1. child was clicked directly");
});

document.querySelector("#parent").addEventListener("click", function() {
  console.log("2. parent heard it too — the event bubbled up");
});
WHAT JUST HAPPENED Clicking #child logs both lines, in that exact order. The click fires on #child first (it's the target), and then the same click event continues upward and fires again on #parent, because #parent is an ancestor with its own "click" listener. Neither listener knows about the other — bubbling is happening automatically underneath both of them.

Event Delegation — The Professional Pattern

Once you know clicks bubble upward, a better strategy appears: don't attach a listener to every child. Attach one listener to their shared parent, and use event.target inside it to figure out which child actually got clicked.

JAVASCRIPT
// Fragile: only covers items that exist right now
document.querySelectorAll(".crew-item").forEach(function(item) {
  item.addEventListener("click", handleCrewClick);
});

// Delegation: ONE listener, works for items added later too
document.querySelector("#crewList").addEventListener("click", function(event) {
  const item = event.target.closest(".crew-item");
  if (!item) return; // click landed somewhere else in the list
  handleCrewClick.call(item, event);
});
WHAT JUST HAPPENED event.target.closest(".crew-item") starts at whatever was actually clicked and walks upward until it finds an element matching that selector (or returns null if it never does) — which matters because a cadet might click a bit of text or an icon inside the item, not the item element itself. Because this listener lives on #crewList and only reads event.target at the moment of the click, it doesn't matter whether a given .crew-item existed when the page loaded or got added by Mission 2.7's DOM code five minutes ago. Delegation checks at click-time, not at wiring-time — that's the entire benefit.

Other Event Types & preventDefault()

Clicks aren't the only event worth knowing. "input" fires as a text field's value changes (every keystroke), "keydown" fires when any key is pressed, and "submit" fires on a <form> right before the browser tries to send it off and reload the page — which is almost always the exact moment you want to step in.

JAVASCRIPT
const form = document.querySelector("#loginForm");

form.addEventListener("submit", function(event) {
  event.preventDefault(); // stop the default full-page reload
  console.log("Handled with JavaScript instead of reloading.");
});

document.querySelector("#search").addEventListener("input", function(event) {
  console.log("current value:", event.target.value);
});
WHAT JUST HAPPENED A plain HTML form's default behavior — the one baked into browsers since the 1990s — is to package up its fields and reload the page to submit them. That reload wipes out every bit of JavaScript state you had. event.preventDefault() tells the browser "I've got this one" and cancels only that default action; everything else about the event (including bubbling) still works normally. It has to be called inside the handler, synchronously — there's no way to prevent a default after the fact.
▸ DEEP DIVE: event.stopPropagation()

If bubbling always happens, is there a way to stop it? Yes — event.stopPropagation(), called inside a handler, prevents the event from continuing to bubble any further up the tree. A real use case: a delegated listener on a list closes a details panel whenever you click anywhere in it, but each list item also has its own small "delete" button that should only delete — not also trigger the "open details" behavior on its way up. Calling stopPropagation() inside the delete button's own click handler stops that specific click from reaching the list's listener at all.

Use it sparingly. It's easy to reach for it defensively and then be baffled later when some completely unrelated, perfectly legitimate listener further up the page — a "click anywhere to close this menu" handler, for example — mysteriously stops firing. Only stop propagation when you have a specific ancestor listener in mind that you deliberately don't want to hear this particular click.

⚠ COMMON MISTAKES

  • Attaching a listener to an element that doesn't exist yet — the script ran before that part of the page was created.
  • Forgetting that elements added after page load need delegation, or their own brand-new listener — an old listener never retroactively covers new elements.
  • Confusing event.target (what was actually clicked) with event.currentTarget (what the listener is attached to) — they're only the same element when there's no nesting involved.
  • Forgetting event.preventDefault() on a form's "submit" listener and getting a jarring full-page reload that wipes out every bit of JavaScript state.
  • Reaching for stopPropagation() defensively and accidentally breaking an unrelated, perfectly legitimate listener further up the page.
