MISSION 0.3: YOUR WORKSHOP

Editor, Files, Running Things, DevTools — and Your AI Co-Pilot

Every engineer has a workshop — a set of tools they know cold, so well that using them stops taking any thought at all. Yours has four parts: a code editor where you write, a terminal where you run things, a browser's DevTools where you inspect what's actually happening, and — increasingly, for every engineer alive today — an AI coding assistant that can write code alongside you. This mission sets up all four, and teaches you the single most important rule for that last one before you ever touch it for real.

🟢 CADET LEVEL ⏱ ~35 MIN 🛠 EDITOR + TERMINAL
1

Briefing

Think of your workshop as mission control itself. The editor is where you write the instructions — a text editor built specifically for code, with features a plain notepad doesn't have: syntax highlighting, error detection, and file management. The terminal is a direct, typed line to your computer's operating system — instead of clicking icons, you type exact commands, and it's faster and more powerful once it's familiar. DevTools, built into every browser, is your window into what a webpage is actually doing right now — you already used its Network tab in Mission 0.2.

The fourth tool is newer, and it changes how engineers work more than anything since the internet itself: an AI coding assistant. It can write working code from a plain-English description, explain a confusing error, or suggest a fix — often in seconds. Used well, it's the single biggest force-multiplier available to you. Used carelessly, it's how people ship code they don't understand and can't fix. This mission draws the line clearly, before you lean on it for anything real.

Four tools, one workshop — the AI co-pilot feeds drafts into the same editor/terminal/DevTools loop you already control.

Field Manual

Your Code Editor

A code editor (the most widely used free one is Visual Studio Code, "VS Code") is a text editor with superpowers built specifically for writing code: it colors your code by meaning (syntax highlighting — you've seen this in every code block in this academy), flags likely mistakes before you even run anything, and organizes your work into projects — a folder containing every file your app needs, kept together on purpose.

THE KEY IDEA Always open your editor on the whole project folder, not a single file. Real projects are made of many files working together (HTML, CSS, JS, images) — your editor needs to see the whole folder to help you navigate between them and catch errors that span files.

The Terminal

The terminal takes typed commands instead of clicks. It sounds old-fashioned; it's actually faster and more precise once you know a handful of commands, and it's how you'll run programs, install tools, and use Git starting in Mission 3.1.

BASH
pwd   # print working directory — "where am I right now?"
ls    # list — "what's in this folder?"
cd missions   # change directory — "go into the missions folder"
ls
cd ..    # go back up one level
WHAT JUST HAPPENED Every terminal session has a "current location" in your file system, exactly like the browser's URL points at a specific address. pwd tells you where you are, ls tells you what's around you, and cd moves you — the three commands you'll type more than any others.
▸ DEEP DIVE: Windows uses different names for some commands

On Windows' own Command Prompt, the list command is dir instead of ls, though pwd, cd, and cd .. work the same. If you install Git for Windows (which you'll need for Mission 3.1 anyway), it comes with "Git Bash," a terminal that uses the same commands shown here — that's what most of this academy assumes.

Browser DevTools

You already used the Network tab in Mission 0.2. DevTools has two other tabs you'll live in constantly: Elements shows you the live DOM tree of the current page — you can click any element on screen and jump straight to its HTML — and Console shows error messages and lets you run JavaScript directly against the live page, which is exactly how the sandboxes in this academy work under the hood.

Your AI Co-Pilot — The One Rule That Matters

An AI coding assistant is extremely capable and occasionally, confidently wrong. It can produce code that looks perfect, runs without errors, and still does the wrong thing — the same gap between "precise" and "correct" you explored with the Literal Robot in Mission 0.1, just harder to spot because the output is fluent, real code instead of an obviously silly action.

THE RULE AI writes the first draft. You are the engineer who reads it, understands it, tests it, and takes responsibility for it. If you can't explain what a piece of AI-written code does, you don't get to use it yet.

This isn't caution for its own sake — it's the actual skill. A junior engineer who can prompt well, read critically, test thoroughly, and catch a subtly wrong suggestion is far more valuable than one who can only copy-paste. You'll practice this explicitly and often, starting with the checklist below and returning to it throughout the academy — it's Thread 1 of what it means to build AI-native systems, and it starts now, not in Sector 7.

⚠ COMMON MISTAKES

  • Opening a single file in your editor instead of the whole project folder — you lose cross-file navigation.
  • Pasting AI-generated code straight into a real project without reading it first.
  • Assuming code that "runs without errors" must be correct — the Literal Robot lesson applies here too.
  • Never checking DevTools Console when something looks wrong — it's usually the very first thing to check.
