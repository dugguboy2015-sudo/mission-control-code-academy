MISSION 1.3: CSS FUNDAMENTALS & THE BOX MODEL

Selectors, the Cascade, Box Model

You've already met CSS selectors and a light touch of the cascade back in Mission 1.4's detour through Flexbox. This mission goes deeper on both — and then spends most of its time on something every single element on every page you'll ever build has to obey: the box model. Once you can predict exactly how big a box actually is on screen, and exactly which rule wins when two fight over the same property, a huge category of "why is this broken" mysteries stops being mysterious.

🟢 CADET LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Think of CSS selectors as the ship's addressing system. Mission Control doesn't broadcast "hey, everyone" when it needs one console recalibrated — it targets a precise address: a deck, a station, a specific piece of hardware. Selectors work the same way: they're how a style rule says exactly which element(s) on the page it's talking to, whether that's "every paragraph," "every element wearing this class badge," or "this one specific, unique component."

But addressing systems create a new problem: what happens when two different orders target the same station with conflicting instructions? That's where the cascade comes in — CSS's rank-and-seniority system for resolving conflicts. It's not random and it's not "whichever loads last always wins" (though source order is part of it). It's a scoring system called specificity, and once you know the ranks, you can always predict the winner instead of guessing.

Then there's the box model — arguably the single most load-bearing concept in all of CSS. Every element on a page, no matter how it looks, is secretly a rectangle, and every rectangle is built from the same four stacked layers: content, padding, border, and margin. This is literally how much physical deck space a component claims on your layout — get it wrong and things overlap, overflow, or mysteriously refuse to line up, no matter how correct your colors and fonts are.

Finally, there's a setting called box-sizing that changes what "width" even means for a box. Get this one concept solid and an enormous number of "my math doesn't add up" layout bugs simply stop happening.

The box model, four layers deep: content sits inside padding, padding sits inside the border, and margin is empty space pushing every other box away. Every element you will ever style is built from these four nested rectangles.

Field Manual

Selectors Recap

A quick refresher on the four selector types you'll use constantly, plus two ways to combine them so you can target elements based on where they sit in the page's structure.

CSS
p {
  color: #a8b3d1; /* element selector — every <p> */
}

.status-card {
  background: #1b2540; /* class — reusable, any number of elements */
}

#launch-button {
  font-weight: bold; /* id — exactly one element on the page */
}

.status-card p {
  font-size: 14px; /* descendant combinator: any p anywhere inside .status-card */
}

.status-card > h3 {
  color: #4ee1ff; /* child combinator: only a direct h3 child, not grandchildren */
}
WHAT JUST HAPPENED A space between two selectors means "descendant, no matter how deep" — .status-card p matches a paragraph nested five layers inside a status card. A > means "direct child only" — .status-card > h3 skips any h3 that isn't an immediate child. IDs should appear exactly once per page; classes are meant to be reused across many elements.

Specificity & the Cascade

When two rules target the same element and disagree, CSS doesn't guess — it scores each selector's specificity and the higher score wins. From lowest to highest rank: element selectors (like p) score lowest, class selectors (like .status-card) beat them, ID selectors (like #launch-button) beat classes, and an inline style="..." attribute beats everything written in a stylesheet. If two rules have equal specificity, the one that appears later in the source wins — that's the actual "cascading" part.

CSS
.status-card {
  color: white;
}

#launch-button {
  color: yellow; /* wins: ID beats class, regardless of order */
}

.status-card {
  color: cyan; /* loses to the ID above, even though it's written later */
}
WHAT JUST HAPPENED The element with id="launch-button" ends up yellow, full stop — source order only breaks ties between rules of equal specificity. It never lets a later, lower-specificity rule beat an earlier, higher-specificity one. If a style you wrote "isn't applying," this is almost always the reason: something more specific is quietly winning.
▸ DEEP DIVE: The exact specificity formula (and why to avoid !important)

Specificity is usually written as three numbers, (IDs, classes, elements). Each ID selector adds 1 to the first slot, each class (and attribute selector, and pseudo-class like :hover) adds 1 to the second, and each element/tag selector (and pseudo-element like ::before) adds 1 to the third. Compare left to right: (1,0,0) beats any number of classes, and (0,1,0) beats any number of elements. So .status-card p scores (0,1,1) — one class, one element — while #launch-button scores (1,0,0) and wins regardless.

There's a nuclear override: adding !important to a declaration makes it beat normal specificity rules almost entirely. It's tempting the first time you're stuck fighting a style — but avoid it. It doesn't fix the underlying specificity conflict, it just steamrolls it, and the next developer (often future-you) now has to fight an !important instead of a normal, readable rule. Reach for a more precise selector, or reorganize the CSS, before reaching for !important.

The Box Model

Every element is four nested rectangles. From the inside out:

  • content — where text and child elements actually live; sized by width and height
  • padding — transparent space between the content and the border; part of the element's own background
  • border — a visible (or invisible) line wrapping the padding, set with border-width, border-style, border-color
  • margin — space outside the border that pushes neighboring elements away; transparent, and not part of the element's own background
CSS
.status-card {
  width: 240px;
  padding: 20px;
  border: 4px solid #4ee1ff;
  margin: 16px;
}
WHAT JUST HAPPENED By default (the classic box-sizing: content-box behavior), width: 240px sets only the content width. The padding and border get added on top of that — so this box's actual visible footprint is 240 + 20+20 + 4+4 = 288px wide, and it claims 288 + 16+16 = 320px of total horizontal space once margin is counted. That gap between "the number I typed" and "the size it actually is" is the single most common source of layout confusion in CSS — which is exactly what the next section fixes.

content-box vs border-box

The box-sizing property changes what width and height actually measure. content-box (the historical CSS default) means width only describes the content — padding and border are added on top, growing the box. border-box means width describes the entire visible box, content-plus-padding-plus-border — so if you add padding, the content area shrinks to compensate, and the box's outer size never moves.

CSS
*, *::before, *::after {
  box-sizing: border-box; /* almost every real project sets this globally */
}
WHAT JUST HAPPENED With this reset applied, width: 240px on that same status card always renders as exactly 240px wide, no matter how much padding or border you add — the browser shrinks the content area to make room instead of growing the box. This is why nearly every real CSS project — and this academy's own stylesheet — starts with that universal selector reset. It makes width math predictable instead of something you have to recompute every time you touch padding.

⚠ COMMON MISTAKES

        
    
          
  • Forgetting box-sizing: border-box, then being confused when a width: 300px box measures wider than 300px on screen once padding and border are added.
    • 
          
  • Reaching for an ID selector (or !important) to "win" a specificity fight instead of writing a more precise, reusable class — it works today and becomes a nightmare to override later.
    • 
          
  • Confusing padding and margin — padding is inside the border and part of the element's own background; margin is outside it and always transparent.
    • 
          
  • Two vertically stacked block elements' margins can collapse into a single margin (the larger of the two) instead of adding together — a surprising default worth knowing before it surprises you.
    • 
          
  • Assuming source order alone decides which rule wins — it only breaks ties between rules of equal specificity, never overrides a higher-specificity rule written earlier.
