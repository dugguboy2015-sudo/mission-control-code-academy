MISSION 5.5: SUPABASE VS FIREBASE

SQL vs NoSQL — When to Choose Which

You've now built with both stacks: Supabase's relational Postgres tables in Mission 5.2, and Firebase's document-shaped Firestore in Mission 5.4. Neither one is "the right answer" — they're two different tools built on two different philosophies of storing data, and a real AI-architect-in-training needs to be able to look at a project and say which one fits, and explain why. That's the entire job of this mission — no new syntax, just judgment.

🔴 COMMANDER LEVEL ⏱ ~35 MIN 🛠 BROWSER ONLY
1

Briefing

The core difference is right there in the names of the categories: SQL databases (like Supabase's Postgres) store relational data — rigid tables of rows and columns, linked by foreign keys, queried with a shared, powerful query language. NoSQL databases (like Firebase's Firestore) store documents — flexible, JSON-like blobs grouped into collections, with no enforced shared structure and no built-in cross-collection JOINs.

Field Manual

Data Shape: Rigid Tables vs Flexible Documents

Recall the crew table from Mission 5.1 — every row has exactly the same columns, and the database itself rejects a row that's missing a required one. A Firestore document has no such guarantee: one crew document might have a callsign field and the next one might not, and Firestore is perfectly happy with both. That flexibility is genuinely useful for data that varies a lot between records — but it also means your application code is the only thing enforcing consistency, since the database won't do it for you.

Relationships & Query Power

This is where the two stacks diverge the most. In Mission 5.1 you built a many-to-many relationship with a crew_missions junction table and a single JOIN query pulled the connected data back in one shot. Firestore has no JOIN at all — connecting two collections means either running multiple separate queries in your own code, or denormalizing: deliberately duplicating a bit of data (like copying a crew member's name directly onto each mission document) purely to avoid a second lookup. That's the same duplication Mission 5.1 warned against for SQL — in Firestore, it's often the recommended approach.

THE TRADE-OFF, PLAINLY SQL makes you design your relationships carefully up front, then lets you query across them however you like, whenever you like. NoSQL lets you start writing data almost immediately, but pushes the relationship-modeling work onto you, later, one query pattern at a time — you often have to know your queries in advance and shape your documents around them.

Realtime, By Default vs By Request

Firestore's onSnapshot() listener (Mission 5.4) is realtime from the moment you write the query — any matching document that changes anywhere pushes an update to every listener instantly, with no extra setup. Supabase's realtime is opt-in: you subscribe to a channel that watches for Postgres row changes on a specific table. Both work well; Firestore's default-on realtime is a big part of why so many chat apps and live dashboards reach for it first.

Free-Tier Shape & Cost-Awareness

Sector 7 formalizes cost-checking as its own habit, but the instinct starts here: the two free tiers fail differently under real use. Supabase's free project pauses automatically after a week of inactivity (fine for a learning project, risky for something you want always-on). Firebase's Spark plan never pauses, but caps you on a per-operation basis — each read, write, and delete counts individually, so an app that reads the same data on every keystroke can burn through the free quota surprisingly fast without ever "storing too much."

WHAT JUST HAPPENED Neither of these numbers matters until you actually look them up for your specific project on each provider's current pricing page — free-tier limits change over time. The habit that matters is remembering to check before committing to a stack, not memorizing today's numbers.

A Practical Decision Guide

  • Reach for Supabase (SQL) when your data has clear, structured relationships you'll query in many different ways — a store, a booking system, anything with reports or dashboards over connected records.
  • Reach for Firebase (NoSQL) when you need realtime updates by default with minimal setup, your data is naturally document-shaped (a chat message, a game state, a user profile), and you don't yet know every query you'll need.
  • Either works fine for a huge range of small and medium projects — this Academy itself uses Supabase, but a nearly identical version of it could have been built on Firebase instead.

Mission Challenge

A friend wants to build a trivia game: players join a room from their phones, answers and scores update live on everyone's screen the instant anyone answers, and the data model is simple (a room, a list of players, a current question) — no complex reports needed.

▸ HINT

⚠ COMMON MISTAKES

  • Picking a stack based on which one is "more popular" instead of what the project's data and query needs actually look like.
  • Choosing NoSQL for data that's obviously relational (orders, inventory, users-and-roles) and then fighting the lack of JOINs the entire project.
  • Choosing SQL for something that's mostly one realtime feed (a chat, a live game state) and hand-building the realtime plumbing Firestore gives you for free.
  • Never checking either provider's current free-tier limits until a real bill or a paused project is the surprise.
