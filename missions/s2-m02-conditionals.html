Briefing

A ship's autopilot never runs a single fixed script from launch to landing. It's constantly evaluating conditions — fuel level, hull integrity, distance to the nearest object, whether a hatch is sealed — and every one of those checks can send the ship down a completely different path. Low fuel means divert to the nearest station. A hull breach means seal the compartment and alert the crew. Nothing wrong at all means keep cruising. The autopilot isn't smart because it has more code — it's smart because it has more branches.

In JavaScript, a conditional is a statement that runs one block of code or another based on whether something is true or false. You already saw a taste of this in Mission 2.1's checkFuelStatus function. This mission goes much deeper: how JavaScript actually decides what counts as "true," the full comparison and logic toolkit, and two more tools — the ternary operator and switch — for when if/else starts feeling clunky.

Get comfortable with this. Every program you'll ever write — a game, a form, an AI agent's decision loop — is fundamentally a pile of conditionals wearing a trench coat. Master branching and you've mastered the skeleton of all programming logic.

An if / else if / else chain as a decision tree. Each diamond is one question; JavaScript checks them top to bottom and stops at the first "yes." The final else has no question of its own — it catches everything that didn't match above it.

Field Manual

if / else if / else In Depth

An if statement runs its block only when the condition in parentheses evaluates to true. Chain as many else if blocks as you need for additional questions, and end with one plain else to catch whatever's left over. JavaScript checks each condition top to bottom and stops at the first one that matches — it never checks the rest, even if a later condition would also be true.

JAVASCRIPT
function checkShields(shieldPercent) {
  if (shieldPercent <= 0) {
    return "SHIELDS DOWN";
  } else if (shieldPercent < 25) {
    return "SHIELDS CRITICAL";
  } else if (shieldPercent < 70) {
    return "SHIELDS HOLDING";
  } else {
    return "SHIELDS AT FULL";
  }
}

console.log(checkShields(15)); // "SHIELDS CRITICAL"
WHAT JUST HAPPENED With shieldPercent = 15, the first check (<= 0) fails, the second (< 25) succeeds, and JavaScript returns immediately — it never even looks at the < 70 check or the final else. Order matters: if you'd written the < 70 check first, a value of 15 would incorrectly match it too, since 15 is also less than 70. Always order your conditions from most specific/extreme to least.

Comparison & Logical Operators

Comparisons produce a boolean (true or false): === and !== check equality/inequality, while <, >, <=, and >= compare order. Logical operators combine or invert booleans: && (AND) requires both sides true, || (OR) requires at least one side true, and ! (NOT) flips a boolean.

JAVASCRIPT
const fuel = 62;
const shieldsUp = true;
const hostileNearby = false;

// AND — both must be true
const readyToJump = fuel > 50 && shieldsUp;
console.log(readyToJump); // true

// OR — at least one must be true
const shouldRetreat = hostileNearby || fuel < 20;
console.log(shouldRetreat); // false

// NOT — flips a boolean
console.log(!shieldsUp); // false
WHAT JUST HAPPENED && and || also short-circuit: in a && b, if a is false, JavaScript never even evaluates b — the whole expression is already false. In a || b, if a is true, b is skipped. This isn't just an efficiency trick; it's a tool you'll use constantly (see the deep dive below). And always reach for ===, never == — == tries to convert mismatched types before comparing, so "5" == 5 is confusingly true, while "5" === 5 is correctly false because a string is never the same type as a number.

Truthiness & Falsiness

Any value, not just true/false, can be used where JavaScript expects a boolean — like inside an if condition. It gets converted to one automatically. Exactly six values convert to false ("falsy"); everything else converts to true ("truthy") — including things that feel like they should be false, like an object with no properties or the string "0".

JAVASCRIPT
// The complete list of falsy values in JavaScript:
if (false) {}      // falsy
if (0) {}          // falsy
if ("") {}         // falsy (empty string)
if (null) {}       // falsy
if (undefined) {}  // falsy
if (NaN) {}        // falsy (Not a Number)

// Everything else is truthy — even these:
if ("0") {}        // truthy! (non-empty string)
if ("false") {}    // truthy! (non-empty string)
if ([]) {}         // truthy! (an array, even an empty one)
if ({}) {}         // truthy! (an object, even an empty one)
if (-1) {}         // truthy! (any nonzero number)
WHAT JUST HAPPENED Memorize the six falsy values — false, 0, "", null, undefined, NaN — and treat literally everything else as truthy. This matters most when you write a shortcut like if (fuel) instead of if (fuel > 0): it looks like it means "if there's fuel," but it actually means "if fuel is anything except exactly 0, NaN, or a falsy value" — which is usually fine for a number, but becomes a real bug the moment a legitimately meaningful value like 0 needs to be treated as valid, not "missing."
▸ DEEP DIVE: Short-circuiting for default values

Because || stops at the first truthy value, it's a common shorthand for "use this value, unless it's missing, in which case fall back to a default":

JAVASCRIPT
function greetCadet(input) {
  const name = input || "Cadet";
  return "Welcome aboard, " + name;
}

console.log(greetCadet("Nova")); // "Welcome aboard, Nova"
console.log(greetCadet(""));     // "Welcome aboard, Cadet" (empty string is falsy)

Watch the trap, though: if a valid input could legitimately be 0 or "", this pattern wrongly replaces it with the default. Modern JavaScript has a safer cousin for exactly this case, ?? (nullish coalescing), which only falls back on null or undefined — worth knowing exists, even if || remains the more common shorthand you'll see in the wild.

The Ternary Operator

When an if/else only exists to pick between two values, the ternary operator — condition ? valueIfTrue : valueIfFalse — says the same thing in one line. It's an expression, meaning it produces a value directly, so it slots neatly into a variable assignment or a template string.

JAVASCRIPT
const fuel = 8;

// The long way:
let status;
if (fuel < 10) {
  status = "LOW";
} else {
  status = "OK";
}

// The ternary way — same result, one line:
const statusShort = fuel < 10 ? "LOW" : "OK";
console.log(statusShort); // "LOW"
WHAT JUST HAPPENED A ternary is a great fit for exactly-two-outcomes decisions — especially inline, like display.style.color = fuel < 10 ? "red" : "green";. It's a bad fit the moment you need more than two branches or your branches need multiple statements each; forcing a three-way decision into nested ternaries reads like a riddle. When in doubt, reach for if/else — clarity beats cleverness.

switch — Many Branches, One Value

A long if/else if chain that keeps testing the same variable against different exact values gets repetitive fast. A switch statement handles that pattern directly: it compares one value against a series of case labels using strict equality (===), and runs the matching block. break stops it from "falling through" into the next case, and default is the equivalent of a final else.

JAVASCRIPT
function describeSector(sectorId) {
  switch (sectorId) {
    case 1:
      return "Sector 1 — Home Systems";
    case 2:
      return "Sector 2 — Deep Code";
    case 3:
      return "Sector 3 — Version Drift";
    default:
      return "Uncharted sector";
  }
}

console.log(describeSector(2)); // "Sector 2 — Deep Code"
console.log(describeSector(9)); // "Uncharted sector"
WHAT JUST HAPPENED Because each case here returns immediately, we didn't strictly need break — returning already exits the function. But if a case just runs a statement (like a console.log) instead of returning, forgetting break means execution "falls through" and keeps running the next case's code too, whether you meant it to or not. That's the single most common switch bug — when in doubt, add the break.

⚠ COMMON MISTAKES

  • Writing a single = (assignment) inside a condition instead of === (comparison) — if (fuel = 0) silently sets fuel to 0 and then evaluates as falsy, instead of checking it.
  • Using == instead of === and getting surprising type-coercion results, like "0" == false being true.
  • Forgetting that the final else catches everything not already matched above it — a badly ordered chain can route unexpected values into the wrong branch.
  • Relying on plain truthiness (if (fuel)) for a number where 0 is a real, meaningful value rather than "missing" — it gets treated as false when it shouldn't be.
  • Forgetting break inside a switch case, causing execution to "fall through" into the next case unintentionally.
