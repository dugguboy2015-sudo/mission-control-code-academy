MISSION 1.9: CAPSTONE — YOUR PERSONAL SITE

Design & Build a Multi-Section Site

Every mission in Sector 1 handed you one tool in isolation: structure, forms, the box model, flexbox, grid, responsive layout, motion, design judgment. A capstone doesn't teach a new tool — it's the moment you point every one of them at a single real target and ship it. By the end of this mission you won't have a page that only works on your own laptop. You'll have a personal site, built by you, living at a public URL any device on the planet can load.

Briefing

Nothing in this mission is new. That's the point. You already know how to structure a page with semantic HTML, take input through a real form, control spacing with the box model, lay things out with flexbox and grid, make a layout reflow across screen sizes, add a transition that feels intentional rather than gimmicky, and choose type and color that a human being can actually read. A capstone is where those separate skills stop being separate — they become one project, built by one engineer, making dozens of small decisions that all have to agree with each other.

Your target for this mission is a personal site: a small, real home on the internet that says who you are, what you're learning, and how to reach you. It doesn't need to be fancy. It needs to be yours — genuinely written and styled by you, not copied — and it needs to actually work, on a phone screen as well as a laptop.

And then it needs to ship. A project sitting in a folder on your computer, that only you have ever seen render, isn't finished — it's a draft. This is Thread 2 of the Architect's Layer, and it starts right here at Ladder Level L1: "done" means deployed to a public URL, and it works on mobile. Every capstone from here forward raises that bar further — secrets kept out of code, real data, evals, monitoring — but the habit begins now, with the smallest possible version: press a few buttons on GitHub, and your project becomes something you can text a link to.

One flow, top to bottom: Hero → About → Projects → Contact → Footer. Every box on this map is one semantic section in your finished page.

Field Manual

Four short stops before you touch the Command Console: plan what goes where, know which earlier mission covers which piece, ship it with a real walkthrough, and give it one honest design pass before calling it finished.

Planning Your Sections

Do not open the Command Console yet. A real build starts with five minutes of planning — on paper, in a notes app, wherever — because every hour you spend deciding what goes where saves you three hours of rearranging HTML later. Answer these before writing a single tag:

  • Hero: what's the one sentence that tells a stranger who you are and what this site is? (Not a paragraph. One sentence.)
  • About / Skills: which 3–5 things about you actually matter here — languages you're learning, things you've built, things you're into?
  • Projects / Interests: pick 2–4 items you can each describe in one line. This is the section flexbox or grid will lay out as a row or a card grid.
  • Contact: what do you actually want a visitor to do — send a message? See a real email address? Keep it to one clear action.

Sketch the sections in order on paper if it helps — it's the same shape as the diagram above. This is the real planning habit every larger project in this academy will keep asking for.

Bringing It Together

Here's exactly which earlier mission is responsible for which piece of your finished site. If a task in the Mission Challenge below feels unfamiliar, this is the mission to revisit.

  • Structure (1.1): semantic <header>, <main>, <section>, and <footer> — not a page built entirely out of <div>.
  • Forms (1.2): a contact section built from a real <form>, with every input properly <label>-ed and given a name.
  • Box model (1.3): consistent padding and margin, and box-sizing: border-box set globally so widths behave the way you expect.
  • Flexbox (1.4) or Grid (1.5): whichever fits your Projects/Interests section — a single row of cards is flexbox's job, a gallery-style grid is Grid's.
  • Responsive design (1.6): at least one @media query that changes the layout at a narrower width, not just text that shrinks.
  • Animation (1.7): one transition or @keyframes animation, used with restraint — motion that supports the page, not motion for its own sake.
  • Design & accessibility (1.8): a real type scale (headings and body text at deliberately different sizes), a small controlled color palette, and text that passes AA contrast against its background.

Quick Launch: Going Live with GitHub Pages

This is a preview of Mission 4.5, which goes much deeper on deployment — pipelines, environment variables, custom domains, the works. You haven't been taught any of that yet, and you don't need it. What follows gets you a real public URL in about five minutes, using nothing but a free GitHub account and a web browser.

  1. Create a free GitHub account. If you don't already have one, go to github.com/join and sign up — it's free for personal use.
  2. Create a new repository. Click the + in the top corner → New repository. Give it any name (like my-personal-site), leave it Public, and click Create repository.
  3. Upload your files. On the new repository's page, click uploading an existing file and drag in your HTML file — make sure it's named exactly index.html, since that's the filename GitHub Pages looks for by default. If you split your CSS into a separate file, upload that too. Commit the upload.
    BASH — ALTERNATIVE IF YOU'VE FINISHED SECTOR 3'S GIT MISSION
    git init
git remote add origin https://github.com/your-username/your-repo.git
git add .
git commit -m "My personal site"
git branch -M main
git push -u origin main
  4. Turn on GitHub Pages. In your repository, click the Settings tab, then Pages in the left sidebar. Under "Build and deployment," set Source to Deploy from a branch, set Branch to main and the folder to / (root), then click Save.
  5. Your site is now live. Give it a minute, then refresh that same Pages settings screen — GitHub will show your public URL near the top, usually shaped like https://your-username.github.io/your-repo/. Open it. Send it to someone. Open it on your phone.
WHAT JUST HAPPENED Enabling Pages didn't compile, bundle, or transform anything — there's no build step here. GitHub is simply taking the exact files sitting in your chosen branch and folder and serving them, byte for byte, at a public address. That's why the filename matters so much: without an index.html at the root of that folder, there's nothing for GitHub to serve, and the URL 404s.
▸ DEEP DIVE: Why does the URL look different for different people?

GitHub Pages has a special case worth knowing about. Name your repository anything ordinary, like my-personal-site, and your live URL lands under a subfolder: https://your-username.github.io/my-personal-site/. But name the repository exactly your-username.github.io (matching your own account name), and GitHub treats it as your one personal "user site," serving it straight from the root: https://your-username.github.io/, no subfolder at all. Both are genuinely live, genuinely public URLs — the second is just reserved for one special repo per account.

Design Review Pass

Before you call it done, give the page one last pass with 1.8's eyes instead of your builder eyes. This takes five minutes and catches almost everything a visitor would actually notice:

  • Shrink your browser to about 375px wide (or open DevTools' device toolbar) — does anything overlap, overflow, or force horizontal scrolling?
  • Run your text/background color pairs through a contrast checker — everything meant to be read should clear 4.5:1.
  • Look at your headings next to your body text — is the size difference obvious at a glance, or does everything look the same weight?
  • Check your spacing rhythm — is it consistent section to section, or did one area get more breathing room than the rest by accident rather than by choice?
  • Click or tap every link and form field once, for real — a broken href or an unlabeled input hides in plain sight until you actually try it.

Mission Challenge

Build your real personal site in the Command Console (or a real code editor, if you have one), then ship it. Every task below must be true of your finished, deployed site.

▸ HINT

If your layout looks perfect on your laptop and breaks on your phone, that's exactly what the "test at a narrow width" step in the Design Review Pass is for — do it before you deploy, not after someone else finds it for you. If your live GitHub Pages URL 404s after you enable it, double-check that your file is named exactly index.html, sitting at the root of the branch/folder you selected in Settings → Pages, not buried in a subfolder.

⚠ COMMON MISTAKES

  • Shipping without ever narrowing the browser window — a layout that only exists at desktop width isn't a finished layout.
  • Dropping alt text on images now that "it's just a personal site" — that rule from Mission 1.1 didn't expire.
  • Building a contact form with no name attributes on its inputs — it looks finished, but there's nothing there yet to actually receive the message (that piece comes much later, in the backend sectors).
  • Enabling Pages against the wrong branch or the wrong folder, so the live URL 404s even though the code is sitting right there in the repo.
  • Uploading everything except index.html itself, or naming it something else — GitHub Pages won't guess.
