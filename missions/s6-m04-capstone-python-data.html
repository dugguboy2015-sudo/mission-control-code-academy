Field Manual

Function Decomposition — One Job Per Function

It's tempting to write a data script as one long sequence of steps from top to bottom. The problem shows up the moment something needs to change: a single giant block is hard to test, hard to reuse, and hard to read months later. The fix is decomposition — splitting the work into small functions, each doing exactly one clearly-named thing.

PYTHON
def parse_log(raw_text):
    # ... turns raw text into a list of dicts
    pass

def total_fuel(log_entries):
    return sum(e["fuel_used"] for e in log_entries)

def average_fuel(log_entries):
    return total_fuel(log_entries) / len(log_entries)

def most_fuel_event(log_entries):
    return max(log_entries, key=lambda e: e["fuel_used"])
WHAT JUST HAPPENED Each function does exactly one job and has a name that describes it — average_fuel doesn't parse anything, and parse_log doesn't compute any statistics. Notice average_fuel even reuses total_fuel instead of re-summing — building small functions that call each other is how real programs avoid repeating the same logic twice.

Handling Bad Data Gracefully: try/except

Real logs eventually contain a malformed row — a missing field, a value that isn't actually a number. Sector 4's JavaScript try/catch has a direct Python equivalent: try/except. Wrapping the risky conversion step lets you skip one bad row instead of crashing the entire analysis.

PYTHON
def parse_log(raw_text):
    lines = raw_text.splitlines()
    entries = []
    skipped = 0

    for line in lines[1:]:
        values = line.split(",")
        try:
            entry = {
                "date": values[0],
                "event": values[1],
                "fuel_used": int(values[2]),
            }
            entries.append(entry)
        except (ValueError, IndexError):
            skipped += 1
            print(f"⚠ Skipped malformed row: {line}")

    print(f"Parsed {len(entries)} rows, skipped {skipped}.")
    return entries
WHAT JUST HAPPENED int(values[2]) raises a ValueError if that field isn't really a number (say, an empty string). Trying to read values[2] at all raises an IndexError if the row didn't have enough comma-separated fields to begin with. Catching both by name — rather than a bare except: that swallows every possible error, including genuine bugs — is what makes this defensible: you're only forgiving the two specific failure shapes you actually expect from messy data.

Assembling the Report

With parsing and statistics handled by separate functions, the "main" part of the program becomes short and readable — it just calls the pieces in order and formats the result.

PYTHON
log = parse_log(RAW_LOG)

print("=== MISSION REPORT ===")
print(f"Entries: {len(log)}")
print(f"Total fuel: {total_fuel(log)}")
print(f"Average fuel per event: {average_fuel(log):.1f}")

biggest = most_fuel_event(log)
print(f"Biggest single expense: {biggest['event']} ({biggest['fuel_used']} fuel)")
WHAT JUST HAPPENED {average_fuel(log):.1f} is an f-string formatting trick — :.1f rounds a float to exactly one decimal place, so 21.666666... prints as a clean 21.7 instead of a long, ugly decimal. This is the same pipeline as Mission 6.3, just organized into functions that each do one job — which is exactly why it reads this cleanly.

⚠ COMMON MISTAKES

  • Writing one giant script instead of small functions — impossible to test or reuse one piece without the whole thing.
  • Using a bare except: that catches every possible error, hiding genuine bugs alongside the expected messy-data cases.
  • Testing only against clean, hand-written sample data and never actually trying a broken row to confirm the error handling works at all.
  • Computing an average by hand instead of reusing an existing total_fuel() function — duplicated logic that can quietly drift out of sync.
