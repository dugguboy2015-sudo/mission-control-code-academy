Briefing

Every mission so far handed you one piece in isolation: variables holding a single value, a loop running against a fixed array, a function you called by hand from the console. Real software doesn't work in isolated pieces — it works because all of those pieces are wired together into one continuous loop that keeps running as long as someone is using it. That loop is exactly what turns a page from something a visitor reads into something a visitor plays.

A game or a quiz is the cleanest possible proof that this loop actually works, because there's no hiding a broken piece — if your state and your display ever disagree, the player notices immediately. Get a number wrong and the feedback has to say so, correctly, every single time. Win, and the game has to know it won and say so. Click "play again," and it has to forget everything it knew and start clean. None of that happens by accident. It happens because you tracked real state, wrote real conditions, updated the real DOM, and wired real event listeners — the same four ingredients from Sector 2, now working together instead of alone.

This capstone is intentionally open-ended: build a number-guessing game, a quiz app, a memory/matching game, or something entirely your own idea — the Command Console below hands you a working number-guessing game as a starting skeleton, but you are not required to keep it. Pick whichever shape excites you more; the underlying skills are identical either way.

And as with every capstone in this academy, "done" doesn't mean "runs on my laptop." This is Ladder Level L1 again, from Mission 1.9: deployed to a public URL, and it works on mobile. A game nobody else can play isn't a finished game — it's a demo only you have ever seen.

The same Input → Process → Output loop from Mission 0.1 — except now it closes itself. The player's next move depends on what the display just showed them, which depended on the state your code just changed. That closed loop, running over and over, is what "interactive" actually means.

Planning Your Game/Quiz

Do not start typing yet. The single most common reason a game "feels buggy" is that nobody decided up front exactly what the program needs to remember. Answer these on paper first:

  • What state do you need? List every value your program has to remember between one player action and the next — a target number, a score, which question you're on, how many guesses are left, whether the game is over. If you can't list it, you can't track it.
  • What's the win/lose or completion condition? Exactly what has to be true for the game to end — a correct guess, running out of attempts, reaching the last question? Write the condition as a real comparison, like guessesLeft === 0, not a vague feeling.
  • What changes on screen, and when? For each piece of state, name the DOM element that has to update when it changes. State that nothing on screen ever reflects isn't state a player can see — it's just a variable you're keeping to yourself.
  • What resets on "play again"? List every value from your first answer again — all of it has to go back to its starting point, not just the parts that are visible.

Quick Launch: Going Live with GitHub Pages

You've done this before — this is the identical walkthrough from Mission 1.9. If it stuck, skim it and move on. If you haven't reached that mission yet, here it is again in full: Mission 4.5 covers deployment properly later, but this gets you a real public URL in about five minutes with nothing but a free GitHub account and a browser.

  1. Create a free GitHub account. If you don't already have one, go to github.com/join and sign up — it's free for personal use.
  2. Create a new repository. Click the + in the top corner → New repository. Give it any name (like my-guessing-game), leave it Public, and click Create repository.
  3. Upload your files. On the new repository's page, click uploading an existing file and drag in your HTML file — make sure it's named exactly index.html, since that's the filename GitHub Pages looks for by default. Commit the upload.
    BASH — ALTERNATIVE IF YOU'VE FINISHED SECTOR 3'S GIT MISSION
    git init
git remote add origin https://github.com/your-username/your-repo.git
git add .
git commit -m "My game"
git branch -M main
git push -u origin main
  4. Turn on GitHub Pages. In your repository, click the Settings tab, then Pages in the left sidebar. Under "Build and deployment," set Source to Deploy from a branch, set Branch to main and the folder to / (root), then click Save.
  5. Your game is now live. Give it a minute, then refresh that same Pages settings screen — GitHub will show your public URL near the top, usually shaped like https://your-username.github.io/your-repo/. Open it. Play it. Then open it on your phone and play it there too — that's the actual mobile check the checklist asks for.
WHAT JUST HAPPENED Same as last time: no build step, no compiling, no bundling. GitHub is serving the exact bytes sitting in your chosen branch and folder at a public address. That's why the filename still matters — no index.html at the root means nothing for GitHub to serve, and the URL 404s.
▸ DEEP DIVE: My game uses two files (HTML + a separate .js file) — does that still work?

Yes. Upload both files into the same repository, and make sure your HTML's <script src="script.js"></script> points at whatever you actually named the second file, with matching capitalization — GitHub Pages serves static files exactly as uploaded, and a mismatched filename or case is the single most common reason a deployed game "loads" but does nothing.

Leveling It Up

Once your core loop genuinely works — state changes, display updates, win/lose fires correctly, play-again resets cleanly — here are two real extensions worth the extra time, and both are exactly what the bonus objective below is asking for:

  • A persistent high score with localStorage. localStorage.setItem("highScore", attempts) writes a value that survives a page reload; localStorage.getItem("highScore") reads it back. You'll cover this properly in Mission 4.4 — this is a legitimate early preview.
  • A difficulty setting. A simple dropdown or set of buttons that changes a number in your state — say, the guessing range, or how many questions get asked — before the game starts. It's a small addition that makes the whole thing feel like a real, configurable app rather than a fixed demo.

Mission Challenge

Build your real game or quiz in the Command Console above (or a real code editor, if you have one), then ship it. Every task below must be true of your finished, deployed app — not just something that ran once in the sandbox.

▸ HINT

If your game "mostly" works but occasionally shows a stale score, a leftover message, or a double-counted click, the bug is almost never in your win/lose logic — it's almost always that some piece of state didn't get reset, or some event listener got attached a second time on top of the first. Before chasing the symptom, go back to your Planning list and check, one by one, whether every value on it actually gets reset on "play again."

BONUS OBJECTIVE

Add persistent high-score tracking with localStorage (best score, or fewest attempts, survives a page reload), or add a difficulty setting the player picks before the game starts. Either one turns this from "a game that works" into "a game that feels finished."

⚠ COMMON MISTAKES

  • State and display quietly falling out of sync — your variable says the score is 3, but the screen still shows 2, because something updated one and forgot the other.
  • A "play again" that clears the screen but forgets to reset a variable buried further up the file — the game looks fresh, but the old target number or old score is still lurking underneath.
  • Re-attaching a fresh addEventListener every time you re-render a list, instead of once — clicks start firing your handler two, three, four times without you touching anything.
  • Never testing an empty or invalid input — the game works perfectly for every "normal" guess and crashes or misbehaves the instant someone submits nothing.
  • Calling it done after one successful play-through instead of trying to break it — win once, lose once, submit garbage once, click fast twice — before trusting it.
