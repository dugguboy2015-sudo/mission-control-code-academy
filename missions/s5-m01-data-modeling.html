MISSION 5.1: DATA MODELING

Tables, Rows, Columns, Keys & Relationships

Before any database gets built, someone has to decide its shape — what tables exist, what belongs in each one, and how they connect. Get that shape wrong and every feature you build on top of it fights you forever: duplicated data drifts out of sync, queries need to be rewritten, and "simple" changes ripple everywhere. Get it right, and the rest of the app almost falls into place. This mission is entirely about designing before building — no SQL commands yet, just the thinking that has to happen first.

🟡 OFFICER LEVEL ⏱ ~40 MIN 🛠 BROWSER ONLY
1

Briefing

You already know the basics from Mission 5.2's records vault: a table is a labeled manifest sheet, each row is one record, each column is one field every record has, and a primary key gives every row a unique identity. That's enough to describe one table. But real applications almost never have just one table — a crew roster, a mission log, and a supply inventory all exist at once, and the real design work is deciding how those tables connect to each other. That connection is called a relationship, and there are exactly three shapes it ever takes.

Every relationship between two tables is one of these three shapes. One-to-many is by far the most common; one-to-one is rare enough that it's often just merged into a single table instead.

Designing a schema is really answering three questions, in order: what are the "things" in your app (those become tables), what facts does each thing have (those become columns), and how do the things reference each other (those become foreign keys — and sometimes an entire extra table, as you'll see below). Get the tables and relationships right first; the columns are usually the easy part.

2

Field Manual

Choosing a Good Primary Key

It's tempting to use a real-world value as a primary key — an email address, a username, a ship registry number. Resist this. Real-world values change (people get new emails, rename their accounts), and if any other table has stored a foreign key pointing at the old value, that link silently breaks. The standard fix is a surrogate key: a meaningless, auto-incrementing number (or an auto-generated random ID) that exists purely to identify the row and never needs to change.

SQL
-- Fragile: email can change, breaking anything that referenced it
CREATE TABLE crew_bad (email TEXT PRIMARY KEY, name TEXT);

-- Solid: id never changes, email is just a regular (UNIQUE) column
CREATE TABLE crew_good (
  id INTEGER PRIMARY KEY,
  email TEXT UNIQUE NOT NULL,
  name TEXT NOT NULL
);
WHAT JUST HAPPENED crew_good still guarantees no two rows share an email — that's what UNIQUE does — but the email itself is never used as the thing other tables point to. Supabase and Firebase both follow this pattern automatically: every row gets an auto-generated id (or UUID) whether you ask for one or not.

One-to-Many: The Foreign Key Goes on the "Many" Side

This is the relationship you'll use constantly. One crew member can lead many missions, but each mission has exactly one leader. The rule for where the foreign key lives is simple: it always goes on the table representing the "many" side, because each row on that side needs to point back to exactly one row on the "one" side.

SQL
CREATE TABLE crew (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL
);

CREATE TABLE missions (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  leader_id INTEGER REFERENCES crew(id)  -- the FK lives here, on the "many" side
);
WHAT JUST HAPPENED Putting leader_id on crew instead would only allow one mission per crew member — the opposite of what "one crew member, many missions" means. When you're unsure which side gets the FK, ask: "can this side have more than one of the other thing?" Whichever side answers yes gets the foreign key.

Many-to-Many: You Need a Third Table

Sometimes both sides can have many of the other: many crew members can work on many missions, and each mission can have many crew members. Neither table can hold a single foreign key for this — a column can't cleanly hold "several other IDs." The fix is a junction table (also called a join table): a third table whose entire job is to hold one row per pairing.

SQL
CREATE TABLE crew_missions (
  crew_id INTEGER REFERENCES crew(id),
  mission_id INTEGER REFERENCES missions(id),
  PRIMARY KEY (crew_id, mission_id)
);

-- Which crew worked on mission 3?
SELECT crew.name
FROM crew_missions
JOIN crew ON crew_missions.crew_id = crew.id
WHERE crew_missions.mission_id = 3;
WHAT JUST HAPPENED crew_missions holds two foreign keys and nothing else — one row means "this crew member worked on this mission." The PRIMARY KEY (crew_id, mission_id) is a composite key — the two columns together must be unique, which stops the same pairing from being inserted twice, even though neither column is unique on its own.

Normalization: Every Fact Lives in Exactly One Place

Normalization is the practice of structuring tables so no fact is ever duplicated. It sounds academic, but the reasoning is entirely practical.

idtitleleader_nameleader_rank
1Survey Kepler StationNovaCaptain
2Repair Outer HullNovaCaptain
Bad: "Nova" and "Captain" are copied into every mission row she leads. Promote her, and you must remember to update every single row — miss one, and the data quietly disagrees with itself.

The fix is exactly what you already know: store leader_id instead, and look up the name and rank from crew whenever you need them. Nova's rank now lives in exactly one row, in one table — update it once, and every mission that references her is automatically correct.

Constraints: Guardrails Built Into the Table Itself

A well-designed schema doesn't just describe the shape of your data — it actively refuses bad data at the door, before your application code even runs. These four constraints do most of that work:

NOT NULLThis column can never be left empty
UNIQUENo two rows may share this value
DEFAULTAuto-fill a value when none is given
CHECKReject rows that fail a custom condition
SQL
CREATE TABLE missions (
  id INTEGER PRIMARY KEY,
  title TEXT NOT NULL,
  status TEXT DEFAULT 'planned',
  crew_slots INTEGER CHECK (crew_slots > 0)
);
WHAT JUST HAPPENED Any INSERT that omits title is rejected outright — the database itself enforces it, so no application bug can ever slip a titleless mission in. status quietly becomes 'planned' if you don't specify one, and crew_slots can never be zero or negative. Validating this deep, at the database level, is a safety net your front-end validation can't replace.

⚠ COMMON MISTAKES

  • Using a real-world value (email, username) as a primary key instead of a surrogate id — it breaks every reference the moment that value changes.
  • Copying the same fact into multiple tables "to save a JOIN" — it always drifts out of sync eventually.
  • Trying to cram a many-to-many relationship into a single foreign key column instead of building a junction table.
  • Putting the foreign key on the "one" side of a one-to-many relationship instead of the "many" side.
  • Skipping constraints like NOT NULL and UNIQUE and hoping the application code always remembers to validate.
