MISSION 2.9: DEBUGGING & DEVTOOLS

Reading Errors Like a Professional

Every programmer, at every skill level, spends a huge amount of time looking at code that doesn't work yet. The difference between someone who panics and someone who fixes it in ten seconds isn't talent — it's knowing how to read what the computer is actually telling you. This mission teaches you to read a stack trace fluently, use the browser's built-in tools on purpose instead of by accident, and freeze a running program mid-flight to see exactly what it's thinking.

🟡 OFFICER LEVEL ⏱ ~40 MIN 🛠 BROWSER + DEVTOOLS
1

Briefing

An error message is not the ship yelling at you. It's not an alarm designed to make you feel bad, and it's not a sign that you've broken something unfixable. It's a diagnostic readout — a system on your ship reporting, with surprising precision, exactly which subsystem failed and why. Every error a JavaScript engine throws carries the same three pieces of information every single time: a type (what category of problem this is), a message (the specific detail — what value, what operation), and a stack trace (the exact chain of function calls that led to the moment it broke). Once you know how to read those three things together, "the code is broken" stops being scary and starts being a puzzle with a printed hint sheet stapled to it.

You already met DevTools' Network tab back in Mission 0.2 — you watched the actual requests a page fires. This mission goes one level deeper, into the Console and Sources tabs, where you'll watch JavaScript itself run, break, and get fixed. And this time the practice below is a little different from the usual sandbox: instead of a free-form editor, you'll run three genuinely broken snippets and see the real error your browser's JavaScript engine actually throws for each one — not a scripted, pretend version of it.

A stack trace reads top to bottom as "where it happened" → "who called it." The top frame is almost always where you should look first.
2

Field Manual

Anatomy of a Stack Trace

Every uncaught error starts with one line combining its type and message, then a list of indented lines starting with at — that's the call stack. Each at line is one function that was "on the stack" (in the middle of running) at the moment things broke.

CONSOLE OUTPUT
Uncaught TypeError: Cannot read properties of undefined (reading 'toFixed')
    at formatSpeed (dashboard.js:22:34)
    at renderPanel (dashboard.js:41:18)
    at dashboard.js:58:3
WHAT JUST HAPPENED The top frame (formatSpeed) is where the error was actually thrown — start reading there, not at the bottom. Each frame below it is the function that called the one above — so renderPanel called formatSpeed, and something at line 58 called renderPanel. The bottom of the trace is the original trigger, usually furthest from the actual bug.

Common Error Types

Almost every runtime bug you'll hit falls into one of three buckets. Learn to recognize them by name and you'll already know roughly where to look before you've read a single word of the message.

JS
// TypeError — used a value in a way its type doesn't support
const readings = undefined;
console.log(readings.length);
// -> TypeError: Cannot read properties of undefined (reading 'length')

// ReferenceError — referenced a name that doesn't exist anywhere in scope
console.log(totalFuel);
// -> ReferenceError: totalFuel is not defined

// SyntaxError — the code isn't even valid JavaScript; nothing runs at all
function launch( {
  console.log('go');
}
// -> SyntaxError: missing ) after argument list
WHAT JUST HAPPENED TypeError almost always means you called a method on, or read a property from, something that turned out to be undefined or null — usually because an earlier step didn't produce what you expected. ReferenceError means the name simply doesn't exist anywhere the engine can see — nearly always a typo or a missing declaration. SyntaxError is special: it's caught by the parser before any code runs, so its reported line is where the parser gave up, not necessarily where the real mistake is — often you have to look a line or two above it for the missing bracket or quote.

console Methods as Real Debugging Tools

The console object isn't just for stray leftover prints — each method is a deliberate signal, and DevTools renders them differently on purpose.

JS
console.log('fuel remaining:', fuelLevel);
console.warn('fuel below 20% — refuel soon');
console.error('engine ignition failed', { code: 12 });
console.table(crewRoster);
WHAT JUST HAPPENED console.log is your general-purpose checkpoint. console.warn prints with a yellow triangle — use it for "this isn't broken yet, but it's suspicious." console.error prints in red with an X icon and, in most browsers, automatically attaches a full stack trace even though nothing was thrown — perfect for flagging a real problem you caught yourself, deliberately, in an if check. console.table turns an array of objects into an actual grid instead of a wall of nested brackets.
▸ DEEP DIVE: console.table() for inspecting arrays of objects

Compare scanning [{name:"Rho",role:"Pilot"},{name:"Kade",role:"Engineer"}] as raw text versus calling console.table(crew) — DevTools renders one column per property (name, role) and one row per object, sortable by clicking a column header. For any array of similarly-shaped objects — API results, a roster, a leaderboard — it's the fastest way to eyeball whether the data actually looks right. You can even pass a second argument, an array of property names, to show only specific columns: console.table(crew, ["name"]).

Breakpoints & Stepping Through Code (Sources Panel)

The Console tells you what already happened. The Sources panel lets you freeze code mid-run and watch it happen, line by line, on a real page.

JS
function calculateTrajectory(velocity, angle) {
  const radians = angle * (Math.PI / 180); // <- click this line's number to set a breakpoint
  const range = (velocity ** 2 * Math.sin(2 * radians)) / 9.8;
  return range;
}
WHAT JUST HAPPENED (describing the real workflow) In DevTools' Sources tab: find the file in the tree on the left, open it, and click a line number in the gutter — a blue flag appears, marking a real breakpoint. Trigger that code path (reload, click a button, whatever calls it) and the entire page freezes right before that line executes. The Scope panel on the right now shows every variable's live value at that exact instant — no guessing. From there: Step Over runs the current line and stops at the next one without diving into functions it calls; Step Into follows execution down into a called function; Step Out finishes the current function and pops back to whoever called it; Resume (the blue play icon) lets the page run normally again until the next breakpoint.

A Method for Reading Errors, Not Just Reacting to Them

Panicking at an error and guessing a fix wastes more time than it saves. Use the same four steps every time: read the full message before anything else, find the top stack frame (where it actually happened), form one specific hypothesis about what value must be wrong to produce exactly that message, and verify the hypothesis before touching any code.

JS
// Hypothesis: manifest.item is undefined because of a typo (should be 'items')
console.log(manifest.item);   // confirm: logs `undefined` — hypothesis confirmed
manifest.items.join(', ');    // now apply the actual fix
THE KEY IDEA Verify before you fix. It feels slower for a two-second bug, but it's the habit that saves you when the bug is subtle — and it's exactly what stops you from "fixing" the wrong thing, seeing the error change shape, and being no closer to done.

⚠ COMMON MISTAKES

  • Panicking at the very first line of a long stack trace instead of reading the actual message underneath it.
  • Assuming "no error was thrown" means "the code is correct" — logic bugs run silently and quietly return the wrong answer.
  • Ignoring yellow console.warn messages because "it's not red" — warnings are often tomorrow's crash.
  • Leaving stray console.log statements scattered in shipped code instead of removing them or replacing them with a deliberate console.warn/console.error.
  • Guessing at a fix and re-running instead of verifying the hypothesis first — you can "fix" the wrong thing and just get a different error.
