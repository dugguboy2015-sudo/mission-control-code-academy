1

Briefing

Every commit you've made so far has lived in one place: the hidden .git folder on your own machine. That's fine for solo experiments, but it's fragile — one dead hard drive and the whole mission log is gone. It's also useless for teamwork, since nobody else can see it.

The fix is a remote: another copy of the same repository, usually hosted on GitHub, that your local repo can talk to. Think of your machine as your own workshop — you can weld, test, and rewire in private. GitHub is Mission Control's shared master copy, the one everyone else reads from and trusts. A remote connection is the radio link between the two: you push your commits up to it, and pull or fetch commits down from it.

But engineers rarely push straight into the master copy. Instead, they finish work on a branch, push that branch to GitHub, and open a Pull Request (PR) — a formal request that says "here's what I changed, please review it before it becomes official." A PR shows a diff (exactly which lines were added or removed), lets teammates comment, and only becomes part of main once someone clicks Merge. It's the same merge you already know from the command line — GitHub just gives it a review step and a paper trail.

Your local repo and the GitHub remote called "origin" — push sends commits up, fetch checks what's new without touching your files, pull fetches and merges in one step.
2

Field Manual

Remotes: origin & git remote -v

A remote is just a URL Git remembers a nickname for. When you clone or connect a repo to GitHub, that remote is almost always named origin by convention — it's not a special keyword, just the default name everyone uses so scripts and habits transfer between projects.

BASH
# List remotes this repo knows about, with their URLs
git remote -v

# Connect a fresh local repo to a GitHub repo for the first time
git remote add origin https://github.com/yourname/your-repo.git
WHAT JUST HAPPENED git remote -v prints every remote and shows two URLs per name — one for fetching, one for pushing (they're almost always the same). git remote add registers a brand-new connection; you only run it once per repo, typically right after creating the GitHub repo.

push, pull & fetch

These three commands move commits between your machine and the remote. They sound similar but do genuinely different things, and mixing them up is one of the most common early-career Git mistakes.

BASH
# Upload your local commits on this branch to GitHub
git push origin feature/shields

# Download what's new on the remote, WITHOUT touching your files
git fetch origin

# Download what's new AND merge it into your current branch
git pull origin main
WHAT JUST HAPPENED push sends your commits up. fetch is the cautious move — it updates Git's memory of what's on the remote so you can look before you leap (git log origin/main, git diff origin/main) but leaves your working files untouched. pull is fetch immediately followed by merge — it downloads and updates your files in one motion.
▸ DEEP DIVE: Why would I ever fetch instead of pull?

git pull is really shorthand for git fetch + git merge origin/<branch>. Most of the time that's exactly what you want. But if a teammate might have pushed something risky, or you have uncommitted work you're not ready to merge against, fetch lets you inspect the incoming changes first — git log main..origin/main shows what you're about to get — before deciding to merge. Professional teams on high-stakes codebases often fetch-then-review-then-merge deliberately instead of blindly pulling.

.gitignore — Keeping Junk Out of the Record

Not everything in your project folder belongs in version control. Dependency folders can be regenerated, build output is disposable, and secret keys should never exist in a shared history at all — once something is committed, it's in the log forever, even if you delete it in a later commit. A .gitignore file tells Git which files and folders to never track in the first place.

TEXT
# .gitignore — one pattern per line
.env
node_modules/
dist/
*.log
.DS_Store
WHAT JUST HAPPENED .env keeps API keys and passwords out of the log entirely. node_modules/ and dist/ are generated — anyone can rebuild them, so tracking them just bloats the repo. *.log and .DS_Store are noise files your OS or tools create automatically. Create this file before your first commit whenever possible — .gitignore can't un-track something that's already been committed.

The Pull Request Workflow

A Pull Request is GitHub's review layer on top of an ordinary merge. The sequence: finish work on a branch, push that branch to GitHub, open a PR comparing it against main, let someone (or yourself, on a solo project) review the diff, then click Merge. GitHub performs the actual merge on the server — the exact same operation as git merge, just triggered by a button instead of a terminal command.

BASH
# Do your work on a branch, never directly on main
git checkout -b feature/shields

# Push the branch so GitHub knows it exists
git push -u origin feature/shields

# Now open a Pull Request on github.com comparing this branch to main
WHAT JUST HAPPENED Pushing a branch doesn't merge anything — it just makes the branch visible on GitHub. Opening the PR is a separate, deliberate step on the GitHub website where you compare feature/shields against main, see every line changed, and only after that review does the merge actually happen.

▸ HINT

If GitHub's "Merge pull request" button is greyed out or shows a warning, someone (maybe future-you on another machine) pushed a conflicting change to main since you branched. Fetch and merge main into your branch locally first, resolve any conflicts, push again, and the button will re-enable.

Open a second PR, but this time leave yourself a review comment directly on one of the changed lines before merging — GitHub lets you comment on individual diff lines, not just the PR as a whole. That's the exact mechanism real teams use to ask "why did you change this?" before approving.

⚠ COMMON MISTAKES

  • Committing a .env file or API key because .gitignore wasn't set up before the first commit — once it's in history, deleting it later isn't enough; it must be scrubbed or the key rotated.
  • Opening a PR and then remembering you forgot to push your latest commits — GitHub can only compare what's actually on the remote.
  • Force-pushing (git push --force) over a branch someone else is also working on, silently erasing their commits.
  • Clicking "Merge pull request" without actually reading the diff — the whole point of a PR is the review, not the click.
  • Confusing fetch and pull, then being surprised local files didn't change after a fetch.
