MISSION 9.2: DEBUGGING METHODOLOGY

Reading Errors Like an Engineer

Mission 2.9 showed you DevTools. This mission is about the METHOD, not the tool — a repeatable process that works whether you're debugging a browser tab, a Python script, or a deployed server: reproduce it reliably, read the error fully, isolate where it actually happens, form a real hypothesis, and fix the root cause — not the symptom.

🔴 COMMANDER LEVEL ⏱ ~40 MIN 🛠 BROWSER ONLY
1

Briefing

The single biggest difference between an engineer who debugs efficiently and one who doesn't isn't tool knowledge — it's method. Randomly changing code and re-running it, hoping something works ("shotgun debugging"), can occasionally get lucky, but it doesn't build understanding, and it often introduces new bugs while chasing the old one. A real method finds the actual cause, reliably, every time.

2

Field Manual

Step 1: Reproduce It Reliably

You can't fix what you can't reliably trigger. Before touching any code, find the EXACT steps or input that cause the bug, every single time. "It happens sometimes" is not yet debuggable — narrowing "sometimes" down to a specific, repeatable condition is real progress, even before you've written a single fix.

Step 2: Read the Error Message, Completely

A stack trace lists function calls from the error's exact location (top) down to where the program started (bottom). The very first line — the actual error type and message — is usually the most important, and it's the line people skim past fastest.

A HABIT WORTH BUILDING Before searching anything online or asking an AI (Mission 9.3), read the full error message and the specific line number it points to, out loud if it helps. A large share of "mystery" bugs are explained in plain language in the very first line of the error — the mystery is usually just not having read it carefully yet.

Step 3: Isolate — Binary Search the Problem

If a bug could be anywhere in 200 lines of code, don't read all 200 hoping to spot it. Comment out or bypass half the code; if the bug disappears, it's in the half you removed — if it's still there, it's in the half you kept. Repeat on the remaining half. This is the exact same idea as binary search from Mission 2.10's algorithmic thinking, applied to finding a bug instead of finding a value in a sorted list.

200 lines → bug still happens? → check lines 1-100 → still happens? → check lines 1-50 → ... → found it in ~8 steps instead of reading 200 lines top to bottom.

Step 4: Form a Hypothesis, Then Test It

Before changing any code, state — even just to yourself — a specific, falsifiable theory: "I think total is undefined because this function is called before the data loads." Then check that ONE specific thing (a console.log, a breakpoint) before changing anything. If you're wrong, you've still learned something real and can form a better hypothesis — that's still progress, unlike a random edit that happens to "fix" something you don't understand.

Step 5: Fix the Root Cause, Not the Symptom

Wrapping a crashing line in a try/catch that silently swallows the error makes the crash go away — without fixing anything. The underlying wrong assumption is still there, waiting to cause a different, harder-to-trace symptom later. Understand WHY the bug happened before deciding how to fix it.

⚠ COMMON MISTAKES

  • Randomly changing code hoping something works, without a specific theory about what's actually wrong.
  • Skimming the error message instead of reading the exact line and message it reports.
  • Wrapping a crash in try/catch and calling it fixed, without understanding why it crashed.
  • Reading through an entire large file top to bottom instead of isolating which half the bug is actually in.
