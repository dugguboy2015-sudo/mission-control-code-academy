MISSION 4.4: STATE & STORAGE

localStorage — Remembering Between Visits

Every app you've built so far has had amnesia. Refresh the page and every variable, every click count, every typed note is gone — wiped clean, like it never happened. That's because it was all living in RAM, and RAM forgets. This mission gives your code a memory: a small, permanent storage locker built into the browser itself, so the things your app knows about a cadet can actually survive a reload, a tab close, even a full computer restart.

🟡 OFFICER LEVEL ⏱ ~35 MIN 🛠 BROWSER ONLY
1

Briefing

Back in Mission 0.1, you learned the difference between RAM and storage: RAM is fast, temporary scratch space that empties the instant power is lost, while storage is slower but permanent — it survives a shutdown. Every JavaScript variable you've written since then — let clicks = 0;, const ship = {...} — lives in RAM. The moment you reload the page, the whole script re-runs from scratch, and every one of those variables gets recreated at zero. That's not a bug. That's just what RAM does.

The collection of "current values your app is tracking right now" is called app state — how many clicks happened, what the cadet typed, which tab is active, whether dark mode is on. Normally, all of that state lives only in RAM and dies on reload. Sometimes that's fine. But sometimes you want state to persist — to still be there the next time the cadet opens the page.

That's what localStorage is for. It's a small key-value storage locker the browser gives to every website, scoped to that one site's origin (a page on your domain can't see another site's locker, and vice versa). Anything you save there sticks around across reloads, across tab closes, even across full browser and computer restarts — until the cadet clears their browsing data or your code deliberately removes it.

You've actually been benefiting from exactly this the entire time you've used this Academy without realizing it. The academy.js file that runs this very page uses localStorage to remember your mission progress, your checklist ticks, your light/dark theme choice, and whether the sidebar was open — which is exactly why none of that resets every time you load a new mission page. It's not magic. It's the same tool this mission is about to teach you.

A variable in memory dies on reload. A localStorage entry is written to the browser's actual storage and comes back exactly as you left it.
2

Field Manual

App State vs. Persistent State

Not everything your app tracks needs to survive a reload. Whether a dropdown menu is currently open, the exact pixel position of a drag-in-progress, the contents of an error message mid-typo — that's transient state, and RAM is exactly the right place for it. It's supposed to reset. But a cadet's saved notes, their high score, their theme preference — that's state you generally want to persist, because losing it on every reload would be annoying or destructive.

The decision isn't automatic. You have to explicitly choose, for each piece of state, whether it belongs only in a variable or also gets written to storage. localStorage never happens by accident — you always call it on purpose.

THE KEY IDEA Ask yourself: "if the cadet reloads this page right now, should this value still be here?" If yes, it needs to live in localStorage (or somewhere else permanent), not just a variable.

setItem, getItem, removeItem

localStorage is a simple key-value store with three core methods. Keys and values are always strings.

JAVASCRIPT
// Save a value
localStorage.setItem("callsign", "Nova");

// Read it back (returns null if the key was never set)
const savedName = localStorage.getItem("callsign");
console.log(savedName); // "Nova"

// Remove it
localStorage.removeItem("callsign");
console.log(localStorage.getItem("callsign")); // null
WHAT JUST HAPPENED setItem(key, value) writes to the browser's actual storage, not a variable — it's still there after a reload. getItem(key) reads it back, and returns null (not undefined, not an empty string) if that key has never been set — always plan for that case, especially the very first time a cadet visits with nothing saved yet.

Storing Objects: JSON.stringify & JSON.parse

Here's the catch that trips almost everyone up the first time: localStorage can only store strings. If you hand it a number, it gets silently converted to text. If you hand it an object or an array, JavaScript converts it too — but not into anything useful.

JAVASCRIPT
const crewMember = { name: "Kip", rank: "Officer" };

// WRONG — localStorage forces this to a string, and objects
// convert to the useless text "[object Object]"
localStorage.setItem("crew", crewMember);
console.log(localStorage.getItem("crew")); // "[object Object]"

// RIGHT — turn it into a JSON string first
localStorage.setItem("crew", JSON.stringify(crewMember));

// ...and turn it back into a real object when reading it
const raw = localStorage.getItem("crew");
const restored = JSON.parse(raw);
console.log(restored.name); // "Kip"
WHAT JUST HAPPENED JSON.stringify() converts a real object or array into a text representation that captures its full shape — safe to hand to setItem. JSON.parse() does the reverse, turning that text back into a real, usable object. Stringify going in, parse coming out — every single time you round-trip an object or array through localStorage.
▸ DEEP DIVE: localStorage's size limit

Every origin gets roughly 5–10MB of localStorage, depending on the browser — plenty for settings, small notes, a handful of saved records, but nowhere near enough for large datasets, images, or anything approaching a real database. It's also fully synchronous, meaning large reads/writes can briefly freeze your page. localStorage is meant for small, simple state — a few saved values, not your app's entire dataset. When you actually need a real database, that's what Sector 5 (Supabase/Firebase) is for.

sessionStorage & When NOT to Persist

localStorage has a sibling with the exact same API — setItem, getItem, removeItem — but different lifespan rules: sessionStorage. Anything saved there is cleared automatically the moment the browser tab closes. It's useful for state that should survive a reload of the same tab (so the cadet doesn't lose progress mid-form) but shouldn't outlive the visit — like a multi-step form's in-progress answers.

JAVASCRIPT
// Same API as localStorage, but cleared when the tab closes
sessionStorage.setItem("draftMessage", "Hey Commander, quick qu");
console.log(sessionStorage.getItem("draftMessage"));

And one rule that matters more than any syntax here: never store sensitive data in localStorage or sessionStorage. Both are plain, unencrypted text sitting on the cadet's computer — anyone with access to that browser (or a malicious script that sneaks onto your page) can open DevTools and read every key instantly. No passwords, no API keys, no payment details, no private personal data. Real authentication systems use special server-managed mechanisms for that — you'll meet them properly in Sector 5.

WHAT JUST HAPPENED Same methods, different lifetime: localStorage persists indefinitely (until cleared), sessionStorage dies with the tab. Neither one is a vault — treat both as readable by anyone at the keyboard.

Using the sandbox above (or a real HTML file with a <script> tag), build a small persistent log-entry tool.

▸ HINT

If your saved object comes back as the text "[object Object]" instead of real data, you skipped JSON.stringify() on the way in. If reading it back throws an error like "Unexpected token", you probably skipped JSON.parse() on the way out — or you're trying to parse a value that was null because nothing was saved yet. Always check for null before parsing.

BONUS OBJECTIVE

Extend your tool to store an array of log entries instead of a single value — each time the cadet adds a note, read the existing array back with JSON.parse, push the new entry onto it, then save the whole array again with JSON.stringify. Confirm the full list survives a page reload, not just the most recent entry.

⚠ COMMON MISTAKES

  • Passing an object straight into setItem() without JSON.stringify() and getting the useless string "[object Object]" back.
  • Forgetting JSON.parse() when reading a stored object back out, then being confused why it's "just a string" with no properties.
  • Not handling the case where getItem() returns null — the very first visit, before anything has ever been saved.
  • Storing sensitive data (passwords, tokens, personal info) in localStorage, forgetting it's plain, unencrypted text anyone at that computer can read.
  • Confusing localStorage's indefinite persistence with sessionStorage's tab-lifetime — using the wrong one for data that needed to (or shouldn't) survive a closed tab.
