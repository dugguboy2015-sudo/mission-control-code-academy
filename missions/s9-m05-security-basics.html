MISSION 9.5: SECURITY & PRIVACY BASICS

Protecting Users and Data

Every feature that accepts input from someone else — a comment box, a URL parameter, a file upload — is a place where a careless assumption becomes a real vulnerability. The single most important habit in this mission: never trust input you didn't generate yourself. That's the root cause behind nearly every entry on the classic list of web vulnerabilities.

🔴 COMMANDER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Picture a comment box on a page. A normal visitor types "great post!" — but nothing stops a different visitor from typing actual HTML, like <img src=x onerror="doSomethingMalicious()">. If your code inserts that text directly into the page as HTML, the browser doesn't know it "wasn't supposed to be code" — it just renders it, exactly like any other tag. This is XSS (Cross-Site Scripting), and it's real, common, and entirely preventable with one specific habit.

2

Field Manual

innerHTML vs textContent — the Actual Difference That Matters

element.innerHTML = userInput parses the string AS HTML — any tags inside it become real, live elements. element.textContent = userInput inserts it as plain, inert text — tags stay as literal visible characters, never becoming real elements.

JAVASCRIPT
const userComment = '<img src=x onerror="alert(1)">';

// VULNERABLE: the browser actually renders (and runs) the injected tag
commentBox.innerHTML = userComment;

// SAFE: the browser shows the literal text, tags and all, as plain characters
commentBox.textContent = userComment;
WHAT JUST HAPPENED The exact same string produces two completely different outcomes depending on one method choice. The rule: whenever you're inserting text that came from a user (or any source you don't fully control) and it's meant to be DISPLAYED, not rendered as markup, textContent is almost always the right call.

Input Validation, Recap

Missions 5.1 and 7.7 already covered this from two angles — database constraints and AI-feature guardrails — and the underlying principle is the same everywhere: validate input at the boundary, before it's used for anything, rather than hoping it's well-formed.

Least Privilege

Mission 5.2's Row Level Security is a real-world example of a bigger idea: grant only the access something actually needs, never more "to be safe" or "just in case." A support tool that only needs to read order status shouldn't also have permission to delete accounts — even if it would never intentionally use that power, a bug or a compromised credential now has a much smaller blast radius.

Privacy: Data Minimization

The most private piece of data is the one you never collected in the first place. Before adding a field to a signup form or a database table, ask whether the feature genuinely needs it. Data you don't store can't be leaked, subpoenaed, or misused later — a real, practical form of security that costs nothing to apply.

⚠ COMMON MISTAKES

  • Using innerHTML to display user-provided text "because it was convenient," without considering what happens if that text contains real HTML.
  • Assuming your own app's users would never try this — XSS payloads are often submitted by automated scanning tools, not just deliberate human attackers.
  • Granting broad access "to be safe" instead of the minimum a feature actually needs.
  • Collecting more personal data than a feature genuinely requires, "in case it's useful later."
