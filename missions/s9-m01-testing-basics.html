MISSION 9.1: TESTING BASICS

Proving Your Code Works

Every mission so far, you've tested your code by looking at it — running it and eyeballing the output. That works for a five-line script. It stops working the moment your project grows past a handful of functions, because you can't realistically re-click through every feature by hand after every single change. A test is a small program that checks another program's behavior automatically — write it once, run it forever, for free.

🔴 COMMANDER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

A unit test checks one small unit of code — usually one function — in isolation. It follows a simple, repeatable shape called Arrange-Act-Assert: arrange the inputs you need, act by calling the function, then assert (check) that the result is what you expected. Run a hundred of these in under a second, every time you change anything, and you know immediately if you broke something that used to work — this is the exact same instinct as Mission 8.6's evals, applied to ordinary deterministic code instead of AI output.

Field Manual

Arrange, Act, Assert

JAVASCRIPT
function calculateTip(bill, percent) {
  return bill * (percent / 100);
}

// ARRANGE
const bill = 50;
const percent = 20;

// ACT
const result = calculateTip(bill, percent);

// ASSERT
if (result !== 10) {
  throw new Error("Expected 10, got " + result);
}
WHAT JUST HAPPENED This IS a real, working test — a program checking another program's behavior, with no human watching. It just isn't organized or reported nicely yet. A tiny test framework (below) fixes that part.

A Minimal Test Framework, From Scratch

JAVASCRIPT
function assert(condition, message) {
  if (!condition) throw new Error(message || "Assertion failed");
}

function test(name, fn) {
  try {
    fn();
    console.log("✓ " + name);
  } catch (err) {
    console.error("✗ " + name + " — " + err.message);
  }
}

test("calculateTip returns correct amount", () => {
  assert(calculateTip(50, 20) === 10, "Expected 10");
});
WHAT JUST HAPPENED test() wraps the risky call in a try/catch (Mission 4.6) so ONE failing test doesn't stop the rest from running, and reports a clean pass/fail line either way. This tiny amount of code is, structurally, exactly what real test frameworks like Jest or Vitest do underneath — just with far more features.

The Happy Path Is Not Enough

A test that only checks the expected, well-behaved input (the "happy path") misses the bugs that actually matter. Good tests also check edge cases: zero, negative numbers, empty strings, missing fields — the exact inputs a careless assumption tends to break on.

WHY THIS MATTERS calculateTip(50, 0) should return 0, not crash or return NaN. A test suite that only ever calls a function with "normal" numbers will confidently report 100% passing while a genuine bug sits untested right next to it.

Debrief / Cheat Sheet

Unit testChecks one small unit of code, in isolation
Arrange-Act-AssertSet up inputs, run the code, check the result
assert(condition)Throws if the condition is false
Happy pathThe expected, well-behaved input — not enough alone
Edge caseZero, negative, empty, missing — where bugs actually hide

⚠ COMMON MISTAKES

  • Only testing the happy path and never an edge case, missing exactly the inputs bugs tend to hide behind.
  • Writing a test so broad it checks multiple unrelated behaviors at once, making a failure hard to diagnose.
  • Letting a test depend on something non-deterministic (today's date, a random number) without controlling for it — Mission 7.1's lesson, applied to test design.
  • Writing code first and never writing a single test for it, then discovering a bug only when a real user hits it.
