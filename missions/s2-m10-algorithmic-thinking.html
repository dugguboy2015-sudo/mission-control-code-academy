Problem-Solving & Simple Algorithms

You've spent this whole sector learning JavaScript's grammar — variables, functions, loops, the DOM. This mission is different: it's about the thinking that happens before any of that grammar gets typed. Every real program starts as a fuzzy goal in someone's head and has to become a precise, ordered sequence of steps before a single line of code is worth writing. You already know this discipline — Mission 0.1's Literal Robot only ever did exactly what it was told, no more, no less. Now you'll apply that same discipline to two of computing's oldest, most useful problems: finding something in a list, and putting a list in order.

Briefing

Back in Mission 0.1, the Literal Robot taught you that a computer never fills in gaps — it does exactly what you tell it, and an algorithm is just a precise, ordered sequence of steps for accomplishing something. That was true with plain-English sandwich instructions, and it's still true now that you're writing real JavaScript. The difference is that real code raises the stakes: a vague step in an English instruction list produces a silly robot; a vague step in a real program produces a bug, a crash, or — worse — code that runs fine and quietly gives the wrong answer.

The habit that separates confident programmers from people who stare at a blinking cursor is decomposition: breaking a big, fuzzy problem into small, ordered sub-steps before writing any code. Sketch the steps in plain language (or pseudocode, like Mission 0.1's fuel-check example) first. Once every step is unambiguous, translating it into JavaScript syntax is almost mechanical — the hard thinking already happened.

This mission puts that habit to work on two classic problems every programmer eventually needs: searching a list for a value, and sorting a list into order. You'll meet two search strategies — linear search (check everything, one at a time) and binary search (repeatedly cut the search space in half) — and you'll see why the second one only works when the data is already sorted. Along the way you'll pick up your first real vocabulary for comparing algorithms: Big-O notation, a way of describing how the amount of work grows as the input grows.

Both searches run on the same sorted array, hunting for the same value (63). Linear search has no shortcut — it walks the boxes in order. Binary search uses the fact that the data is sorted to throw away half the possibilities with every single check.

Field Manual

Decomposition: Pseudocode to Code

Before touching a keyboard, describe the problem in plain steps. Take "find the highest score in a list of exam scores." Decomposed: (1) assume the first score is the highest so far, (2) look at every other score one at a time, (3) whenever you find one bigger than your current "highest," update it, (4) after checking everything, report whatever "highest" ended up holding. Only now is it worth opening the editor.

JAVASCRIPT
function findHighestScore(scores) {
  let highest = scores[0]; // step 1: assume the first is highest

  for (let i = 1; i < scores.length; i++) { // step 2: check the rest
    if (scores[i] > highest) {
      highest = scores[i]; // step 3: update when we find bigger
    }
  }

  return highest; // step 4: report the result
}

console.log(findHighestScore([72, 95, 61, 88, 95, 70])); // 95
WHAT JUST HAPPENED Every line of real code maps back to one of the four decomposed steps — there's nothing in the function that wasn't already decided in plain English first. This is the move: decompose in words (or pseudocode), then transcribe into syntax. Skipping straight to code usually means redoing the thinking mid-way through, tangled up with semicolons.

Linear Search

Linear search is the most obvious way to find something: start at the beginning, check each item, and stop the moment you find a match (or run out of items). It works on any list — sorted or not — because it never assumes anything about the order.

JAVASCRIPT
function linearSearch(arr, target) {
  for (let i = 0; i < arr.length; i++) {
    if (arr[i] === target) {
      return i; // found it — report where
    }
  }
  return -1; // checked everything, no match
}

const crewIds = [104, 88, 231, 15, 76];
console.log(linearSearch(crewIds, 231)); // 2
console.log(linearSearch(crewIds, 999)); // -1
WHAT JUST HAPPENED Returning -1 for "not found" is a long-standing convention (an array can never have a real index of -1, so it's an unambiguous signal). In the worst case — the target is last, or missing entirely — linear search checks every single element. If the list has n items, that's up to n checks.

Binary Search (On Sorted Data)

Binary search is dramatically faster, but it comes with a non-negotiable requirement: the data must already be sorted. It tracks a low and high boundary around the range that could still contain the target, checks the middle (mid) of that range, and — because the data is sorted — instantly knows which entire half to throw away.

JAVASCRIPT
function binarySearch(sortedArr, target) {
  let low = 0;
  let high = sortedArr.length - 1;

  while (low <= high) {
    const mid = Math.floor((low + high) / 2);
    if (sortedArr[mid] === target) {
      return mid; // found it
    } else if (sortedArr[mid] < target) {
      low = mid + 1; // target must be in the right half
    } else {
      high = mid - 1; // target must be in the left half
    }
  }
  return -1; // range shrank to nothing — not present
}

const sorted = [5, 10, 17, 28, 42, 63, 71, 89];
console.log(binarySearch(sorted, 63)); // 5, in just 2 checks
WHAT JUST HAPPENED mid compares once, and that single comparison eliminates an entire half of the remaining range — not one element, half of everything left. That's why it's so much faster: an 8-element array takes at most 4 checks; a 1,024-element array takes at most 11. Trace it below in the Command Console until low > high feels automatic.
▸ DEEP DIVE: What if the data isn't sorted?

Binary search's entire trick depends on one guarantee: everything to the left of mid is smaller, everything to the right is bigger. Break that guarantee and the algorithm doesn't crash — it just silently trusts a lie. Run binarySearch([42, 17, 89, 5, 63, 28, 71, 10], 63) — an unsorted array where 63 sits plainly at index 4 — and trace it by hand: mid = 3 is 5, which is less than 63, so the algorithm sets low = 4, discarding indices 0–3 (correctly, this time). Next, mid = 5 is 28, still less than 63, so low = 6. Next, mid = 6 is 71, which is greater than 63, so high = 5. Now low (6) is greater than high (5) — the loop ends and the function returns -1, "not found," after only 3 checks. But 63 was sitting right there the whole time, at index 4. The algorithm never lied to itself on purpose — it just followed its rules perfectly on data that broke the one assumption those rules depend on. This is exactly why "is this actually sorted?" has to be answered before you reach for binary search, not after something goes wrong.

A Simple Sort: Bubble Sort

Bubble sort repeatedly walks through the list comparing neighbors, swapping any pair that's out of order. After one full pass, the largest remaining value has "bubbled" all the way to the end. Repeat, ignoring the part that's already settled, until a full pass makes zero swaps — at that point, everything is in order. It's not fast (real-world code almost never uses it), but it's the clearest possible window into what "sorting" actually means, step by step.

JAVASCRIPT
function bubbleSort(arr) {
  const a = [...arr]; // copy — don't mutate the original

  for (let i = 0; i < a.length - 1; i++) {
    let swapped = false;

    for (let j = 0; j < a.length - 1 - i; j++) {
      if (a[j] > a[j + 1]) {
        [a[j], a[j + 1]] = [a[j + 1], a[j]]; // swap
        swapped = true;
      }
    }

    if (!swapped) break; // already sorted — stop early
  }

  return a;
}

console.log(bubbleSort([42, 17, 89, 5, 63, 28, 71, 10]));
// [5, 10, 17, 28, 42, 63, 71, 89]
WHAT JUST HAPPENED The inner loop shrinks each pass (a.length - 1 - i) because the last i elements are already correctly placed — no point re-checking them. The swapped flag is a small but real optimization: if a whole pass makes no swaps, the list is already sorted and there's no reason to keep looping. A Gentle Intro to Big-O

Big-O notation is just a way to describe how the amount of work an algorithm does grows as the input gets bigger — without getting bogged down in exact numbers. Linear search is O(n): double the list, and in the worst case you double the checks. Binary search is O(log n): double the list, and you only need one more check, because each check cuts the remaining space in half.

Array size (n)Linear search — worst caseBinary search — worst case
88 checks4 checks
1616 checks5 checks
6464 checks7 checks
1,0241,024 checks11 checks
1,000,0001,000,000 checks20 checks
WHAT JUST HAPPENED Nobody's counting exact CPU cycles here — Big-O is about the shape of the growth curve, not a stopwatch reading. O(n) means "work scales in a straight line with input size." O(log n) means "work barely grows at all." Bubble sort, for what it's worth, is O(n²) — its nested loops mean doubling the input roughly quadruples the work, which is exactly why it's a teaching tool and not something you'd run on a million-row spreadsheet.

⚠ COMMON MISTAKES

  • Running binary search on unsorted data and trusting a "not found" result that's actually wrong.
  • Off-by-one errors in the midpoint math — using low = mid instead of low = mid + 1 can cause an infinite loop.
  • Writing code before decomposing the problem, then getting lost halfway through a tangle of half-finished logic.
  • Treating "sorted" as automatic — forgetting that binary search requires you to sort first, and that sorting itself costs time.
  • Assuming bubble sort (or any O(n²) algorithm) is fine for large, real-world datasets — it's a teaching tool, not production code.
