MISSION 8.7: OBSERVABILITY & TRACING FOR AI

Logging Prompts, Outputs, Cost, Failures

Mission 8.6's evals tell you whether your AI works BEFORE you ship it, against scenarios you thought to test. Observability tells you what it's actually doing right now, for real users, including the scenarios you never thought to test. Without logging every call — the prompt, the response, how long it took, what it cost, whether it succeeded — a production AI feature is a black box you can't debug, improve, or even fully trust.

🔴 COMMANDER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Evals and observability answer different questions with the same underlying discipline: evals ask "does it pass the cases I thought to write," observability asks "what is it actually doing, right now, for real people." Neither replaces the other — a feature can pass every eval and still misbehave in production on inputs nobody anticipated, which is exactly what logs reveal that a test suite can't.

2

Field Manual

What to Log for Every AI Call

Every request, without exception, should record: a timestamp, the prompt/messages sent, the response received, latency (how long it took), token counts and cost (Mission 7.8), which model handled it (useful with 7.8's routing/fallback), and whether it succeeded or failed.

JAVASCRIPT
async function loggedCall(prompt, callFn) {
  const start = Date.now();
  try {
    const response = await callFn(prompt);
    logEntry({
      timestamp: new Date().toISOString(),
      prompt, response,
      latencyMs: Date.now() - start,
      success: true,
    });
    return response;
  } catch (err) {
    logEntry({
      timestamp: new Date().toISOString(),
      prompt, error: err.message,
      latencyMs: Date.now() - start,
      success: false,
    });
    throw err;
  }
}
WHAT JUST HAPPENED Every call gets logged exactly once, on EITHER path — success or failure — because the logging happens in both the try and catch blocks. A logger that only records successes gives a falsely rosy picture of how the feature is actually performing.

Tracing a Multi-Step Agent Run

A single agent run (Mission 8.2) makes several LLM calls, not one. A useful trace groups ALL of them under one shared ID, so you can look at one complete agent run — every reason/act/observe step — together, in order, instead of as disconnected individual log lines.

WHY THIS MATTERS FOR DEBUGGING If an agent gives a wrong final answer, the useful debugging question is "which specific step in its reasoning went wrong" — answerable only if you can see the whole chain of reason/act/observe steps for that one run together, not scattered across unrelated log entries.

Privacy & the Cost of Logging Everything

Full prompts and responses can contain real user data — logging every byte forever is both a privacy risk and a real storage cost. Mature systems redact sensitive fields before storing them and sample (log every call's metadata, but only a fraction of full prompt/response bodies) rather than keeping everything indefinitely.

⚠ COMMON MISTAKES

  • Only logging successful calls, giving a falsely optimistic picture of real-world performance.
  • Logging individual calls with no way to group a multi-step agent run's steps back together.
  • Storing every full prompt and response forever with no redaction or sampling, both a privacy and cost risk.
  • Building observability only after something breaks in production, instead of from day one.
