MISSION 4.1: ORGANIZING CODE — MODULES & FILES

Splitting the Ship into Systems

Every project you've built so far has lived in one script. That works fine when a script is 40 lines long. It stops working the moment it's 4,000 — one file holding your math, your UI, your data-loading, and your event handlers all tangled together, where changing one thing quietly breaks three others. This mission is about the fix: splitting code into separate files with clearly defined connections between them, using JavaScript's built-in module system.

🟡 OFFICER LEVEL ⏱ ~35 MIN 🛠 BROWSER ONLY
1

Briefing

A real starship isn't one enormous undifferentiated hull with wires running everywhere. It has separate systems — propulsion, life support, navigation — each built and maintained in its own compartment, each with a clearly labeled panel of connectors on the wall: "power in here," "sensor data out there." An engineer working on life support doesn't need to understand the wiring of the navigation computer. They just need to know what connects to what.

That's exactly the problem JavaScript modules solve. Instead of one giant script.js holding everything, you split your code into separate files, each responsible for one thing — say, math.js for calculations, ui.js for building display strings, and main.js for tying it all together. Each file explicitly exports the specific pieces it wants to share, and any other file that needs them explicitly imports them by name. Nothing leaks out by accident, and every connection between files is written down in plain sight at the top of the file.

This isn't just tidiness for its own sake. As a project grows, "everything is global and everything can touch everything" stops being manageable — you lose track of what depends on what, two functions accidentally get the same name and collide, and a small change ripples out in ways nobody can predict. Modules give every piece of code its own compartment, with the wiring between compartments made explicit instead of implicit.

math.js exports pure calculations that both ui.js and main.js import; ui.js exports display helpers that main.js imports; the browser only ever loads main.js directly, via a <script type="module"> tag in the HTML — everything else is pulled in automatically by the import chain.

Field Manual

Why One Giant File Breaks Down

Nothing stops you from writing every function your app needs into a single script.js. For a small project, that's fine. But watch what happens as it grows:

JAVASCRIPT (DON'T DO THIS)
// script.js — 2,000 lines and counting...
function addFuel(current, amount) { /* ... */ }
function renderFuelBar(current) { /* ... */ }
function saveToStorage(data) { /* ... */ }
function validateForm(form) { /* ... */ }
function calculateBurn(distance, rate) { /* ... */ }
function renderStatus(msg) { /* ... */ }
// ...another 40 unrelated functions, all in one scope
WHAT JUST HAPPENED Every one of these functions lives in the same global scope. Finding "the fuel math" means scrolling past storage code and form validation to find it. Two people (or two different tutorials) both naming a helper render() silently overwrite each other. And there's no way to tell, just by looking, which functions are meant to be used by other files and which are just internal scratch work.

export & import Syntax

A module is just a regular .js file that uses two new keywords. export marks something as available to other files; import pulls a specific exported thing into the current file, naming exactly which file it came from.

MATH.JS
export function addFuel(current, amount) {
  return current + amount;
}

export const MAX_FUEL = 100;
MAIN.JS
import { addFuel, MAX_FUEL } from './math.js';

let fuel = addFuel(60, 20);
console.log(fuel, MAX_FUEL);
WHAT JUST HAPPENED The import path './math.js' is relative to the file doing the importing — ./ means "same folder." Notice the full .js extension is included; unlike some other JavaScript tooling you may encounter later, plain browser modules require it. Anything not marked export stays completely private to that file — a genuine, enforced boundary, not just a naming convention.

Named vs. Default Exports

A file can have any number of named exports (each imported in matching curly braces, by exact name) but at most one default export (imported without braces, under whatever name you choose).

UI.JS
export function renderFuelBar(current) {
  return `[FUEL: ${current}%]`;
}

export default function renderStatus(message) {
  return `>> ${message}`;
}
MAIN.JS
import renderStatus, { renderFuelBar } from './ui.js';
// renderStatus  — the default export, any local name works
// renderFuelBar — a named export, must match exactly
WHAT JUST HAPPENED Use a default export when a file has one obvious "main thing" it provides (a single component, a single class). Use named exports for a toolbox of related-but-separate helpers, like the math functions in math.js — that way a file importing from it only pulls in exactly the names it needs, and it's obvious at a glance which functions came from where.

Loading Modules in HTML

Modules need one extra signal in your HTML: the script tag that kicks everything off must include type="module". This tells the browser "treat this file, and everything it imports, as a module" — which unlocks import/export syntax and a few other module-only behaviors.

INDEX.HTML
<script type="module" src="main.js"></script>
WHAT JUST HAPPENED You only ever point a <script type="module"> tag at your entry file — here, main.js. You don't add separate script tags for math.js or ui.js; the browser follows the import statements inside main.js and fetches them automatically. Leave off type="module" and the browser reads import/export as a plain syntax error, because regular scripts were never designed to understand them.
▸ DEEP DIVE: Why modules refuse to run from a plain double-click

If you've ever built an HTML file, double-clicked it, and watched it open straight in your browser with a file:///... address bar — try that with a module-based project and it breaks. Modules load their imports with the same kind of request a browser uses to fetch data over the network, and browsers block that entirely under the file:// protocol for security reasons (it's the same family of protection — CORS — that stops a random webpage from silently reading files off your hard drive). Open the console and you'll see an error like "has been blocked by CORS policy."

The fix is exactly why this academy's own mission pages, and every real web project you'll build from here on, are served through a local development server instead of opened directly — something as simple as VS Code's "Live Server" extension, or running python -m http.server in a project folder, which serves your files over http://localhost instead of file://. If you've ever wondered why tutorials keep telling you to "run a local server" instead of just opening the file — this is the reason, and modules are where it stops being optional.

Organizing a Small Project into Files

There's no single correct way to split a project, but a good starting instinct is: one file per responsibility. A small app might look like this:

PROJECT LAYOUT
my-project/
├── index.html         (has <script type="module" src="main.js">)
├── main.js            (entry point — imports from the others, wires it up)
├── math.js            (pure calculation helpers, no DOM code)
└── ui.js              (functions that build display strings/DOM)
WHAT JUST HAPPENED math.js knows nothing about the page — no document, no DOM. That's deliberate: it's easier to test and reuse a file that just does calculations. ui.js knows how to build and display things but doesn't decide game logic. main.js is the "wiring closet" — it imports from both and connects them, but keeps almost no logic of its own. This pattern (logic files → display files → one small entry file that connects them) scales up to real production codebases with hundreds of files.

This one has to happen outside the browser sandbox, on your own machine, with real files. That's the point — you need to actually feel a module boundary in action.

▸ HINT

If the console says something about "has been blocked by CORS policy" or "Failed to load module script," check the address bar first — if it starts with file:///, that's the whole problem. Start a local server and reload from the http://localhost address it gives you instead.

BONUS OBJECTIVE

Add a third file (like ui.js) that main.js also imports from, and give it one default export alongside its named ones. Import the default export under a name of your choosing in main.js, right next to a named import from the same file, on one import line.

⚠ COMMON MISTAKES

  • Forgetting type="module" on the script tag — import/export then throw a plain syntax error.
  • Opening the HTML file directly from disk (file:///...) instead of through a local server, and hitting a CORS error.
  • Dropping the .js extension in an import path — browsers require it, even though some other JS tooling doesn't.
  • Mixing up named vs. default import syntax — braces ({ name }) for named, no braces for default.
  • Trying to have two default exports in one file — a file gets at most one, but unlimited named exports.
