MISSION 7.3: CALLING AN LLM API SAFELY

Build a Chatbot Through Your Own Proxy

Mission 5.6 taught you why a secret key can never live in client-side code — a visitor can always read it with DevTools. An LLM API key raises the stakes: unlike most leaked keys, it's usually billed by usage, meter running the instant someone else finds it and starts sending requests on your account. This mission is the single most important rule of this entire sector, made concrete: your app never talks to the LLM provider directly — it talks to your own backend, which holds the key.

Briefing

A leaked database password is bad. A leaked LLM API key is a live meter: every request anyone sends with it costs real money, instantly, with no undo. This is exactly why the pattern from Mission 5.6 isn't optional here — it's the entire architecture.

Field Manual

The Proxy Function — a Real Cloudflare Worker

This is Mission 5.6's serverless function pattern, applied specifically to an LLM call. Your app calls this endpoint; this endpoint — and only this endpoint — calls the real provider.

JAVASCRIPT (Cloudflare Worker)
export default {
  async fetch(request, env) {
    if (request.method !== 'POST') {
      return new Response('Method not allowed', { status: 405 });
    }

    const { messages } = await request.json();

    const response = await fetch('https://api.openai.com/v1/chat/completions', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        // env.OPENAI_API_KEY lives ONLY here, set in the Cloudflare
        // dashboard — never in any file the browser downloads.
        Authorization: `Bearer ${env.OPENAI_API_KEY}`,
      },
      body: JSON.stringify({ model: 'gpt-4o-mini', messages }),
    });

    return new Response(response.body, {
      headers: { 'Content-Type': 'application/json' },
    });
  },
};
WHAT JUST HAPPENED The Worker receives the messages array (Mission 7.2's role-based shape) from your app, attaches the real secret key server-side, forwards the request to the actual provider, and streams the response back. Your app's code never contains the string OPENAI_API_KEY anywhere — it only ever calls your own Worker's URL.

Calling Your Proxy From the Client

From your app's perspective, this looks exactly like any other fetch call from Mission 4.3 — because it is one. The only difference is the URL points at infrastructure you control, not the LLM provider directly.

JAVASCRIPT (client)
async function askAssistant(messages) {
  const response = await fetch('https://your-worker.your-name.workers.dev/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ messages }),
  });
  const data = await response.json();
  return data.choices[0].message.content;
}
WHAT JUST HAPPENED Notice there is nothing sensitive in this entire function — no key, no secret, nothing a curious visitor reading your source could abuse. That's the whole point: the client's job shrinks to "send messages, receive a reply," and the proxy carries all the risk, safely, on infrastructure only you control.

Rate Limiting — Your Proxy Needs Its Own Guardrails

Hiding the key isn't the whole job. A public proxy with no limits at all is still an open invitation — anyone who finds its URL can send unlimited requests and run up your bill, even without your provider key. Real proxies add their own protection: a simple per-visitor rate limit, requiring a lightweight token of your own (not the provider's key) before forwarding a request, and capping the maximum tokens per response.

A MINIMUM VIABLE GUARDRAIL Even a crude limit — "reject if this IP has made more than 20 requests in the last hour" — closes off the worst-case scenario of an open proxy being discovered and hammered. Mission 7.10's capstone asks you to add exactly this.

⚠ COMMON MISTAKES

  • Calling the LLM provider's API directly from client-side JavaScript with the real key embedded "just to test it quickly."
  • Building a proxy that hides the key but has no rate limiting at all — still an open invitation to abuse.
  • Forgetting that a leaked LLM key isn't just a privacy problem — it's a live, metered bill running on your account.
  • Assuming a proxy is "done" once it works once — production readiness means it survives being discovered and hit hard.
