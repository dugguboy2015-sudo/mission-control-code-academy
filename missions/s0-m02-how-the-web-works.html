MISSION 0.2: HOW THE WEB WORKS

Browsers, Servers & the Journey of a Single Request

Every time you open a website, something remarkable happens in a fraction of a second: your computer finds another computer, possibly on the other side of the planet, asks it a question, and gets an answer back — formatted precisely so your browser can turn it into the page you see. Before you build anything that lives on the web, you need a working mental model of that journey. It's not magic. It's a small number of well-defined steps, repeated billions of times a second, all over the world.

1

Briefing

Think of the internet as a galaxy of space stations, each one a computer, each with its own address. Your laptop or phone is one small ship. When you type a website address and hit enter, your ship isn't downloading the website from thin air — it's sending a very specific, structured request across the network to one particular station, and that station is sending a structured response back. The two computers involved have names: the one asking is the client (your browser), and the one answering is the server (another computer, usually running 24/7, somewhere in a data center).

Two things have to happen before your ship can even send its message. First, it needs the station's exact coordinates — a numeric address called an IP address. Since nobody wants to memorize numbers, we use human-friendly names instead (like nasa.gov), and a global directory service called DNS (Domain Name System) translates the name into the real address behind the scenes, automatically, every time. Second, both computers need to agree on a shared language for the conversation — that's HTTP (HyperText Transfer Protocol), a strict set of rules for how a request must be phrased and how a response must be structured, so any browser can talk to any server on Earth without confusion.

DNS resolves the name to an address first; then the client sends an HTTP request and the server sends back an HTTP response.
2

Field Manual

URLs — The Full Address

A URL (Uniform Resource Locator) is a complete, structured address — not just a station name, but the exact room inside it. Each piece has a job.

URL ANATOMY
https://api.example.com:443/missions/7?sort=newest#debrief

https              -- protocol (how to talk)
api.example.com    -- domain (which server)
443                -- port (which door on that server)
/missions/7        -- path (which resource)
?sort=newest       -- query string (extra options)
#debrief           -- fragment (a spot within the page)
WHAT JUST HAPPENED A port is like a numbered docking bay on the server — one machine can run several different services at once, each listening on its own port. You'll rarely type a port number by hand because https defaults to port 443 and plain http defaults to 80 — but you'll see ports constantly once you run your own local servers in later missions (e.g. localhost:3000).

HTTP — The Language of Requests and Responses

Every HTTP request has a method that states its intent. GET asks for data without changing anything. POST sends new data to be created. There are others (PUT, DELETE) you'll meet properly in Sector 4 when you start talking to real APIs.

HTTP REQUEST
GET /missions/7 HTTP/1.1
Host: api.example.com
Accept: text/html
HTTP RESPONSE
HTTP/1.1 200 OK
Content-Type: text/html

<html>...</html>
WHAT JUST HAPPENED Every response starts with a status code — a three-digit number that tells the client exactly what happened before it even reads the content. 200 means success. You've almost certainly seen 404 (not found) — that's the server explicitly saying "I understood your request, and the thing you asked for doesn't exist here."
▸ DEEP DIVE: Common status codes worth knowing now

200 OK — success. 301 — this moved permanently, go here instead. 404 Not Found — no resource at this path. 500 Internal Server Error — the server itself broke while handling this. You'll debug real versions of all four once you start working with APIs in Sector 4.

What the Browser Actually Does With the Response

Getting the HTML back is only half the job. The browser then reads that HTML top to bottom, and whenever it finds a reference to something else it needs — a CSS file, a JavaScript file, an image — it fires off additional HTTP requests for each one, in parallel where it can. Only once everything it needs has arrived does the fully-styled, fully-interactive page appear. This is why a page can "flash" unstyled for a split second on a slow connection: the HTML arrived, but the CSS request is still in flight.

THE KEY IDEA One page load is rarely one request — it's a small flurry of requests, all triggered by that first HTML response. You'll actually watch this happen, request by request, using DevTools' Network tab in Mission 0.3.

Static vs. Dynamic — Two Kinds of Servers

Some servers just hand back a file exactly as it's stored on disk — this is a static site, and it's what GitHub Pages and Cloudflare Pages serve in Mission 4.5. Others run actual code every time a request arrives, building a custom response on the fly — often by pulling data out of a database first. That's a dynamic server, and it's what powers anything with logins, live data, or personalization. You'll build both, starting simple and static in Sector 1 and going dynamic starting in Sector 5.

Mission Challenge

Open your browser's real DevTools (right-click any webpage → "Inspect" → the "Network" tab) and reload a real site.

▸ HINT

If DevTools looks empty, reload the page (Ctrl+R / Cmd+R) while the Network tab is already open — it only records requests that happen while it's watching. Most browsers also have a "Preserve log" checkbox worth turning on.

BONUS OBJECTIVE

Find a request with a status in the 300 range (a redirect). Click it and see the response header telling the browser where to go instead — that's exactly how http:// URLs automatically become https:// on most modern sites.

⚠ COMMON MISTAKES

  • Assuming "the website" is one file — a real page load is usually a dozen or more separate requests.
  • Confusing a domain name with the server itself — the name is just a friendly label DNS translates for you.
  • Thinking a 404 means "the whole internet is broken" rather than "this one specific path doesn't exist on this server."
  • Forgetting that https and http default to different ports (443 vs. 80) behind the scenes.
