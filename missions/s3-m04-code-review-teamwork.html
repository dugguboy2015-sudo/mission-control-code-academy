MISSION 3.4: CODE REVIEW & TEAMWORK

Building Software Together

Mission 3.3 got your code into a Pull Request. Now comes the part that makes teams great: someone else reads it before it ships. Code review catches bugs and security holes, spreads knowledge, and — done kindly — makes everyone better. In this mission you'll review a real-looking Pull Request, write feedback a teammate would actually thank you for, and decide whether it's ready to merge.

🟡 OFFICER LEVEL ⏱ ~35 MIN 🛠 BROWSER ONLY
1

Briefing

Almost no professional code reaches users without a second pair of eyes. The author opens a Pull Request; a reviewer reads the diff line by line, leaves comments, and finally chooses Approve, Comment, or Request changes. The goal isn't to prove you're smarter — it's that the team's code gets better, and the author learns something rather than feeling attacked.

With AI writing more and more code, reviewing has become one of the most important skills a developer has: reading code critically is how you catch what the machine (or your tired self) got wrong.

2

Field Manual

What a Reviewer Looks For — in This Order

  1. Correctness — does it do what the PR says? Any bugs or missing edge cases?
  2. Security — secrets in code, untrusted input used unsafely, data leaking? (Sector 9 goes deep.)
  3. Clarity — can the next person understand it? Clear names, no mystery numbers, no dead code.
  4. Nits — tiny style preferences. Label them "nit:" so nobody mistakes them for blockers.

Feedback People Can Use: Kind, Specific, Actionable

REVIEW COMMENTS
✗  This is wrong.
✗  Why would you do this??

✓  Line 5 uses = (assignment) instead of > — so every score overwrites the best one.
   Could we change it to `if (score > best)`?
✓  nit: `x` could be called `previousBest` so it's clear what it holds.
✓  Really nice idea to save the best score locally — players will love it.
WHAT JUST HAPPENED Good comments say where (the line), what goes wrong and why, then suggest a fix as a question ("Could we…?"). They comment on the code, never the person. And they include genuine praise — reviews aren't only for problems.

Being Reviewed

Every developer, at every level, gets review comments. Treat them as free lessons. Say thanks, ask if something is unclear, fix it or explain your reasoning — and remember the comment is about the code, not about you. Small PRs get faster, better reviews than giant ones.

Other Ways Teams Build Together

  • Issues — a written to-do for one bug or feature, so work can be split up and tracked.
  • Pair programming — two people, one keyboard: a "driver" types while a "navigator" thinks ahead. Then swap.
  • Agreeing on style — a formatter like Prettier settles spacing arguments automatically, so reviews focus on what matters.

⚠ COMMON MISTAKES

  • Approving without actually reading the diff ("looks good to me" on code you skimmed).
  • Commenting on the person ("you always…") instead of the code.
  • Blocking a PR over nits while missing the real bug.
  • Taking review comments personally — they're free lessons from someone who read your work carefully.
