MISSION 5.4: FIREBASE

The Universal Comm Relay — Data That Pushes Itself

In Mission 07 you learned how a database like Supabase organizes data into rigid tables and rows, and how your code has to explicitly ask for updates. Firebase, Google's platform, takes a genuinely different approach on both fronts: data lives as flexible documents instead of table rows, and — its signature feature — the database can push changes to every connected device the instant they happen, with no one needing to ask twice.

🟡 OFFICER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

Firebase's database, called Firestore, doesn't use tables and rows at all. Instead, it stores documents — flexible bundles of fields, similar to a JavaScript object — grouped into collections. Two documents in the same collection don't even need the same fields. This is called NoSQL, and it trades some of the strict structure and guaranteed relationships you saw with SQL for flexibility and speed at massive scale.

collection: "crew"
doc: crew_001
name: "Nova"
rank: "Captain"
station: "Bridge"
doc: crew_002
name: "Kip"
rank: "Engineer"
certifications: ["EVA", "welding"]
Two documents in the same collection — notice "crew_002" has an extra field "crew_001" doesn't have. No schema is enforced.

Just like Supabase, your website never talks to Firestore directly — it goes through the Firebase SDK, a library that handles the connection, and Firebase's own Authentication system for managing who's allowed to do what.

Same overall shape as Supabase's architecture — client, controlled access layer, database and auth — different vendor, different data model.

The bigger conceptual shift is how updates travel. A normal request works like sending a message and waiting for a reply — ask, then get an answer, once. Firestore instead lets you subscribe to a piece of data: you get an initial answer immediately, and then the server keeps that connection open and pushes you a fresh update automatically, in real time, every single time the data changes — no polling, no refreshing, no asking again.

Real-time listeners are Firebase's headline feature — this is what powers live chat apps, multiplayer games, and collaborative tools.

Field Manual

Setting Up a Firebase Project

Everything starts at the Firebase console. After creating a project, you'll land on a dashboard with a left sidebar listing available services.

WHERE TO CLICK In the left sidebar, click Build → Firestore Database and press "Create database" to provision your NoSQL store. Click Build → Authentication and press "Get started" to enable sign-in methods (email/password, Google, and others are all toggles here). Under Project settings (the gear icon), you'll find a "Your apps" section where registering a web app gives you a small config object containing your project's API keys — you'll paste that directly into your code.

Writing & Reading Documents

The Firestore SDK gives you functions for each piece of the CRUD picture you learned in Mission 07 — just with document/collection vocabulary instead of table/row vocabulary.

JAVASCRIPT
import { getFirestore, collection, addDoc, getDocs } from "firebase/firestore";

const db = getFirestore();

// Create a document
await addDoc(collection(db, "crew"), {
  name: "Nova",
  rank: "Captain",
  station: "Bridge"
});

// Read every document in the collection
const snapshot = await getDocs(collection(db, "crew"));
snapshot.forEach((doc) => {
  console.log(doc.id, doc.data());
});
WHAT JUST HAPPENED addDoc creates a new document with an auto-generated ID inside the "crew" collection — you didn't have to define columns or types ahead of time, unlike CREATE TABLE in SQL. getDocs fetches a one-time snapshot of every document currently in that collection; doc.data() returns each document's fields as a plain JavaScript object.

Real-Time Listeners with onSnapshot

This is the function that makes Firebase famous. Instead of asking once with getDocs, you subscribe with onSnapshot, and your callback function re-runs automatically every time the data changes — on any device, anywhere.

JAVASCRIPT
import { collection, onSnapshot } from "firebase/firestore";

onSnapshot(collection(db, "crew"), (snapshot) => {
  const list = document.querySelector("#crewList");
  list.innerHTML = "";
  snapshot.forEach((doc) => {
    list.innerHTML += `<li>${doc.data().name}</li>`;
  });
});
WHAT JUST HAPPENED This function runs once immediately with the current data, and then automatically runs again every time anyone, anywhere, adds, edits, or removes a document in the "crew" collection — without you writing any refresh logic, polling timer, or manual reload. This single pattern is how apps like live chat, shared whiteboards, and multiplayer lobbies actually work.
▸ DEEP DIVE: Doesn't a permanently open connection cost something?

Yes — every active listener counts toward Firebase's usage-based billing, and leaving listeners attached to elements that no longer exist on the page is a common source of both bugs and unexpected cost. Production apps carefully detach listeners (using the "unsubscribe" function onSnapshot returns) when a component is no longer visible.

Firebase Authentication

Just like Supabase, Firebase handles the entire sign-up/login flow so you never write your own password storage — this is a case where using a proven system instead of building your own is a genuine security requirement, not a shortcut.

JAVASCRIPT
import { getAuth, createUserWithEmailAndPassword, signInWithEmailAndPassword } from "firebase/auth";

const auth = getAuth();

// Sign up
await createUserWithEmailAndPassword(auth, "cadet@example.com", "secure-password");

// Log in
await signInWithEmailAndPassword(auth, "cadet@example.com", "secure-password");
WHAT JUST HAPPENED Firebase stores and hashes the password securely on its own servers — your code never sees or stores the raw password after this call. Once signed in, auth.currentUser holds the logged-in user's info, and Firestore's security rules can reference that identity to decide what data that specific user is allowed to read or write.

⚠ COMMON MISTAKES

  • Leaving Firestore's security rules wide open ("allow all") past initial testing — this is a real, common way to leak an entire database publicly.
  • Trying to run a SQL-style JOIN — Firestore has no equivalent; related data is either nested or manually fetched in a second query.
  • Attaching an onSnapshot listener and never unsubscribing, quietly wasting reads and money.
  • Assuming every document in a collection has the same fields, since NoSQL never enforces that.
  • Confusing a one-time getDocs() read with a live onSnapshot() subscription — they behave very differently.
