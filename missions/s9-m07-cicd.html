MISSION 9.7: CI/CD & DEPLOY PIPELINES

Automated Build → Test → Ship

Mission 9.1's tests are only as valuable as how reliably they actually run. "I'll remember to run them before I push" fails eventually — everyone forgets sometimes. CI/CD (Continuous Integration / Continuous Deployment) automates this: every single change automatically triggers a pipeline that builds the project, runs every test, and only deploys if everything passes. No memory required, no exceptions.

🔴 COMMANDER LEVEL ⏱ ~50 MIN 🛠 BROWSER + GITHUB ACCOUNT

Briefing

Continuous Integration (CI) means every change automatically gets built and tested the moment it's pushed. Continuous Deployment (CD) means code that passes CI gets automatically shipped to production, with no manual "click deploy" step. Together, a failing test literally blocks a bad deploy from ever reaching real users — a safety net that works even on the day you forget to run tests yourself.

Field Manual

A Real GitHub Actions Workflow

Mission 4.5 deployed by hand. A real CI/CD pipeline runs the same steps automatically, on every push, using a config file GitHub itself reads and executes.

YAML — .github/workflows/deploy.yml
name: Build, Test, Deploy
on: push

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm install
      - run: npm test
      - run: npm run build
      - name: Deploy to Cloudflare Pages
        if: success()
        run: npx wrangler pages deploy ./dist
WHAT JUST HAPPENED on: push means this runs automatically on every single push, with zero manual action. The steps run in order, top to bottom, and — this is the critical part — if: success() means the deploy step only runs if EVERY previous step (including npm test) succeeded. A failing test genuinely, automatically blocks a bad deploy.

Fail Fast

A well-designed pipeline stops at the FIRST failing step instead of continuing pointlessly. If tests fail, there's no reason to spend time building or deploying — the pipeline should stop immediately and report exactly which step failed.

The Pipeline as a Safety Net, Not a Formality

The whole point is that a pipeline catches mistakes automatically, before they reach real users — not after a bug report comes in. This is Sector 9's central theme, made concrete and automatic: testing (9.1), code quality (9.4), and security checks (9.5-9.6) all become dramatically more valuable once they run on every single change, guaranteed, instead of "whenever someone remembers."

Mission Challenge

Build and break your own pipeline, then design the real one.

▸ HINT

A step function should throw a real, descriptive error message on failure rather than just returning false — that's what lets the pipeline report a specific, useful reason instead of a generic failure.

BONUS OBJECTIVE

Add a step that only runs conditionally — for example, a "deploy to staging" step that only fires on certain conditions, versus "deploy to production" that requires an extra explicit flag. This mirrors how real pipelines often deploy differently based on which branch triggered them.

⚠ COMMON MISTAKES

  • Deploying manually "just this once" instead of trusting and using the automated pipeline consistently.
  • A pipeline that continues running steps after an earlier one already failed, wasting time and obscuring the real failure.
  • Writing tests (Mission 9.1) but never actually wiring them into an automated pipeline that runs on every push.
  • A deploy step with no gate at all, so it runs regardless of whether tests passed.
