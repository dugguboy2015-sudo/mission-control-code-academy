MISSION 8.5: CONNECTING AGENTS TO REAL SYSTEMS

MCP, Introduced

Every tool your agents have used so far was a JavaScript function you wrote directly into the same file. Real agents need to connect to genuinely external systems — a calendar, a file system, a company's database, someone else's API — and without a shared standard, every single one of those connections needs its own custom, one-off integration code. MCP (Model Context Protocol) is an open standard that fixes this: one consistent way for any system to expose its tools, and one consistent way for any agent to discover and use them.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

Imagine you want your agent to use a calendar, a notes app, AND a weather service. Without a standard, that's three completely different APIs, three different auth schemes, three sets of custom glue code — and every new integration repeats the work. MCP defines a client-server relationship: an MCP server wraps one system (the calendar, the notes app, whatever) and exposes its capabilities in one standard shape; an MCP client (your agent) connects to any number of servers and discovers what each one can do, without hardcoding it in advance.

One agent, one standard protocol, connected to as many MCP servers as it needs — each server wraps a different real system.
2

Field Manual

MCP's Core Idea: Discovery, Then Calling

Instead of hardcoding "this server has a search_notes tool," an MCP client asks the server directly: "what can you do?" The server responds with a list of its available tools — name, description, and parameters, exactly Mission 7.4 and 8.3's tool shape. The client can then call any of those discovered tools by name, without ever needing to know about them in advance.

JAVASCRIPT (conceptual MCP client flow)
const tools = await mcpClient.listTools(); // discover, at runtime
// tools looks like: [{ name: "search_notes", description: ..., parameters: ... }, ...]

const relevantTool = tools.find(t => t.name === "search_notes");
const result = await mcpClient.callTool(relevantTool.name, { keyword: "trip" });
WHAT JUST HAPPENED Nothing about search_notes specifically was hardcoded anywhere in the client's code — it was discovered at runtime from whatever server happened to offer it. Swap in a completely different MCP server tomorrow, and the exact same client code can discover and use its tools too, with zero changes.

Why This Matters, Concretely

Mission 8.3 already taught you good tool design and Mission 7.4 taught you the tool-calling shape. MCP doesn't replace either — it standardizes HOW tools get exposed and discovered, so a tool built once (an MCP server) can be reused across many different agents and apps instead of being rewritten as bespoke integration code every single time. This is the same instinct as Sector 5's realization that a standard API is better than every client reinventing its own protocol to reach a database.

⚠ COMMON MISTAKES

  • Hardcoding which server has which tool instead of genuinely discovering it via listTools() — defeats the entire point of the standard.
  • Writing custom, one-off integration code per system instead of reaching for a shared protocol when one's available.
  • Forgetting to track which server a discovered tool came from, making it impossible to actually call it later.
  • Assuming MCP replaces good tool design (Mission 8.3) — it standardizes discovery and calling, not tool quality.
