MISSION 3.2: BRANCHING & MERGING DEEP-DIVE

Parallel Timelines, Conflict Resolution

You've already split a timeline and merged it back. Now we go deeper: how to name and organize branches like a real engineering team, why Git sometimes just slides a pointer forward and sometimes builds a whole new commit to join two histories, and — the part every cadet dreads until they've done it once — what to do when Git looks you dead in the eye and says it can't decide for you.

🟡 OFFICER LEVEL ⏱ ~50 MIN 🛠 TERMINAL REQUIRED
1

Briefing

Imagine two engineering teams both working from the same panel schematic. Team A is upgrading the thruster wiring. Team B is rerouting the coolant lines. As long as they're editing different corners of the blueprint, someone can tape both sets of changes onto the master copy with zero problems — the changes don't overlap, so combining them is mechanical, almost boring. That's most merges. Git does the taping-together automatically and you barely notice it happened.

But every so often, both teams need to change the exact same wire on the exact same panel — and they don't agree on what it should become. Now taping both versions on top of each other makes no sense. Somebody — a human, not the photocopier — has to look at both proposals and decide the final wiring. That is a merge conflict. It is not an error, it is not something you broke, and it is not rare. It is Git being honest that it hit a decision it isn't allowed to make for you.

This mission covers three things: choosing when and how to branch like a professional, understanding why Git sometimes merges quietly (a fast-forward) and sometimes builds a visible junction (a merge commit), and — the main event — reading and resolving a real conflict, markers and all.

Branch A merges into main quietly (fast-forward — main hadn't moved). Branch B converges on the same line main just changed, so Git stops at a conflict. A human picks the final value; the merge completes as a real merge commit.
2

Field Manual

Branch Strategy & Naming

Any time you're about to do something that could temporarily break the project — a new feature, a risky fix, an experiment you're not sure will work — branch first. The rule of thumb: if you'd be embarrassed to have main in this state during a demo, you're on the wrong branch. Keep branches short-lived — the longer a branch lives apart from main, the more both timelines drift, and the more likely a merge turns into a conflict.

Git doesn't enforce branch names, but real teams do, by convention — it keeps a busy branch list scannable and often drives automation (like which branches trigger a deploy).

BASH
# A new capability
git checkout -b feature/shield-recalibration

# A bug fix
git checkout -b fix/thruster-overheat

# Non-functional housekeeping — docs, deps, config
git checkout -b chore/update-flight-docs
WHAT JUST HAPPENED Nothing Git-mechanical — feature/, fix/, and chore/ are just text before a slash. But that text tells every other engineer (and often your CI pipeline) what kind of change lives here before they open a single file.

Fast-Forward vs. Merge Commits

When you run git merge, Git first checks one thing: has the branch you're merging into moved at all since you split off? If main hasn't gained a single new commit since your branch was created, Git doesn't need to combine anything — it just slides the main pointer forward to your branch's tip. This is a fast-forward: no new commit is created, and the history stays perfectly linear.

If main has moved — someone else merged something, or you committed directly on main too — Git can no longer just slide the pointer. It performs a real three-way merge and creates a new merge commit with two parents: one pointing back into main's history, one pointing back into your branch's history. That's the visible "junction" you see in a commit graph.

BASH
# Default: fast-forwards automatically when possible
git merge feature/shield-recalibration

# Force a real merge commit even if a fast-forward was possible
# (some teams do this on every feature branch, to keep a visible record)
git merge --no-ff feature/shield-recalibration
WHAT JUST HAPPENED Neither outcome is "better" — fast-forward keeps history tidy and linear; --no-ff preserves the fact that a feature branch existed at all, which some teams want for traceability. Either way, you didn't create a conflict just by having two branches — a conflict only shows up in the three-way-merge path, and only when both sides touched the same lines.

What Causes a Conflict

A three-way merge compares three snapshots: the base (the common ancestor commit both branches split from), ours (the tip of the branch you're on), and theirs (the tip of the branch you're merging in). For every region of every file, Git asks: did only one side change this since the base? If so, take that side — easy, automatic, silent. Did both sides change the same region, to the same new content? Also fine, no real disagreement. Did both sides change the same region to different content? That's the only case Git refuses to guess on. That's a conflict.

TEXT
base:    THRUST_LIMIT = 100
ours:    THRUST_LIMIT = 150   (fix/raise-thrust-limit, already merged into main)
theirs:  THRUST_LIMIT = 80    (feature/safety-cap)

-> both changed the same line to different values -> CONFLICT
WHAT JUST HAPPENED Notice it's about lines, not files or "how big" a change is. Two branches can rewrite an entire file each and merge cleanly if they touched different sections. Two branches can each change a single character on the same line and conflict. Overlap is the only thing that matters.

Reading Conflict Markers

When a conflict happens, Git doesn't refuse to touch the file — it edits it and drops both versions directly into the text, wrapped in markers, so you can see exactly what disagreed:

mission-config.txt
THRUST_CEILING = 500
<<<<<<< HEAD
THRUST_LIMIT = 150
=======
THRUST_LIMIT = 80
>>>>>>> feature/safety-cap
WHAT JUST HAPPENED <<<<<<< HEAD opens your current branch's version — everything down to the ======= divider is "ours." Everything between ======= and >>>>>>> feature/safety-cap is "theirs" — the incoming branch's version, and Git labels it with that branch's name so you know exactly whose change you're looking at. The unmarked line above (THRUST_CEILING = 500) didn't conflict, so Git left it alone entirely.

Resolving & Completing the Merge

Resolving a conflict is manual, ordinary text editing — there's no special "conflict mode" tool required, though editors often add nice highlighting for it. The workflow is always the same four steps:

BASH
# 1. See which files are still unmerged
git status

# 2. Open the file, decide the real final content, and DELETE all three
#    marker lines (<<<<<<<, =======, >>>>>>>) — they are not part of the file

# 3. Tell Git you've resolved this file
git add mission-config.txt

# 4. Complete the merge — Git pre-fills a merge commit message for you
git commit
WHAT JUST HAPPENED git add mid-conflict means something slightly different than usual: it's not just staging a change, it's telling Git "I've looked at this file and decided its final form." Once every conflicted file has been added, git commit seals the three-way merge — it already knows both parent commits, so it just needs your green light.
▸ DEEP DIVE: I'm mid-conflict and I want out. What now?

Not every conflict needs solving right this second. If you're not ready — need to check with a teammate, ran out of time, or realize you branched from the wrong place — you can cancel the entire merge attempt and go back to exactly how things were before you ran git merge:

git merge --abort

This restores your working file (markers and all, gone) and clears the in-progress merge state. Nothing is lost — the branch you tried to merge is untouched, and you can try again whenever you're ready.

Debrief / Cheat Sheet

git merge <branch>Fast-forwards if possible, else 3-way merges
git merge --no-ff <branch>Force a real merge commit
<<<<<<< HEADStart of "ours" — your current branch
=======Divider between the two versions
>>>>>>> branch-nameEnd of "theirs" — the incoming branch
git statusLists unmerged files mid-conflict
git add <file>Marks a conflict as resolved
git commitCompletes the merge (message pre-filled)
git merge --abortCancel the merge, restore pre-merge state

⚠ COMMON MISTAKES

  • Leaving a conflict marker (<<<<<<<, =======, or >>>>>>>) in the file by accident — Git will happily commit it, and now your code has a syntax error hiding in plain sight.
  • Panicking and assuming a conflict means something is broken — it's a normal, expected outcome of two branches touching the same lines, not a failure state.
  • Resolving a conflict without actually reading both versions first — you can only pick (or combine) correctly if you understand what each side was trying to do.
  • Forgetting git add after editing the file, then being confused why git commit still refuses to finish the merge.
  • Working directly on main instead of branching first — the more people commit straight to main, the more often everyone's changes collide there.
