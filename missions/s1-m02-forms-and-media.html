MISSION 1.2: FORMS, INPUTS & MEDIA

Taking Input from the Cadet

Mission 1.1 built the hull — structure that just sits there and displays. But most real systems need to listen. A ship's control panel doesn't just show readouts; it has switches, dials, and keypads the crew uses to send commands back to the ship. On the web, that panel is the <form> element and its family of inputs. This mission covers how to collect text, choices, and files from a visitor, how to embed audio and video, and how to catch obviously bad input before it ever leaves the browser.

🟢 CADET LEVEL ⏱ ~40 MIN 🛠 BROWSER ONLY
1

Briefing

Every mission so far has been one-way: your HTML tells the browser what to display, and the browser displays it. A <form> flips that around. It's the ship's control panel — a bounded region of the page where the crew (your visitor) can flip switches, type coordinates, and press a big red button that sends everything back to whoever's listening. Without forms, the web would be a read-only museum. With them, it's login screens, search bars, checkout pages, and every comment box you've ever typed into.

A form is a container — literally <form>...</form> — that wraps a collection of controls: text boxes, checkboxes, radio buttons, dropdowns, and more. Each control has a name attribute, which acts like a label on a wire. When the form is submitted, the browser bundles up every control's name and current value into a package and sends it off. Forget the name, and that control's wire isn't connected to anything — its data vanishes on submit, no error, no warning.

Two ideas matter more than the rest here. First: a control is only as useful as its <label> — the text that tells a human (or a screen reader) what the control is actually for. Second: the browser can catch some bad input before it's ever sent, using validation attributes like required and type="email" — a first line of defense, not the only one, but a genuinely useful one that costs you zero JavaScript.

This mission also covers <audio> and <video> — not because they're related to forms mechanically, but because they're the other major way a page takes something beyond plain text and hands it to the browser to render, and this is the natural place in the curriculum to cover "embedding media" before Sector 1 moves on to layout and styling.

Every control's name becomes a labeled wire. On submit, the browser bundles name=value pairs from every control and sends the whole package at once.
2

Field Manual

Text Inputs & Labels

The most common control is <input>, and its type attribute decides what kind of data it collects and what keyboard/UI the browser gives the user for it. type="text" is a plain single-line box; type="email" and type="number" look almost identical but carry different meaning and different built-in checks. Every input needs a name (so its data is identifiable when submitted) and, ideally, an id so a <label> can point at it.

HTML
<label for="callsign">Call Sign</label>
<input type="text" id="callsign" name="callsign">

<label for="email">Comms Email</label>
<input type="email" id="email" name="email">

<label for="age">Age</label>
<input type="number" id="age" name="age" min="9" max="18">
WHAT JUST HAPPENED type="email" and type="number" aren't cosmetic — mobile browsers show an @-key keyboard or a numeric keypad automatically, and both types get free format checking you didn't write. min/max on a number input constrain the range without a single line of JavaScript.

Choice Controls: Checkboxes, Radios & Select

Not every question has a free-text answer. Checkboxes are independent on/off switches — any number can be checked at once. Radio buttons that share the same name form a group where only one can be selected — picking a new one un-picks the others. A select dropdown does the same "exactly one choice" job as radios, but compresses it into a single control, which is better when there are many options.

HTML
<input type="checkbox" id="terms" name="terms">
<label for="terms">I have read the mission briefing</label>

<p>Preferred station:</p>
<input type="radio" id="bridge" name="station" value="bridge">
<label for="bridge">Bridge</label>
<input type="radio" id="engineering" name="station" value="engineering">
<label for="engineering">Engineering</label>

<label for="rank">Rank</label>
<select id="rank" name="rank">
  <option value="cadet">Cadet</option>
  <option value="officer">Officer</option>
</select>
WHAT JUST HAPPENED The shared name="station" is what makes the two radios mutually exclusive — the browser groups them by name, not by anything visual. Each radio also needs its own value, since that's what actually gets sent when it's the one selected. A checkbox sends name=on when checked and sends nothing at all when unchecked — worth remembering later when you read submitted data.

Longer Text: <textarea>

A plain <input type="text"> is a single line. When you need multiple lines — a message, a bio, mission notes — use <textarea> instead. It's a different tag, not an input type, and unlike <input> its starting content goes between the opening and closing tags rather than in a value attribute.

HTML
<label for="notes">Mission Notes</label>
<textarea id="notes" name="notes" rows="4"></textarea>
WHAT JUST HAPPENED rows sets the visible height in lines of text — the user can still type more than that; it just scrolls. Leaving the tags empty (<textarea></textarea>) starts it blank; putting text between the tags pre-fills it.

Embedding Audio & Video

<audio> and <video> give the browser a built-in media player — no plugin, no external library. Both accept a src pointing at a media file and a controls attribute that turns on the play/pause/volume UI. Without controls, the element exists but the user has no way to interact with it (useful only if you're driving it entirely from JavaScript, which is beyond this mission).

HTML
<audio controls src="launch-alert.mp3">
  Your browser doesn't support audio playback.
</audio>

<video controls width="320" src="docking-footage.mp4">
  Your browser doesn't support video playback.
</video>
WHAT JUST HAPPENED The text inside the tags is fallback content — it only shows up if the browser can't play the format at all, the same safety-net idea as alt text on an image. For video with several source formats, you can swap a single src for multiple <source> child elements so the browser picks the one it supports — useful to know exists, not required for this mission's challenge.

Basic Validation

The browser can reject obviously-bad input before your form ever submits, using nothing but HTML attributes. required blocks submission if a field is empty. minlength/maxlength constrain text length. pattern takes a regular expression the value must match — useful for things like a specific phone-number shape. None of this replaces checking data again on a server (a visitor can always bypass browser checks), but it catches typos instantly and gives the user feedback with zero network round-trip.

HTML
<label for="email2">Email</label>
<input type="email" id="email2" name="email" required>

<label for="pass">Access Code</label>
<input type="text" id="pass" name="pass" minlength="6" required>

<label for="phone">Comm Number</label>
<input type="tel" id="phone" name="phone" pattern="[0-9]{3}-[0-9]{4}" placeholder="555-0100">
WHAT JUST HAPPENED Try submitting a form with a required field left empty — the browser stops you and highlights it, no JavaScript written. pattern here means "exactly three digits, a dash, exactly four digits" — you don't need to master regular expressions today, just recognize that pattern is where they plug in.
▸ DEEP DIVE: Why <label for> actually matters

Linking a <label> to its input via matching for/id does two real things, not one cosmetic thing. First, a screen reader announces the label text when the user tabs to the input — without it, a blind user hears "edit text," with no idea what to type. Second, clicking anywhere on the label text focuses (or toggles) the input itself — try clicking the word "Bridge" above instead of the tiny radio circle. That's a real, measurably larger click target, which matters enormously on a phone screen with a thumb instead of a precise mouse cursor.

Debrief / Cheat Sheet

<form>Container that bundles and sends control data on submit
<label for="id">Names a control; links by matching the control's id
<input type="text/email/number">Single-line inputs with type-specific behavior
<input type="checkbox">Independent on/off toggle
<input type="radio">Exactly one choice per shared name group
<select><option>Dropdown, exactly one choice
<textarea>Multi-line free text
required / minlength / patternBrowser-side validation attributes
<audio controls> / <video controls>Native media players, no plugin needed
name attributeThe wire — no name means no data on submit

⚠ COMMON MISTAKES

  • Building an input with no <label> at all — the field looks fine but is invisible to a screen reader and hard to click precisely.
  • Forgetting the name attribute — the control renders and works visually, but its value is simply never sent anywhere.
  • Using type="text" for everything, including emails, numbers, and dates, and losing all the free validation and mobile-keyboard benefits those specific types give you.
  • Giving two unrelated radio buttons the same name by accident, which silently makes them mutually exclusive when they shouldn't be.
  • Mismatching <label for="x"> with an input whose id is spelled differently — the link silently fails and nobody notices until an accessibility check flags it.
