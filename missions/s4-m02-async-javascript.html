MISSION 4.2: ASYNC JAVASCRIPT

Promises & async/await

Some things a computer does are instant — add two numbers, check a condition, update a variable. Other things are slow: fetching data from a server on the other side of the planet, reading a file, waiting for a timer. JavaScript runs on a single thread, meaning it can only do one thing at a time — but it has a trick for the slow stuff: kick it off, keep working on everything else, and come back to it the moment it's ready. That trick is what this mission is about.

1

Briefing

Picture a ship's comms officer sending a message to a distant relay station. Radio waves aren't instant — there's a real delay before a reply comes back. A bad comms officer would key the mic, then stand frozen at the console staring at the speaker, doing absolutely nothing else, until a reply crackles through. A good comms officer sends the message, notes that a reply is expected, and goes right back to monitoring life support, logging the stardate, and checking on the rest of the crew — then reacts the instant the reply actually arrives. Same message sent, same reply eventually received, but only one of those officers actually gets anything else done in the meantime.

JavaScript's engine is that comms officer, and it only has one set of hands — there is no second thread quietly working in the background. When your code does something slow (a network request, a timer, reading a large file), the event loop is the mechanism that lets the engine start that slow thing, immediately move on to the next line of code, and only come back to handle the result once it's actually ready. Nothing happens in true parallel — the engine is never doing two things at the exact same instant — but by not waiting around for slow things, it stays free to do other work while they're in flight.

Historically, JavaScript handled "come back to this later" with callbacks: you'd hand a slow function another function to run once it finished. That works, but nest several slow steps that each depend on the last and you get "callback hell" — deeply indented, hard-to-follow pyramids of nested functions. Promises were introduced to represent "a value that isn't ready yet, but will be" as an actual object you can work with, and async/await — built on top of Promises — lets you write that same waiting-for-things code so it reads top-to-bottom like ordinary, synchronous code, even though it isn't.

Field Manual

The Event Loop, Intuitively

JavaScript runs your code one line at a time, on one thread — it is never doing two of your instructions simultaneously. But the browser (or Node) around it can hand off slow work — a timer, a network request, reading a file — to be handled elsewhere, and notify JavaScript the moment that work is done. The event loop is the process that keeps checking: "is the main thread free right now, and is there a finished bit of async work waiting to be handled?" If both are true, it runs that follow-up code next. This is why async code never truly interrupts synchronous code — it only ever runs once the current stack of synchronous code has completely finished.

JAVASCRIPT
console.log("1. First line");

setTimeout(function () {
  console.log("3. This runs later, after a 0ms delay");
}, 0);

console.log("2. Second line");
WHAT JUST HAPPENED Even with a 0 millisecond delay, the output is 1, 2, 3 — never 1, 3, 2. setTimeout's callback can only run once the main thread is completely free, and the main thread doesn't become free until every line of synchronous code below it (here, "2. Second line") has already run. This is the single most important intuition in this whole mission: async code always waits its turn behind whatever is currently running synchronously.

Callbacks (and Why They Fall Apart)

The original way to say "run this once that slow thing finishes" was to pass in a function — a callback. It still works today and you'll still see it. The problem shows up once you need several slow steps in sequence, each depending on the previous one's result.

JAVASCRIPT
getCrewList(function (crew) {
  getShipStatus(crew, function (status) {
    getFuelLevel(status, function (fuel) {
      console.log("Finally have everything:", fuel);
      // one more nested step and this becomes unreadable
    });
  });
});
WHAT JUST HAPPENED Each step only knows how to run "inside" the previous one, so the code marches to the right with every additional step — the infamous "callback hell" pyramid. It's not that callbacks are wrong; it's that they don't scale to multi-step sequences without becoming hard to read, hard to add error-handling to, and easy to get subtly wrong. Promises exist specifically to fix this shape.

Promises: Pending → Fulfilled / Rejected

A Promise is an object representing a value that doesn't exist yet, but will eventually — either successfully (fulfilled) or unsuccessfully (rejected). Every Promise starts in a pending state, then settles into exactly one of the other two, exactly once. .then() attaches a function to run on fulfillment; .catch() attaches one to run on rejection.

JAVASCRIPT
function contactRelay() {
  return new Promise(function (resolve, reject) {
    setTimeout(function () {
      resolve("Relay station acknowledges.");
    }, 1500);
  });
}

contactRelay()
  .then(function (message) {
    console.log(message);
  })
  .catch(function (error) {
    console.error(error);
  });

console.log("Message sent — not blocking on a reply.");
WHAT JUST HAPPENED contactRelay() returns a pending Promise immediately — the setTimeout inside it hasn't fired yet. The "Message sent…" line logs right away, before the relay ever responds, because attaching .then() doesn't pause anything; it just registers "call this function later, whenever the Promise settles." 1.5 seconds afterward, resolve(...) runs, the Promise becomes fulfilled, and then the .then() callback finally fires with that value.

async/await — the Same Thing, Readable Top-to-Bottom

Marking a function async lets you use await inside it. await pauses that function (and only that function — not the whole program) until the Promise it's waiting on settles, then hands back the fulfilled value directly, as if it were a normal synchronous return.

JAVASCRIPT
async function reachRelay() {
  console.log("Sending signal...");
  const message = await contactRelay();
  console.log(message);
  console.log("Sequence complete.");
}

reachRelay();
console.log("Not blocked — this still runs first.");
WHAT JUST HAPPENED Calling reachRelay() runs it up to the await, then immediately gives control back — which is why "Not blocked…" logs before "Relay station acknowledges." does, exactly like the .then() version above. The difference is purely how it reads: no nested callbacks, no chained .then()s — just instructions in order, even though line 3 (await contactRelay()) doesn't actually finish until 1.5 seconds after line 6 (reachRelay()) is called. async/await is "syntax sugar" over Promises — under the hood, it's still Promises doing the work.

Error Handling with try/catch

A rejected Promise that nobody handles doesn't quietly disappear — it surfaces as an "unhandled promise rejection," which is exactly the kind of bug that's easy to miss until it breaks something in production. Wrapping an await in a try/catch block catches a rejection the same way it would catch a thrown error in ordinary synchronous code.

JAVASCRIPT
async function attemptDocking() {
  try {
    const result = await riskyDock();
    console.log(result);
  } catch (err) {
    console.error("Docking failed: " + err);
  }
  console.log("Docking sequence complete either way.");
}
WHAT JUST HAPPENED If riskyDock()'s Promise rejects, control jumps straight to the catch block — the line right after await never runs — and the program keeps going afterward instead of crashing. This is the async equivalent of wrapping risky synchronous code in try/catch, and it's the standard way to handle a network call that might fail, a file that might not exist, or any other slow operation with a real chance of going wrong.
▸ DEEP DIVE: Promise.all() — waiting on several things at once

Sometimes you need several independent slow operations, and none of them depends on the others' results — checking three different systems, for example. Awaiting them one after another wastes time, since each wait wastes the time the others could have used. Promise.all([p1, p2, p3]) takes an array of Promises, starts them all essentially simultaneously, and gives you back a single Promise that fulfills once every one of them has — with an array of their results, in the same order you passed them in. If total wait time for three operations run one-by-one is 3 seconds, running them with Promise.all can bring that down to roughly however long the slowest single one takes — often close to 1 second. The catch: if any one of them rejects, the whole Promise.all immediately rejects, so it's best used when the operations don't depend on each other and you're fine treating "any failure" as "the batch failed."

⚠ COMMON MISTAKES

  • Forgetting await and getting a Promise object back instead of the actual resolved value — logging it just shows Promise {<pending>}, not your data.
  • Using await inside a function that isn't marked async — this is a syntax error, not a runtime bug.
  • Never attaching a .catch() (or a try/catch around an await) — an unhandled rejection doesn't just vanish quietly.
  • Running independent await calls one after another inside a loop when they don't depend on each other, wasting time that Promise.all could have overlapped.
  • Assuming async/await makes code run in parallel — it doesn't. It's still one Promise chain underneath, just written to read top-to-bottom.
