MISSION 9.3: USING AI AS A CODING PARTNER

Responsibly, and Well

You've been building alongside an AI assistant this whole journey — that habit deserves its own dedicated mission, formalized as a real skill, not just a background fact of how you learned. The rule that matters most: AI writes the first draft; you are the engineer who understands and owns it. Never blind-paste code you haven't read, understood, and verified — the exact same hallucination risk from Mission 7.1 applies just as much to generated code as to any other AI output.

🔴 COMMANDER LEVEL ⏱ ~40 MIN 🛠 BROWSER ONLY
1

Briefing

An AI coding assistant is a genuine force-multiplier — but it's still Mission 7.1's next-token predictor underneath, applied to code instead of prose. It can write code that looks completely plausible, is stylistically clean, and is subtly wrong: an off-by-one error, a forgotten edge case, a security hole. "It compiled" and "it looks right" are not the same as "it's correct" — the same discipline from Mission 9.1's testing and 9.2's debugging applies directly here.

2

Field Manual

Prompting for Code, Specifically

Mission 7.2's prompt engineering applies directly: be specific about the exact behavior you want, mention constraints ("no external libraries," "must handle an empty array"), and ask for one focused change at a time rather than "rewrite my whole app." A vague request like "make this better" gets a vague, hard-to-verify result.

Always Read and Verify — Never Blind-Paste

Before accepting any generated code, you should be able to explain, in your own words, what every line does and why it's correct. If you can't, that's not a reason to trust it more — it's the exact signal to slow down and actually read it, or ask the assistant to explain the specific part you don't follow.

THE RULE, PLAINLY "AI writes the first draft; you are the engineer who understands and owns it." If a bug ships, "the AI wrote it" is not a valid explanation — you accepted and shipped it, which means you're responsible for having verified it first.

Using It to Debug Alongside You, Not Instead of You

Pasting an error message and asking "what's wrong" can be genuinely useful — but Mission 9.2's method still applies. Read the AI's explanation the same way you'd read a stack trace: as a hypothesis to verify, not an automatic truth. A useful pattern: explain what you already tried and ruled out, so the assistant doesn't waste your time re-suggesting it.

When NOT to Trust AI-Generated Code Blindly

Some code deserves extra scrutiny before you ever accept it: anything touching authentication or permissions (Mission 5.3), anything handling money or user data, anything you genuinely can't verify because you don't yet understand the underlying concept well enough to check it. In those cases, slow down, ask it to explain its reasoning, and cross-check against what you've actually learned — don't accept code you can't personally vouch for.

⚠ COMMON MISTAKES

  • Accepting generated code you can't explain in your own words, just because it "looks right" and runs without errors.
  • Treating an AI's debugging explanation as automatically correct instead of a hypothesis to verify (Mission 9.2).
  • Asking for one giant rewrite instead of one focused, specific, independently-verifiable change at a time.
  • Giving less scrutiny to security- or money-sensitive generated code than to code you wrote yourself.
