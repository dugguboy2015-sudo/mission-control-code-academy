MISSION 9.4: CODE QUALITY & REFACTORING

Making It Good, Not Just Working

"It works" is the minimum bar, not the finish line. Code that works but is duplicated, unreadable, or tangled into one giant function is a real liability — every future change to it costs more time and carries more risk than it should. Refactoring is changing code's internal structure without changing what it does, and Mission 9.1's tests are exactly what makes that safe to do with confidence.

🔴 COMMANDER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

A code smell isn't a bug — the code still works — but it's a warning sign that maintaining it will get harder over time. Duplicated logic, deeply nested conditionals, a function doing five unrelated things, unexplained "magic numbers" scattered through the code: none of these crash anything today, but each one makes tomorrow's change slower and riskier.

2

Field Manual

DRY — Don't Repeat Yourself

JAVASCRIPT — BEFORE
function greetCaptain(name) {
  return "Welcome aboard, Captain " + name + ".";
}
function greetEngineer(name) {
  return "Welcome aboard, Engineer " + name + ".";
}
JAVASCRIPT — AFTER
function greetCrewMember(name, rank) {
  return "Welcome aboard, " + rank + " " + name + ".";
}
WHAT JUST HAPPENED Both original functions did the exact same thing with one word different. One shared function, parameterized, replaces both — and fixing a typo in the greeting now only needs to happen in one place instead of two (or ten).

Magic Numbers — Name Your Constants

JAVASCRIPT
// BEFORE: what does 0.15 mean here? Someone reading this has to guess.
const tip = bill * 0.15;

// AFTER: the name IS the documentation
const STANDARD_TIP_PERCENT = 0.15;
const tip = bill * STANDARD_TIP_PERCENT;
WHAT JUST HAPPENED A named constant explains itself on sight. It also means changing the standard tip rate everywhere only requires editing one line, instead of hunting down every place 0.15 was typed by hand.

One Function, One Job (Recap from Mission 6.4)

A function handling five unrelated responsibilities is hard to test, hard to reuse, and hard to change safely — exactly Mission 6.4's function-decomposition lesson, now framed as a general refactoring target. If a function's name needs the word "and" to describe what it does (validateAndSaveAndEmail), it's very likely doing too much.

Tests Make Refactoring Safe

Refactoring means changing HOW code works without changing WHAT it does. The only way to be confident you didn't accidentally change behavior is to have tests (Mission 9.1) that pass before the refactor and still pass, unchanged, after it. Refactoring without tests is really just "hoping."

⚠ COMMON MISTAKES

  • Copy-pasting similar code instead of extracting one shared, parameterized function.
  • Sprinkling unexplained numeric literals through code instead of naming them as constants.
  • Refactoring with no tests in place, unable to confirm behavior genuinely didn't change.
  • Confusing refactoring with rewriting — refactoring preserves behavior exactly; a rewrite doesn't have to.
