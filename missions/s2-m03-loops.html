MISSION 2.3: LOOPS & ITERATION

Doing Things Again, On Purpose

Conditionals taught your code to make a decision once. Real programs need to make the same decision — or repeat the same action — dozens, thousands, or millions of times, without you typing it out by hand each time. That's what a loop is: an instruction, run repeatedly, on purpose, with a precise rule for when to stop. Get the rule wrong and your program either quits too early or never quits at all. This mission is about writing that rule correctly, every time.

🟢 CADET LEVEL ⏱ ~40 MIN 🛠 BROWSER ONLY
1

Briefing

Think about a pre-launch checklist. Mission Control doesn't write "check oxygen system" once and hope it covers everything — they run one diagnostic sweep across every sensor on the ship: hull integrity, then life support, then propulsion, then comms, one after another, using the exact same check each time. That's a loop in real life: one instruction, repeated across a set of things, until there's nothing left to check.

Code loops work the same way, and they come in two basic flavors. Some loops are "do this N times" — you know the count in advance, like running exactly 5 diagnostic passes. Others are "do this until something changes" — you don't know how many times it'll take, only the condition that should eventually stop it, like draining fuel until the tank reads empty.

Every loop, no matter which flavor, needs three things to behave: a starting point, a condition that's checked before each pass, and something inside the loop that actually moves the condition closer to becoming false. Miss that third piece and the loop has no way to know it should ever stop — which is the single most common bug you'll write this mission, and the one worth understanding before you meet it in the wild.

Every loop cycles through the same four stages: check the condition, run the body if it's true, update whatever the condition depends on, then check again. The loop only stops once that check comes back false.
2

Field Manual

for Loops — When You Know the Count

A for loop packs all three required pieces — start, condition, update — into one line, in that exact order, separated by semicolons. Use it whenever you know roughly how many times you need to repeat something, or you're counting through a range.

JAVASCRIPT
for (let i = 0; i < 5; i++) {
  console.log("Diagnostic pass " + i);
}

console.log("All passes complete.");
WHAT JUST HAPPENED The three parts inside the parentheses run in a strict order every pass: let i = 0 runs once, before anything else. Then, before every pass, i < 5 is checked — if it's true, the body runs; if it's false, the loop ends immediately and skips the body. After each pass, i++ runs (shorthand for i = i + 1), and then the condition is checked again. With i starting at 0 and stopping before 5, this prints passes 0 through 4 — five total passes, not six.

while Loops — When You Don't Know the Count

A while loop only has the condition — you're responsible for setting up the starting value beforehand and updating it yourself, somewhere inside the body. Use it when the number of passes depends on something happening, not a fixed count.

JAVASCRIPT
let fuel = 100;

while (fuel > 0) {
  fuel -= 20;
  console.log("Fuel remaining: " + fuel);
}

console.log("Tank empty.");
WHAT JUST HAPPENED fuel starts at 100, set up before the loop. The condition fuel > 0 is checked before every pass, the body drains 20 fuel and logs it, and eventually fuel hits 0 — the condition becomes false, and the loop stops on its own. Notice that the update (fuel -= 20) lives inside the body here, not baked into the loop's header like a for loop. That freedom is exactly what makes while loops flexible — and exactly what makes them easy to get wrong.
▸ DEEP DIVE: The infinite-loop trap

Here's a loop that looks almost identical to the fuel example, with one small thing missing:

JAVASCRIPT — DO NOT RUN
let power = 100;

while (power > 0) {
  console.log("Power: " + power);
  // forgot to update power here!
}

The condition is power > 0, and power starts at 100 — but nothing inside the body ever changes power. The condition is checked, it's true, the body runs, the condition is checked again... and it's still true, forever. This is an infinite loop: the browser tab freezes trying to keep up, and eventually crashes or has to be force-closed. It's one of the few bugs in JavaScript that doesn't politely show up as an error message — it just hangs.

The fix is always the same: find every variable the condition depends on, and confirm the body actually changes it — on every pass, not just inside an if that might not run. The same trap catches for loops too, if you accidentally reset the counter inside the body (like i = 0; hiding partway through) instead of only using the loop's own increment.

for...of — Iterating Arrays & Strings

Counting with i and reaching into an array with arr[i] works, but it's easy to get the bounds wrong. for...of skips the index entirely and just hands you each value in order — it works on arrays, strings, and a few other "iterable" collections.

JAVASCRIPT
const crew = ["Nova", "Kip", "Zed"];

for (const member of crew) {
  console.log(member + " reporting for duty.");
}

const callsign = "ORION";
for (const letter of callsign) {
  console.log(letter);
}
WHAT JUST HAPPENED On each pass, member is automatically set to the next value in crew — no index, no bounds to get wrong, no i++ to remember. It stops on its own once it's handed you every item. Strings work the same way because a string is really just an ordered sequence of characters — the loop hands you one letter per pass.

break & continue — Changing the Loop's Path

Sometimes you don't want a loop to run to completion exactly as written. break exits the loop immediately, skipping every remaining pass. continue skips the rest of the current pass only and jumps straight to the next one.

JAVASCRIPT
for (let i = 0; i < 10; i++) {
  if (i === 3) continue; // skip this one pass
  if (i === 6) break;    // stop the loop entirely
  console.log(i);
}
WHAT JUST HAPPENED This logs 0, 1, 2, 4, 5 — then stops. continue on i === 3 jumps to the increment without logging 3, but the loop keeps going. break on i === 6 exits the loop entirely — the console never even sees 6, 7, 8, or 9. Both keep the increment running normally (i++ still happens on a continue); break is the only one that shuts the whole loop down.

Debrief / Cheat Sheet

for (let i=0; i<n; i++) {}Loop a known number of times
while (condition) {}Loop until a condition becomes false
for (const x of arr) {}Loop over each value in an array or string
breakExit the loop immediately, skipping what's left
continueSkip the rest of this pass, keep looping
i++ / i--Shorthand for increasing/decreasing by 1
arr.lengthCommon upper bound when looping an array by index
condition never falseThe infinite-loop bug — always verify the update runs

⚠ COMMON MISTAKES

  • Forgetting to update the loop variable (or a condition that can never become false) — the classic infinite loop, and the one that freezes the tab.
  • Off-by-one errors: using i <= arr.length instead of i < arr.length, which reads one slot past the end of the array.
  • Reaching for for...in to loop over an array — it was built for object keys, not array values, and can hand back indexes as strings or unexpected extra properties. Use for...of for arrays instead.
  • Mixing up break and continue and being surprised the loop either stopped completely or kept running when you expected the opposite.
  • Declaring the loop counter with var instead of let inside a for loop, which can cause confusing bugs if the loop variable is used later in a callback.

Quick check — what's wrong with for (let i = 0; i < 5; i++) { i = 0; }?
