MISSION 3.1: GIT & GITHUB FUNDAMENTALS

Splitting the Timeline — Version Control for Real Engineers

Every serious engineering project needs a flight recorder — a way to save checkpoints, branch off to try risky experiments, and merge good ideas back into the main mission without losing anything. That's Git. Today you install the tool every professional software team on Earth (and presumably beyond) uses every single day.

🟡 OFFICER LEVEL ⏱ ~50 MIN 🛠 TERMINAL REQUIRED
1

Briefing

Picture your codebase as a spacecraft's mission log. Every time you make real progress — a working feature, a bug fix, a new module wired in — you drop a checkpoint buoy into the timeline. That buoy records the exact state of every file at that moment, forever. If a future change breaks something, you don't panic: you fly back to the last good buoy and pick a different path forward.

Git is the system that manages these buoys. Each checkpoint is called a commit. The chain of commits is your project's history. And because software is rarely built by one person sitting alone, Git also lets you branch — split off a parallel timeline to try something experimental (a new feature, a risky refactor) without touching the main timeline at all. If the experiment works, you merge it back in. If it doesn't, you just... don't. The main timeline never knew it happened.

This is the single most important habit separating hobby coders from engineers: never work without a safety net you fully control.

The main timeline keeps advancing while a branch splits off to build a feature safely, then merges back in at "merge."

Field Manual

Initializing the Ship's Log

Every Git project starts by turning an ordinary folder into a repository — a folder Git is now watching for changes. This creates a hidden .git directory that stores the entire history.

BASH
# Run this inside your project folder
git init

# Check that Git is now watching this folder
git status
WHAT JUST HAPPENED Git created a hidden .git folder that will hold every commit you ever make in this project. git status is your dashboard — it always tells you the current state: what's changed, what's staged, what branch you're on.

The Staging Area — Choosing What Goes in the Log

Git doesn't save your whole project every time. It saves a snapshot of exactly the files you choose. That selection step is called staging. Think of it as loading specific cargo onto the checkpoint buoy before you drop it — you decide what's important enough to record right now.

BASH
# Stage a specific file
git add mission.py

# Or stage everything that's changed
git add .

# Commit the staged snapshot with a clear message
git commit -m "Add thruster control script"
WHAT JUST HAPPENED git add moves files into the staging area (the "about to be recorded" zone). git commit permanently seals that staged snapshot into the project history with a message explaining why. Good commit messages are a real engineering skill — future-you will read them at 2am trying to figure out what past-you broke.
▸ DEEP DIVE: Why not just save everything automatically?

Because not every change is worth a permanent checkpoint. You might have half-finished experiments, temporary debug prints, or files you never want tracked at all (like passwords). Staging gives you full control over what becomes "official" history. You'll also use a .gitignore file to tell Git to never even look at certain files or folders (like node_modules/ or .env).

Branching — Opening a Parallel Timeline

Branches let you build something new without risking the working main version. This is the feature that makes Git actually powerful, not just a backup tool.

BASH
# Create a new branch
git branch feature/laser-controls

# Switch to it
git checkout feature/laser-controls

# Or do both in one command (shortcut)
git checkout -b feature/laser-controls
WHAT JUST HAPPENED You now have two timelines: main and feature/laser-controls, currently pointing at the same commit. Any commits you make now happen only on the branch you're standing on. main stays exactly as it was until you decide to merge.

Merging — Bringing the Timeline Back Together

Once your branch's work is solid, you bring it back into main. Git tries to combine the histories automatically. Most of the time it just works. Sometimes both timelines changed the same line of the same file — that's a merge conflict, and Git asks you to decide which version wins.

BASH
# Switch back to the timeline you want to merge INTO
git checkout main

# Pull the branch's commits into main
git merge feature/laser-controls
WHAT JUST HAPPENED Git replayed the branch's commits onto main (or created a special "merge commit" joining both histories). Your feature is now part of the main timeline, and the branch can be deleted — its work has already been absorbed.
▸ DEEP DIVE: What does a merge conflict actually look like?

Git edits the file directly and inserts conflict markers so you can see both versions and choose:

<<<<<<< HEAD
thrust_power = 100
=======
thrust_power = 120
>>>>>>> feature/laser-controls

You delete the markers, keep (or blend) the code you actually want, then git add the file and git commit to finish the merge. It's not scary — it's just Git being honest that it needs a human decision.

Remotes — Syncing with Mission Control (GitHub)

So far everything has lived only on your machine. A remote is a copy of the repository hosted elsewhere — usually GitHub — so you can back up your work, sync across devices, and collaborate with other engineers.

BASH
# Connect your local repo to a GitHub repo
git remote add origin https://github.com/yourname/your-repo.git

# Send your commits up to GitHub
git push -u origin main

# Pull down commits made elsewhere (e.g. by a teammate)
git pull origin main
WHAT JUST HAPPENED origin is just a nickname for "the remote repository." push uploads your local commits; pull downloads and merges commits you don't have yet. The -u flag remembers this pairing so future pushes are just git push.

If git checkout main refuses because of "uncommitted changes," it means you forgot to commit on the experiment branch first. Git is protecting you from silently losing work — that's a feature, not a bug.

Debrief / Cheat Sheet

git initStart tracking a folder
git statusShow current state
git add <file>Stage a change
git commit -m "msg"Save a checkpoint
git branch <name>Create a branch
git checkout <name>Switch branches
git checkout -b <name>Create + switch in one step
git merge <name>Combine a branch into current one
git logView commit history
git pushUpload commits to remote
git pullDownload commits from remote
git clone <url>Copy a remote repo locally

⚠ COMMON MISTAKES

  • Committing without staging first (git commit only saves what's staged, not everything).
  • Vague commit messages like "fix" or "stuff" — you will regret this in three weeks.
  • Working directly on main for risky experiments instead of branching first.
  • Forgetting to commit before switching branches, then wondering where the work went.
  • Panicking at a merge conflict instead of reading what Git is actually telling you.
