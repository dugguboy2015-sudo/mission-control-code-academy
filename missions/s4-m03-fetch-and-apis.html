MISSION 4.3: FETCH, JSON & PUBLIC APIS

Talking to Other Ships

Mission 0.2 taught you what happens when a browser asks a server for a page: a request goes out, a response comes back, wrapped in a status code. That was the theory. This is the mission where you actually make that conversation happen from your own code — reaching across the internet, in real time, to a server you don't control, and pulling back real data to put on your own page. This is how every weather app, every game leaderboard, and every dashboard on Earth actually works under the hood.

🟡 OFFICER LEVEL ⏱ ~55 MIN 🛠 INTERNET REQUIRED
1

Briefing

Back in Mission 0.2 you learned that a webpage is really the result of an HTTP conversation — a client sends a request, a server sends back a response, and a status code tells you what happened. Everything in that mission was something the browser did automatically the moment you typed a URL. Today you take the wheel yourself. JavaScript has a built-in function, fetch(), that lets your own code start that exact same conversation, on demand, while the page is already running — no reload, no address bar involved.

An API (Application Programming Interface) is just a server that's designed to be talked to by code instead of by a human clicking around a page. Instead of HTML meant for a browser to display, it sends back JSON — a compact, structured text format built entirely out of the same building blocks JavaScript already uses: objects, arrays, strings, numbers, booleans. Before you write a line of fetch code, look at the whole trip a request takes, because every gotcha in this mission comes from misunderstanding one leg of this journey.

Three legs, every time: your code sends a request across the internet, the server sends structured JSON back, and only then does your own code turn that data into something visible.

Notice that nothing in that diagram is instant. Steps 1 and 2 involve an actual round trip across real infrastructure — sometimes a few milliseconds, sometimes a full second or more if the connection is slow. JavaScript can't just pause and wait, frozen, for that to finish (that would lock up the whole page). Instead, fetch() hands you back a placeholder for a value that doesn't exist yet, and lets the rest of your code keep running. That placeholder is called a Promise, and understanding exactly how to unwrap one is 80% of this mission.

2

Field Manual

JSON — The Data Format Everyone Speaks

JSON (JavaScript Object Notation) is plain text, built from the same shapes JavaScript already has: curly braces for objects, square brackets for arrays, quoted strings, plain numbers, true/false, and null. It's the universal language APIs use to send structured data, because nearly every programming language on Earth can read and write it.

JSON — WHAT PIKACHU'S DATA LOOKS LIKE (SIMPLIFIED)
{
  "name": "pikachu",
  "height": 4,
  "weight": 60,
  "sprites": {
    "front_default": "https://.../pikachu.png"
  }
}

Two built-in functions convert between JSON text and real JavaScript values: JSON.parse(text) turns a JSON string into a live object you can use (data.name, data.sprites.front_default), and JSON.stringify(obj) does the reverse — turning a JavaScript value into JSON text, which is what you'd do to send data to an API.

WHAT JUST HAPPENED You will almost never call JSON.parse() yourself when using fetch() — as you're about to see, the Response object has a built-in .json() method that calls JSON.parse() for you. It's worth knowing it exists underneath, because you'll meet raw JSON.parse/JSON.stringify constantly once you start using localStorage in Mission 4.4.

fetch() Returns a Promise

Calling fetch(url) immediately sends the HTTP request and immediately hands you back a Promise — not the data itself, but an object representing "a value that will exist once the request finishes." A Promise can be pending, fulfilled (it succeeded, with a value), or rejected (it failed, with a reason). The cleanest way to wait for a Promise to settle is the await keyword, used inside a function marked async.

JAVASCRIPT
async function loadPikachu() {
  const response = await fetch("https://pokeapi.co/api/v2/pokemon/pikachu");
  console.log(response); // a Response object, NOT the data yet
}

loadPikachu();
WHAT JUST HAPPENED await fetch(...) pauses this function (only this function — the rest of the page keeps running) until the HTTP round trip finishes, then unwraps the Promise into a Response object. That Response is a wrapper around the reply: it carries the status code, the headers, and a raw, not-yet-read body. It is not the JSON data you actually want — that's the next step, and skipping it is the single most common mistake in this whole mission.

The Double-Await: Response → .json()

Here's the part that trips almost everyone up the first time: getting the actual data takes two asynchronous steps, not one. fetch() resolves to a Response. Calling .json() on that Response reads and parses its body — and .json() itself also returns a Promise, because reading the body can take time too. So you need a second await.

JAVASCRIPT
async function loadPikachu() {
  const response = await fetch("https://pokeapi.co/api/v2/pokemon/pikachu");
  // response is a Response object — headers + status, body still unread

  const data = await response.json();
  // data is now the REAL parsed object: data.name, data.height, ...

  console.log(data.name, data.height, data.weight);
}
WHAT JUST HAPPENED — TRACED STEP BY STEP (1) fetch(url) returns Promise #1. (2) await unwraps Promise #1 into a Response object — call it the "envelope." (3) response.json() opens the envelope and starts parsing the JSON text inside it, returning Promise #2. (4) The second await unwraps Promise #2 into the actual data — the "letter" inside the envelope. Two Promises, two awaits. If you only await once and try to read response.name directly, you'll get undefined — the Response object doesn't have a name property; the data inside it does, but you never opened the envelope.

Rendering Fetched Data Into the DOM

Once you have the real data, putting it on the page is exactly the DOM work you already know from Sector 2 — find an element, then set its content. The only new part is that this now happens after a network round trip, so the page usually starts in a "loading" state and updates once the data arrives.

JAVASCRIPT
async function loadPikachu() {
  const display = document.querySelector("#shipDisplay");
  display.textContent = "Loading...";

  const response = await fetch("https://pokeapi.co/api/v2/pokemon/pikachu");
  const data = await response.json();

  display.innerHTML = `
    <strong>${data.name}</strong> — height ${data.height}, weight ${data.weight}
    <img src="${data.sprites.front_default}" alt="${data.name}">
  `;
}
WHAT JUST HAPPENED Setting a loading message before the await line matters — the cadet sees immediate feedback instead of a frozen blank screen while the request is in flight. The template literal (backticks, ${...}) makes it easy to weave live values straight into HTML you're about to insert with innerHTML. Note the field is literally called sprites.front_default in the real PokeAPI response — it's a URL string, and the browser fetches and displays that image the moment it hits an <img> tag, no extra fetch call needed on your part.

Handling Errors: response.ok and Network Failures

Here's the second classic gotcha, and it's a big one: fetch()'s Promise does not reject just because the server said "no." A 404 Not Found, a 500 Internal Server Error — fetch() treats all of these as a successful HTTP conversation, because technically it was: the request went out, and a response came back. The Promise only rejects for a true network-level failure — no internet connection, DNS couldn't resolve the domain, the connection was refused entirely.

That means checking whether the request "succeeded" from your app's point of view is your job, using response.ok (true only for status codes 200–299) or response.status directly.

JAVASCRIPT
async function loadPokemon(name) {
  const display = document.querySelector("#shipDisplay");
  display.textContent = "Loading " + name + "...";

  try {
    const response = await fetch("https://pokeapi.co/api/v2/pokemon/" + name);

    if (!response.ok) {
      display.textContent = "No Pokémon named \"" + name + "\" (status " + response.status + ")";
      return;
    }

    const data = await response.json();
    display.textContent = data.name + " — height " + data.height;
  } catch (err) {
    // only reaches here on a TRUE network failure
    display.textContent = "Network error: " + err.message;
  }
}
WHAT JUST HAPPENED Notice there are two separate failure paths, and they are not the same thing: the if (!response.ok) branch handles a server that answered but said "not found" (a 404 for a Pokémon name that doesn't exist), while the catch block only ever runs if the request couldn't complete at all (offline, DNS failure, the server is completely unreachable). Mixing these up — expecting a 404 to land in catch — is exactly the bug this section exists to prevent.
▸ DEEP DIVE: Why doesn't fetch() just reject on a 404?

From the network's point of view, a 404 response is a complete, well-formed, successful HTTP exchange — the server received your request and sent back a valid answer; it just happens to be "I don't have that." fetch()'s Promise is only about whether the network operation succeeded, not whether you're happy with the result. This is a deliberate design choice (older tools like jQuery's $.ajax did auto-reject on bad status codes, and it caused constant confusion about what counted as an "error"). The tradeoff: you must always check response.ok yourself, every single time, or a 404/500 will silently sail past your error handling and crash later when you try to read a field that doesn't exist on an error payload.

Debrief / Cheat Sheet

fetch(url)Sends an HTTP request, returns a Promise
await fetch(url)Pauses until that Promise resolves to a Response object
response.json()Parses the body — and ALSO returns a Promise
await response.json()Pauses again, unwraps the actual parsed data
response.okTrue only for status codes 200–299
response.statusThe raw numeric status code
JSON.parse() / .stringify()Text ↔ JS values, manually (fetch's .json() does this for you)
async functionA function allowed to use await inside it
try / catchCatches a true network failure, NOT a 404

⚠ COMMON MISTAKES

  • Forgetting the second await/.then() for .json() and trying to read data straight off the raw Response object.
  • Assuming fetch() throws or rejects on a 404 — it doesn't; you must check response.ok yourself.
  • Using await inside a function that isn't declared async — this is a syntax error, not a runtime one.
  • Never handling the case where the network itself fails (offline, DNS down) — without a catch or a .catch(), that Promise rejection crashes silently.
  • Building the URL with a typo'd path (like forgetting the /v2/) and assuming the API is broken instead of checking the actual status code that came back.
