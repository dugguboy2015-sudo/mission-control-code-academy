Briefing

Ladder Level L3 (Mission 5.7) asked for real data, real auth, and provable free-tier headroom. L4 keeps every one of those requirements and adds the ones specific to AI: AI calls go through a proxy — never the provider directly from the client; guardrails on both input and output; cost estimated and tracked, not guessed at after the fact; and a graceful fallback when the model fails or is slow. None of these are new skills today — they're the exact four things Missions 7.3, 7.7, and 7.8 already taught you, now required together, in one real app, at the same time.

The L4 stack: your proxy still holds the key and runs guardrails (7.3, 7.7); an AI Gateway sits in front of the actual provider call adding caching, cost tracking, and multi-provider fallback almost for free.

Field Manual

One genuinely new piece today — everything else is synthesis of Missions 7.3-7.9.

AI Gateway — a Proxy in Front of Your Proxy's Provider Call

Cloudflare (and other providers) offer an AI Gateway: a service that sits between your Worker and the actual LLM provider. Instead of your Worker calling api.openai.com directly, it calls your AI Gateway's URL, which forwards the request — and adds, with almost no extra code, things you'd otherwise have to build yourself: automatic caching of identical requests (so repeat questions don't cost tokens twice), built-in cost and usage logging per request, and configurable fallback across multiple providers if your primary one is down.

WHY THIS MATTERS AT L4 Mission 7.8 taught you to hand-write a callWithFallback() function. An AI Gateway gives you a production-grade version of that same idea — plus caching and cost visibility — configured once, instead of hand-rolled in every project. Your Worker's code barely changes: the URL it calls points at the Gateway instead of the provider directly.

The L4 Checklist, As Code You Already Know

  • Proxy, not direct calls — Mission 7.3's architecture: the client never holds a provider key.
  • Guardrails, both directions — Mission 7.7's checkInputGuardrail() / checkOutputGuardrail(), now mandatory on every request.
  • Cost estimated AND tracked — Mission 7.8's math, but running live as the app is actually used, not just estimated once up front.
  • Graceful fallback — Mission 7.8's callWithFallback() pattern, so one provider hiccup doesn't take down the whole feature.

⚠ COMMON MISTAKES

  • Adding cost to the running total even for a request the guardrail rejected — inflates your tracked cost above what was actually spent.
  • Building guardrails and fallback separately without testing them together — a rejected input should never even reach the fallback logic.
  • Treating cost estimation as a one-time calculation done before building, instead of also tracking real usage as the app runs.
  • Skipping the proxy architecture "because it's just a school project" — the habit matters more than any single project's actual risk.
