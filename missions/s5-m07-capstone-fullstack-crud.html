Briefing

A real, live web application is really three cooperating systems, each with one job. Cloudflare serves your static files — HTML, CSS, JS — fast, from servers positioned close to every visitor worldwide. Supabase handles anything that needs to be remembered or protected: your database and your login system. GitHub is the source of truth in the middle — the single place both your code and your deployment history live, and the trigger that tells Cloudflare "something changed, rebuild and redeploy."

Two independent services, one experience: Cloudflare never sees your data, and Supabase never serves your HTML.

Getting a change live involves a second pipeline, entirely separate from what a visitor experiences: your own workflow for shipping updates.

This is the same shape as Mission 06's GitHub Pages pipeline — Cloudflare is a different provider, but the pattern (push → auto-build → live) is universal.

Field Manual

Building Real Auth: Sign Up, Sign In, Sign Out

You saw supabase-js read and write data in Mission 07. Authentication uses the same client, with its own auth object.

JAVASCRIPT
const supabase = createClient(SUPABASE_URL, SUPABASE_ANON_KEY);

// Sign up a new cadet
const { data, error } = await supabase.auth.signUp({
  email: 'cadet@example.com',
  password: 'secure-password'
});

// Sign in an existing cadet
await supabase.auth.signInWithPassword({
  email: 'cadet@example.com',
  password: 'secure-password'
});

// Sign out
await supabase.auth.signOut();
WHAT JUST HAPPENED Supabase handles password hashing, storage, and issuing a secure session token automatically — you never touch a raw password after this call. error is always worth checking: a failed sign-in due to a wrong password comes back here rather than throwing, so silently ignoring it means broken logins fail invisibly.

Reacting to Auth State — Locking and Unlocking the UI

A real app needs to know, at every moment, whether someone is logged in — and update the page accordingly without a reload. onAuthStateChange is a listener, similar in spirit to Firebase's onSnapshot from Mission 08: it fires immediately with the current state, then again automatically every time that state changes.

JAVASCRIPT
supabase.auth.onAuthStateChange((event, session) => {
  const dashboard = document.querySelector("#dashboard");
  const loginForm = document.querySelector("#loginForm");

  if (session) {
    dashboard.style.display = "block";
    loginForm.style.display = "none";
  } else {
    dashboard.style.display = "none";
    loginForm.style.display = "block";
  }
});
WHAT JUST HAPPENED session is null when nobody is logged in and an object (containing the user's info and token) when they are. This single listener replaces having to manually re-check login state after every sign-in, sign-out, or page load — it stays live the entire time the page is open.
SECURITY NOTE Hiding the dashboard with CSS only protects what a visitor sees — it doesn't protect the actual data. Anyone who's logged in could still directly ask Supabase for another user's data unless you also set up Row Level Security policies on the database side, restricting each row to its own owner. The frontend check is for user experience; the database-side check is what's actually enforcing security.

Environment Variables & Keeping Secrets Out of Git

Not every key is safe to publish. Supabase's anon key is designed to be public — it's restricted by the permission rules you configure. Its service role key, by contrast, bypasses all restrictions entirely and must never appear in frontend code or a public GitHub repo.

BASH
# .gitignore
.env

# .env (never committed)
SUPABASE_URL=https://yourproject.supabase.co
SUPABASE_ANON_KEY=your-public-anon-key
WHAT JUST HAPPENED A .gitignore file tells Git to never track certain files — listing .env there means it never gets committed or pushed to GitHub, even accidentally. For a real deployed site, Cloudflare Pages has its own separate "Environment Variables" settings page where you re-enter these values directly in the dashboard, so your live site has them without them ever touching your repository.
▸ DEEP DIVE: If the anon key is public anyway, why hide it at all?

The anon key genuinely is meant to end up visible in your shipped JavaScript — that's normal and expected for Supabase. Using an environment variable is still good practice because it keeps your project's specific configuration separate from your code, makes it trivial to point the same code at a different project (like a separate testing database), and builds the habit that will matter enormously the moment a real secret (like a service role key) enters the picture.

Deploying to Cloudflare Pages

With your code pushed to GitHub and your Supabase keys ready, connecting Cloudflare takes just a few screens.

WHERE TO CLICK In the Cloudflare dashboard, go to Workers & Pages → Create → Pages → Connect to Git, then choose your GitHub repository. Since this is a plain HTML/CSS/JS site with no build step, leave "Build command" empty and set "Build output directory" to the root (/). Before deploying, open Settings → Environment Variables and add your SUPABASE_URL and SUPABASE_ANON_KEY exactly as they appear in your local .env. Click Save and Deploy — Cloudflare builds your first version and hands you a live *.pages.dev URL immediately.
WHAT JUST HAPPENED Cloudflare is now watching the same GitHub repository the way GitHub Pages did in Mission 06 — every future git push to your main branch triggers a fresh automatic build and deploy, typically live within seconds, distributed across Cloudflare's global network for fast loading everywhere.

⚠ COMMON MISTAKES

  • Committing a .env file (or any secret key) to a public GitHub repository — treat this as a genuine emergency if it happens: rotate the key immediately.
  • Hiding the dashboard with CSS and assuming that alone makes the data secure — it doesn't, without Row Level Security on the database side.
  • Forgetting to add environment variables inside Cloudflare's own dashboard, so the live site can't find keys that exist only on your laptop.
  • Not checking the error object returned from auth calls, so failed logins fail silently instead of showing the user what went wrong.
  • Testing only on your own logged-in laptop and never confirming the flow actually works for a brand-new visitor with no prior session.
