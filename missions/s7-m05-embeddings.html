MISSION 7.5: EMBEDDINGS & SEMANTIC SEARCH

Meaning as Numbers

Mission 5.2's SQL WHERE clause matches exact or partial text — searching "puppy training" finds rows containing those exact words, and nothing else, even a document titled "raising a young dog" that means almost the same thing. Embeddings solve a completely different problem: converting text into a list of numbers that captures its meaning, so that texts with similar meaning end up with similar numbers — searchable by closeness, not exact wording.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY

Briefing

An embedding is a fixed-length list of numbers (a vector) that a specialized model produces for a piece of text — real ones are typically hundreds or thousands of numbers long. The specific numbers don't mean anything you could read directly, but their arrangement does: texts about similar things get vectors that sit close together, and texts about unrelated things get vectors far apart. This mission builds the whole pipeline — embed, compare, rank — using a hand-built toy model small enough to see the mechanism directly.

"dog" and "cat" cluster together; "rocket" and "planet" cluster together, far from the animals. Real embeddings work the same way, just in far more dimensions than can be drawn.

Field Manual

Cosine Similarity — Measuring "How Close"

To compare two vectors, you need a number that says how similar they are. The standard tool is cosine similarity: it measures the angle between two vectors, ignoring their length, giving a score from -1 (opposite meaning) to 1 (identical direction, i.e. near-identical meaning). 0 means unrelated.

JAVASCRIPT
function cosineSimilarity(a, b) {
  let dot = 0, normA = 0, normB = 0;
  for (let i = 0; i < a.length; i++) {
    dot += a[i] * b[i];
    normA += a[i] * a[i];
    normB += b[i] * b[i];
  }
  return dot / (Math.sqrt(normA) * Math.sqrt(normB));
}
WHAT JUST HAPPENED dot is the vectors' dot product — multiply matching positions together and sum them. Dividing by the product of both vectors' lengths (their "norm") is what makes this measure the direction only, not the magnitude — two vectors pointing the same way score close to 1 even if one is much "longer" than the other.

Getting Real Embeddings (Through Your Own Proxy)

Just like Mission 7.3's chat calls, real embedding API calls need a key — so the exact same rule applies: never call the embeddings endpoint directly from client code. Route it through your own proxy.

JAVASCRIPT (client, calling YOUR proxy)
async function embedText(text) {
  const response = await fetch('https://your-worker.workers.dev/embed', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ text }),
  });
  const data = await response.json();
  return data.embedding; // e.g. an array of 1536 numbers
}
WHAT JUST HAPPENED This looks identical to any other proxy call from Mission 7.3 — because architecturally, it is one. The only difference from a chat call is what comes back: not a reply, but a plain array of numbers you can store and compare later.

Semantic Search — the Full Algorithm

Combine everything above into the algorithm that powers "search by meaning": embed every document once, ahead of time; when a search happens, embed only the query; compute cosine similarity between the query's vector and every stored document vector; sort by that score and return the top matches.

JAVASCRIPT
function semanticSearch(query, documents, embedFn, topN) {
  const queryVector = embedFn(query);

  const scored = documents.map((doc) => ({
    text: doc,
    score: cosineSimilarity(queryVector, embedFn(doc)),
  }));

  return scored.sort((a, b) => b.score - a.score).slice(0, topN);
}
WHAT JUST HAPPENED In a real system, you'd embed all your documents once and store the vectors — re-embedding them on every single search would be slow and wasteful. Only the query gets embedded fresh, every time. Mission 7.6 (RAG) builds directly on top of this exact function.

⚠ COMMON MISTAKES

  • Re-embedding every document on every single search instead of embedding them once and storing the vectors.
  • Comparing vectors of different lengths — cosine similarity requires both vectors to have the same number of dimensions.
  • Calling a real embeddings API directly from client code with the key exposed — the exact same rule from Mission 7.3 applies here too.
  • Expecting a similarity score of exactly 1 for "close enough" matches — in practice, even very similar real texts often score around 0.8-0.9, not a perfect 1.0.
