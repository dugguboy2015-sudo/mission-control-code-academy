MISSION 2.7: THE DOM IN DEPTH

Finding & Changing the Page — Querying, Building, and Tearing Down Live Elements

Mission 2.1 taught you to flip switches that already existed on the panel — grab an element, change its text, toggle a class. That's most of what a beginner ever does to the DOM. But real pages don't ship with every element pre-built: chat apps create a new message bubble per message, to-do lists create a new row per task, dashboards remove cards when data disappears. This mission is about the DOM as something you construct, not just adjust — finding many elements at once, building brand-new ones from nothing, wiring them in, and cleanly pulling them back out.

🟡 OFFICER LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Think of the DOM as the control panel of a ship that's already flying. In Mission 2.1 you learned to operate switches that were bolted onto the panel before launch — querySelector found one, and you flipped it. That covers a lot of real work, but it has a hard limit: it only touches what's already there.

Real interfaces grow and shrink while they run. A crew roster starts empty and fills up as people check in. A search results page throws away yesterday's list and builds a new one from this second's data. None of those elements existed when the page first loaded — the JavaScript itself had to manufacture them, install them into the tree, and later rip out the ones that no longer belong. That's a fundamentally different skill from flipping an existing switch: it's building new hardware while the ship is running, then decommissioning it cleanly when it's no longer needed.

This mission also finishes a piece Mission 2.1 only sampled: querySelector finds exactly one match and stops looking. Most real tasks — "highlight every overdue task," "disable every button while loading" — mean operating on all the matches at once. That's querySelectorAll, and it comes back with a whole batch of elements you loop over rather than a single one you use directly.

The parent <ul> doesn't change — a brand-new <li> is manufactured in memory with createElement, then wired into the tree as a new child with appendChild. Nothing appears on screen until that second step.
2

Field Manual

querySelectorAll & Iterating Many Elements

querySelector stops at the first match. querySelectorAll keeps going and hands back every match, bundled into a NodeList — an array-like collection you loop over, even if it only found one element, or none at all.

JAVASCRIPT
const allBadges = document.querySelectorAll(".crew-card");

console.log(allBadges.length); // e.g. 4, even if only one class matches

allBadges.forEach(function (badge) {
  badge.classList.add("checked-in");
});
WHAT JUST HAPPENED querySelectorAll always returns a NodeList — never a single element, never null. If zero elements match, you get back an empty NodeList (length 0), not an error. Modern NodeLists support .forEach() directly, which is the standard way to run the same logic against every match. It's also a static snapshot of what matched at the moment you called it — elements added to the page afterward won't magically appear in that same list.

Creating & Inserting Elements

document.createElement(tag) manufactures a brand-new element — entirely in memory, completely detached from the page. It doesn't appear anywhere until you explicitly insert it somewhere with appendChild, the shorthand .append(), .prepend(), or insertBefore.

JAVASCRIPT
const list = document.querySelector("#crewList");

const rookie = document.createElement("li");
rookie.textContent = "Talia";

list.appendChild(rookie);          // added at the end

const medic = document.createElement("li");
medic.textContent = "Rho (Med Officer)";
list.prepend(medic);               // added at the front, ahead of everyone
WHAT JUST HAPPENED createElement only builds the element — it's like machining a part on a bench, not yet bolted to anything. appendChild/.append() installs it as the last child of the container; .prepend() installs it as the first. Need it somewhere in the middle? parent.insertBefore(newNode, referenceNode) drops newNode immediately before a sibling you already have a reference to.

Removing Elements

Pulling an element out of the page is a one-liner: call .remove() directly on the element you no longer want.

JAVASCRIPT
const list = document.querySelector("#crewList");
const members = list.querySelectorAll("li");

members[0].remove(); // the first crew member is gone from the page
WHAT JUST HAPPENED .remove() detaches the element from the tree — it disappears from the page immediately. Older code you'll sometimes still see does the same job via the parent: list.removeChild(members[0]). Either way, removing an element doesn't erase your JavaScript variable pointing at it; that variable just now refers to an element that isn't on the page anymore, unless you reinsert it somewhere.

Attributes & textContent vs. innerHTML

Attributes are the name/value pairs written inside a tag, like data-rank="ensign". Read and write them with getAttribute and setAttribute — useful for custom data that doesn't need its own CSS class or JS variable. Separately, when it comes to setting an element's contents, textContent and innerHTML look similar but behave very differently.

JAVASCRIPT
const badge = document.querySelector("#crewList li");

badge.setAttribute("data-rank", "ensign");
console.log(badge.getAttribute("data-rank")); // "ensign"

badge.textContent = "Nova <ensign>";      // shown as literal text, exactly as typed
badge.innerHTML = "Nova <strong>Ensign</strong>"; // parsed as real HTML — <strong> actually bolds it
WHAT JUST HAPPENED textContent treats whatever you assign as plain text — even if it contains angle brackets, they're displayed literally, never turned into real tags. innerHTML instead parses the string as HTML and builds real elements from it, which is exactly why it can insert a whole chunk of structured markup in a single line.
▸ DEEP DIVE: why professional code is careful with innerHTML

If a string you hand to innerHTML came from somewhere you don't fully control — a text box someone typed into, a URL, another user's message — and that string happens to contain something like <img src=x onerror="doSomethingBad()">, the browser will parse it as real HTML and actually run it. That's called Cross-Site Scripting (XSS), and it's one of the most common real-world web vulnerabilities — attackers use it to steal login sessions or quietly run their own code inside someone else's page.

The fix isn't complicated: for anything that includes user-typed or otherwise dynamic content, prefer textContent, or build the structure yourself with createElement and set text on the pieces individually. Save innerHTML for content you wrote yourself, hardcoded, with nothing plugged in from outside. It's not that innerHTML is broken — it's that it will faithfully run whatever HTML you give it, so you have to be the one making sure that HTML is trustworthy.

⚠ COMMON MISTAKES

  • Calling array methods like .map() or .filter() directly on a NodeList — it only ships with .forEach() built in; convert with Array.from(list) first if you need the rest.
  • Forgetting that querySelectorAll returns a collection, not a single element, and trying to read .textContent straight off it instead of looping over the matches.
  • Appending a freshly created element to the wrong container — easy to do when two variables have similar names, and the element silently lands somewhere you didn't intend.
  • Calling querySelector/getElementById before the target element actually exists in the page yet (script running too early, or a typo in the selector).
  • Using innerHTML to insert anything that includes user-typed or otherwise untrusted text, opening the door to XSS.
