MISSION 7.9: CONTEXT ENGINEERING

Managing the Context Window

Mission 7.7's conversation history only grows. Mission 7.6's RAG pipeline adds retrieved text on top. Every one of those pieces, plus the system prompt, plus the current question, all count toward one shared, finite limit: the context window — the total amount the model can "see" in a single request. This mission is about deliberately managing what fits inside that limited space, because eventually, without a plan, something has to get cut.

Briefing

Every model has a maximum context window, measured in tokens (Mission 7.1) — and everything you send counts against it together: the system prompt, the full conversation history so far, any RAG-retrieved chunks, and the current question. Exceed it, and the request either fails outright or gets silently truncated, depending on the provider. A long-running chatbot conversation, left unmanaged, will eventually hit this wall — context engineering is the practice of making sure it never does.

Field Manual

Truncation Strategies — What Gets Cut, and How

When the budget is about to be exceeded, something has to give. The simplest and most common approach is a sliding window: drop the OLDEST messages first, keeping the most recent conversation intact, since recent turns are usually most relevant to the current question.

JAVASCRIPT
function trimHistory(history, maxMessages) {
  if (history.length <= maxMessages) return history;
  // Keep the newest N messages, drop the oldest ones first.
  return history.slice(history.length - maxMessages);
}
WHAT JUST HAPPENED .slice(history.length - maxMessages) is Mission 6.2's slicing, applied here to keep only the tail end of an array — the most recent messages. A more advanced strategy summarizes the dropped older messages into a short condensed note instead of deleting them outright, preserving some memory of the earlier conversation without the full token cost.

More Context Isn't Always Better

It's tempting to think "just include everything, to be safe." Two real problems argue against that. First, cost (Mission 7.8) — every extra token in the context is billed as input, every single request. Second, and less obvious: research on real models has found a "lost in the middle" effect, where relevant information buried in the middle of a very long context is sometimes used less reliably than the same information near the start or end. Padding context with marginally-relevant material can measurably hurt answer quality, not just cost more.

A Practical Context Budget

Treat the context window like Mission 7.8's cost budget: decide, ahead of time, roughly how much of it each piece is allowed to use. A reasonable starting split for a RAG-powered chatbot: a small fixed amount for the system prompt, a moderate chunk reserved for retrieved RAG context, most of the remainder for recent conversation history — and critically, some budget held back, unused, for the model's own response, since input and output usually share the same total window.

WHY RESERVE SPACE FOR THE OUTPUT If your input already uses the entire context window, there's no room left for the model to actually respond — some providers will error, others will simply cut the reply short mid-sentence. Always budget input to leave real headroom for the response.

⚠ COMMON MISTAKES

  • Letting conversation history grow forever with no trimming strategy until a request suddenly fails.
  • Dropping the NEWEST messages instead of the oldest when trimming — usually backwards from what the user actually needs.
  • Assuming more context always means a better answer, when irrelevant padding can dilute the model's focus.
  • Budgeting input right up to the context limit, leaving no room for the model's own response.
