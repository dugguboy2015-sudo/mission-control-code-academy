MISSION 2.4: FUNCTIONS IN DEPTH

Parameters, Return Values, Scope

You've written functions already — calculateFuelNeeded, checkFuelStatus. This mission is about writing them well: choosing the right syntax for the job, giving parameters sensible defaults, exiting early instead of nesting five levels deep, and understanding exactly which variables a piece of code can see. Along the way you'll meet closures — a function's odd, useful habit of remembering where it came from.

🟢 CADET LEVEL ⏱ ~45 MIN 🛠 BROWSER ONLY
1

Briefing

Think of a function as a standing order given to a specific crew station. You don't re-explain docking procedure to the pilot every single time a ship approaches the bay — you wrote the procedure once, gave it a name, and now you just say "run docking procedure" with the current ship's details. The station already knows what to do with whatever it's handed.

That's exactly what a function is: a block of logic you define once, then call as many times as you need, each time with different arguments filling in its parameters. The function runs its body using those values and, when it's done, can hand a result back with return — the equivalent of the station reporting "docking complete, bay 4" back to the bridge.

Where this gets interesting is everything around the call: what happens if a parameter is left out? What if the logic needs to bail out early instead of nesting deeper and deeper? And which variables can a function actually see — just its own, or everything on the ship? Get comfortable with the answers here, because every function you write from now on leans on them.

Anatomy of a call: parameters go in, the body runs exactly once, and return sends exactly one value back out. The function itself never prints or displays anything — it's the caller's job to decide what to do with the result.
2

Field Manual

Declarations vs. Arrow Functions

There are two common ways to write a function, and picking between them is a matter of idiom, not correctness. A function declaration is the classic form — named up front, and hoisted (usable even before its line in the file). An arrow function is a shorter syntax, usually stored in a const, and it's what you'll reach for most for short, inline logic.

JAVASCRIPT
function calculateFuelNeeded(distance, efficiency) {
  return distance * efficiency;
}

// same logic, arrow syntax — implicit return, no braces needed
const calculateFuelNeeded2 = (distance, efficiency) => distance * efficiency;
WHAT JUST HAPPENED Both versions behave identically when called. The arrow version skips { } and return entirely because a one-expression arrow function automatically returns whatever that expression evaluates to. Reach for a declaration for named, top-level utility functions you'll call by name throughout a file. Reach for an arrow function for short logic passed directly into something else — a callback for addEventListener or an array method — where naming it separately would just add noise.

Default Parameters & Early Returns

A parameter can have a default value, used automatically whenever the caller leaves that argument out (or passes undefined). Write it right in the parameter list: efficiency = 12.

JAVASCRIPT
function calculateFuelNeeded(distance, efficiency = 12) {
  return distance * efficiency;
}

console.log(calculateFuelNeeded(5));      // 60 — efficiency defaults to 12
console.log(calculateFuelNeeded(5, 20));  // 100 — override supplied

Now consider a function that needs to check several conditions before deciding what to do. Nesting if/else blocks inside each other gets hard to read fast. An early return — a guard clause that exits the function the moment it knows the answer — keeps the logic flat.

JAVASCRIPT
function fuelStatusReport(fuel) {
  if (fuel < 0) return "ERROR: negative fuel reading";
  if (fuel < 10) return "CRITICAL: refuel immediately";
  if (fuel < 40) return "LOW: plan a refuel stop";
  return "NOMINAL";
}
WHAT JUST HAPPENED Each guard clause handles exactly one case and immediately hands control back to the caller — there's no else anywhere, and no risk of accidentally falling through to a case that shouldn't apply. Compare this to writing the same logic as nested if/else if/else: it works, but adding a fifth or sixth condition turns it into a staircase. Guard clauses stay flat no matter how many cases you add.

Scope: Block vs. Function

Scope is the answer to "which variables can this line of code see?" Variables declared with let or const are block-scoped — they only exist inside the nearest { } that contains them, including the braces of an if, a for loop, or a function body.

JAVASCRIPT
function checkFuel(fuel) {
  if (fuel < 10) {
    let status = "CRITICAL";
    console.log(status); // fine — inside the same block
  }
  console.log(status); // ReferenceError — status doesn't exist out here
}
WHAT JUST HAPPENED status was declared inside the if block, so it only lives there — once execution leaves the closing }, it's gone. This is function scope's counterpart: a variable declared anywhere directly inside a function (not nested in a further block) is visible throughout that entire function, but never outside it. Nesting only ever narrows visibility going in — inner code can always see outer variables, never the reverse.
▸ DEEP DIVE: Why global variables cause bugs that are hard to trace

A global variable — one declared outside every function — is visible to everything on the page. That sounds convenient until two functions both need to touch it:

Before (fragile): let fuel = 100; declared globally. burnFuel(20) subtracts from it, refuel(30) adds to it, and a third function reads fuel to update the display. Call them in the wrong order, add a fourth function that also touches fuel, or run one twice by accident, and the display shows a number nobody can explain — because the bug isn't in any single function, it's in the shared state between them, and there's no way to tell from reading one function alone what else might have changed fuel first.

After (traceable): each function takes fuel in as a parameter and hands the new value out with return — fuel = burnFuel(fuel, 20);. Now every function's behavior depends only on what you handed it, nothing is hidden, and you can test or reason about each one in complete isolation. This is why "avoid global variables" is one of the oldest rules in programming: it's not that globals are forbidden, it's that every one you add is a variable any function anywhere could be silently depending on.

A First Look at Closures

Here's something that feels like magic the first time you see it: a function can return another function — and that returned function keeps working with the variables from the scope it was originally defined in, even after the outer function has already finished running. That's called a closure: the inner function "closes over" its birth environment and remembers it.

JAVASCRIPT
function makeCounter() {
  let count = 0;
  return function () {
    count = count + 1;
    return count;
  };
}

const counterA = makeCounter();
console.log(counterA()); // 1
console.log(counterA()); // 2
console.log(counterA()); // 3

const counterB = makeCounter();
console.log(counterB()); // 1 — a brand-new, independent count
WHAT JUST HAPPENED makeCounter() runs, creates a local variable count set to 0, and returns a small function that can read and update it — then makeCounter itself finishes. Normally count would be destroyed right there, since it was function-scoped to makeCounter. But the returned function still references it, so JavaScript keeps it alive. Every call to counterA() increments that specific count, which is why the log reads 1, 2, 3. Calling makeCounter() again for counterB runs the whole function fresh, creating a brand-new count starting at 0 again — counterA and counterB each remember their own private variable, completely unaware of each other. That's the whole idea: a closure gives a function its own private, persistent memory.

⚠ COMMON MISTAKES

  • Forgetting return entirely and being confused when the function's result is undefined.
  • Shadowing: declaring a variable inside a block with the same name as one outside it — the inner one silently wins inside that block, and edits to it never touch the outer variable.
  • Relying on a global variable instead of passing values as parameters — it works until a second function touches the same variable and the bugs become nearly impossible to trace.
  • Assuming a default parameter only skips truly "empty" arguments — it actually only triggers when the argument is undefined, not for other falsy values like 0 or "".
  • Arrow functions handle this differently from regular functions (they don't have their own) — it won't bite you yet, but keep the name in mind for when objects and event handlers make it matter.
