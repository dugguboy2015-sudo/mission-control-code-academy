Briefing

Back in Mission 1.9, "done" meant Ladder Level L1: deployed to a public URL, works on mobile. That was the right bar for a personal site — mostly static, mostly forgiving. But an app that talks to a live API over the real internet has a whole category of ways to fail that a static page never faces: the network can be slow, the network can drop entirely, and the API itself can legitimately say "no results" instead of crashing. None of that is a bug in the API. It's just what happens when your code leaves your machine and starts depending on someone else's server, somewhere else in the world, that you don't control.

That's what Ladder Level L2 is actually about. From Part F of the curriculum plan: secrets in env vars — never in code; handles error and loading states; has a README. Read that as a single idea rather than three separate chores: a production app has to survive contact with reality, and it has to leave behind enough of a trail that someone else — including future-you, six months from now — can understand what it does and run it again. L1 asked "can strangers reach this?" L2 asks "does it behave correctly when things go wrong, and could someone else pick it up?"

The good news is you already have every raw skill this needs. Mission 4.3 gave you fetch and JSON parsing. Mission 4.2 gave you async/await and the vocabulary for a promise that's pending, resolved, or rejected. Mission 4.4 gave you localStorage for remembering things across a reload. Mission 4.5 gave you a working deploy pipeline. This mission doesn't teach you a single new syntax feature — it teaches you the discipline of using all four together so the app never leaves a user staring at a blank screen or a silent failure.

Concretely, you're going to build a small search app against a real, free, no-key public API, and take it from "runs in the sandbox" to "lives on a public URL with a README a stranger could follow." The Field Manual below walks through the four things that actually separate a hobby fetch demo from a shippable L2 app — loading states, error states, remembering the last search, and writing that README — before you build the whole thing in the Command Console.

Every search your app runs cycles through exactly these four states. A production app makes each one visible on screen — a demo that only ever shows SUCCESS is one bad network away from confusing its user. Loading States

A fetch call is not instant. Between the moment you call it and the moment the response arrives, real time passes — milliseconds on a fast connection, seconds on a slow one, sometimes longer on a phone losing signal. If your code does nothing visible during that gap, the page looks frozen. The user doesn't know if it's thinking, broken, or ignoring them entirely — and the most common thing they do next is click the button again, which fires a second overlapping request into an app that was never designed to handle two.

JAVASCRIPT — SHOWING AND HIDING A LOADING STATE
async function searchPokemon(name) {
  loadingEl.hidden = false;
  errorEl.hidden = true;
  resultEl.hidden = true;

  try {
    const response = await fetch(
      "https://pokeapi.co/api/v2/pokemon/" + name.toLowerCase()
    );
    // ...
  } finally {
    loadingEl.hidden = true;
  }
}
WHAT JUST HAPPENED The loading indicator turns on before the await, and the finally block turns it off no matter what happens next — a successful response, a thrown error, anything. That's the detail that matters: if you only hide the spinner inside the success path, a failed request leaves it spinning forever, which is its own kind of broken UI.

Error States

There are two genuinely different ways a search can fail, and a production app has to tell them apart instead of lumping everything into one vague "something went wrong." The first is a network failure — the request never even reached the server, because the connection dropped or the API is down. fetch reports that by rejecting the promise, which is what your catch block is for. The second is a valid response that says "not found" — the request worked fine, the server answered, and the answer is a 404 because no Pokémon named "qwerty" exists. fetch does not reject for this — response.ok is false, but the promise still resolves. Missing that distinction is the single most common reason a "working" fetch app still crashes on a bad search term.

JAVASCRIPT — HANDLING BOTH FAILURE MODES
try {
  const response = await fetch(url);

  if (!response.ok) {
    // The server answered — it just said "no."
    throw new Error("No Pokémon found with that name.");
  }

  const data = await response.json();
  renderResult(data);

} catch (err) {
  // Network failure AND our own thrown "not found" both land here.
  errorEl.textContent = err.message;
  errorEl.hidden = false;
}
WHAT JUST HAPPENED A rejected fetch promise (no connection at all) and a manually thrown Error (a resolved-but-unsuccessful response) both end up in the same catch block here — which is fine, since the user-facing fix is the same either way: show a clear message and let them try again. What's not fine is never checking response.ok at all — that's the gap where a real API's honest "not found" answer gets treated by your code as if it were a success.

Remembering the Last Search

Mission 4.4 covered localStorage as a way to persist state across a reload. Here it earns its keep for real: nobody wants to reopen your app tomorrow and see a blank input, having to retype the same Pokémon they were looking at yesterday. Persisting the last search — and restoring it automatically when the page loads — is a small addition that makes the app feel like it actually remembers you.

JAVASCRIPT — WRITE ON SEARCH, READ ON LOAD
const LAST_SEARCH_KEY = "mcca_apiapp_lastSearch";

// after a successful search:
localStorage.setItem(LAST_SEARCH_KEY, name);

// on page load:
const remembered = localStorage.getItem(LAST_SEARCH_KEY);
if (remembered) {
  input.value = remembered;
  searchPokemon(remembered);
}
WHAT JUST HAPPENED Notice the key name is specific and namespaced — mcca_apiapp_lastSearch, not just "lastSearch". On a real domain, every script sharing that origin shares the same localStorage, so a generic key name is exactly how one script's data quietly gets overwritten by another's. Naming your keys like you'd never want to collide with anyone else's is a habit worth building now, not after it bites you.

Writing a README

Every deployed project so far has been judged by whether it works when you click the link. A README is judged by something different: whether a person who has never seen your code can figure out what it does and how to run it, without asking you. That person is very often future-you, reopening a project you built months ago and no longer remember the details of. A good README is short — three things, honestly answered, beat ten vague ones:

  • What does this project do? One or two real sentences, not just the project's name repeated.
  • How do you run it? The actual steps — even if it's just "open index.html" or "visit the live URL below."
  • What API does it use, and are there any limits? Name it, link it, and note anything a future user of your README should know (rate limits, no API key required, etc.).
MARKDOWN — README.md
# Pokédex Search

A small web app that searches the PokeAPI for any Pokémon by name and
shows its stats, types, and official artwork. Remembers your last search
across reloads.

## Live demo
https://your-username.github.io/pokedex-search/

## How to run it locally
1. Clone this repository
2. Open `index.html` in any browser — no build step, no install

## API used
[PokeAPI](https://pokeapi.co/) v2 — free, no API key required, no
published rate limit for reasonable personal use.

## Known limitations
- Only searches by exact Pokémon name (no partial matches)
- No offline support
WHAT JUST HAPPENED None of that took more than a few minutes to write, and every sentence in it is something only you know about your own project — no amount of reading your source code replaces it. That's the actual test for "does my project have production hygiene": would a stranger, or you in six months, get unstuck by this file, or would they be starting from zero?
▸ DEEP DIVE: Debouncing — don't fetch on every keystroke

If you wire your search to fire on every input event instead of a button click, typing "pikachu" fires seven separate fetch requests — one per letter — most of which are wasted the instant the next keystroke lands. The fix is called debouncing: instead of searching immediately, you start a short timer (150–400ms) every time the input changes, and cancel the previous timer if another keystroke arrives before it fires. Only when the user pauses does the timer actually complete and trigger the real search.

JAVASCRIPT — A MINIMAL DEBOUNCE
let debounceTimer;
input.addEventListener("input", () => {
  clearTimeout(debounceTimer);
  debounceTimer = setTimeout(() => {
    searchPokemon(input.value.trim());
  }, 300);
});

This isn't required for the checklist below — a search button that only fires on click sidesteps the whole problem — but it's a real technique you'll see in almost every production search box, and it's worth trying once you have the core app working.

▸ HINT

If your app "mostly" works but occasionally shows both an old result and a leftover error message at the same time, you almost certainly never reset one of them at the top of your search function. Every search should start by hiding the error box, hiding the old result, and showing the loading indicator — all three, every time — before the fetch call even begins.

BONUS OBJECTIVE

Store the last five searches (not just one) in localStorage as an array, and render them as a clickable history list — clicking a past search re-runs it instantly. This is the same persistence technique as the checklist above, just holding a small array instead of a single string.

⚠ COMMON MISTAKES

  • A loading spinner that only gets hidden inside the success path — if the fetch fails, it spins forever, and the user has no idea the search already ended.
  • An error handler that only catches network failures, never checking response.ok — a legitimate "no results" answer from the API gets rendered as if it were a real Pokémon, usually crashing on undefined somewhere downstream.
  • Forgetting to reset the previous error message or previous result at the start of a new search — a failed search followed by a successful one can leave both messages on screen at once.
  • Using a generic, unnamespaced localStorage key like "data" or "lastSearch" that silently collides with another script on the same page or origin.
  • Shipping without a README — the app runs fine today, but six months from now, not even you remember which API it calls or how to run it locally.
