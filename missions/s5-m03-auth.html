MISSION 5.3: AUTH

Sign Up, Sign In & Protected UI — Locking and Unlocking the Dashboard

Row Level Security in Mission 5.2 answered "what can this user touch in the database" — but it all assumed you already know who is asking. That's what authentication solves: proving a visitor is who they claim to be, then remembering that fact for the rest of their visit so every request afterward can be checked against it. This is one of the few areas of programming where "roll your own" is genuinely a bad idea — and understanding why is as important as knowing the API.

🔴 COMMANDER LEVEL ⏱ ~60 MIN 🛠 BROWSER ONLY
1

Briefing

Two words get used almost interchangeably by beginners but mean very different things. Authentication ("authn") is proving identity — "this is really Nova, because she typed the correct password." Authorization ("authz") is deciding what someone who's already proven their identity is allowed to do — "Nova is a Captain, so she can see the crew roster, but not the admin billing page." Row Level Security is authorization. Everything in this mission — sign-up, sign-in, sessions — is authentication, the step that has to happen first.

Signing in happens once. Checking permission happens constantly, on every request, using the session that sign-in produced.
2

Field Manual

Why You Never Hand-Roll Password Storage

A password must never be stored as plain text — if the database ever leaks, every account leaks with it, and since most people reuse passwords, the damage spreads to other sites too. The fix is hashing: running the password through a one-way function that scrambles it into something unrecoverable. To check a login later, you hash the typed password again and compare hashes — the real password is never stored anywhere, not even by the service itself.

YOU'VE ALREADY SEEN THIS This project's own child-PIN system does exactly this — set_child_pin() in the schema calls crypt(p_pin, gen_salt('bf')), a real password-hashing function, instead of storing the PIN as plain text. A proper auth provider does the same thing for full account passwords, correctly, with battle-tested algorithms — which is the whole reason to use one instead of writing this yourself.

Sessions & Tokens — Staying Signed In

Sending your password on every single request would be slow and risky. Instead, after a successful sign-in, the server hands back a session token — a long, signed, hard-to-forge string. The browser stores it and attaches it to every future request instead of the password. The server can verify the token is genuine (and hasn't expired) without ever touching a password again.

JAVASCRIPT
const { data, error } = await supabase.auth.signInWithPassword({
  email: 'nova@starbase.dev',
  password: 'correct-horse-battery-staple'
});

// data.session.access_token is that token — supabase-js stores
// and resends it automatically from here on.
WHAT JUST HAPPENED On success, Supabase returns a session object containing an access_token. Every RLS policy checking auth.uid() — which you used constantly in Mission 5.2 — is really reading the identity baked into this token. No token, no auth.uid(), and every RLS policy correctly treats you as a stranger.

The Core Supabase Auth API

Four functions cover almost everything a real app needs.

JAVASCRIPT
// Create an account
await supabase.auth.signUp({ email, password });

// Sign in an existing account
await supabase.auth.signInWithPassword({ email, password });

// Check the current session at any time (e.g. on page load)
const { data: { session } } = await supabase.auth.getSession();

// Sign out — clears the session everywhere
await supabase.auth.signOut();
WHAT JUST HAPPENED signUp and signInWithPassword both return a session on success. getSession() is what a page calls the instant it loads, to find out "is anyone already signed in from before?" — critical, because a session survives page refreshes and even closing the tab. Notice none of these four functions ever mention hashing, tokens, or cookies directly — that machinery is exactly what you're paying Supabase to handle correctly on your behalf.

The Protected UI Pattern

Knowing whether someone is signed in is only useful if the page actually behaves differently for them. The standard pattern — the exact one this Academy's own dashboard and mission pages use — is: hide everything by default, check the session the instant the page loads, then reveal the page only after that check succeeds.

HTML + JS
<!-- in <head>, BEFORE any content renders -->
<style>html{visibility:hidden}</style>

<script>
(async function () {
  const { data: { session } } = await supabase.auth.getSession();
  if (session) {
    document.documentElement.style.visibility = 'visible';
  } else {
    window.location.replace('/login.html');
  }
})();
</script>
WHAT JUST HAPPENED The CSS rule hides the entire page the instant it starts loading — before any real content, and before an unauthenticated visitor could ever glimpse it. The script is the ONLY thing allowed to set visibility back to "visible", and only after confirming a session exists. Get that one line wrong — setting it to an empty string instead of the word "visible", say — and the page stays invisible forever no matter what the rest of your code does. That exact bug happened during this Academy's own build and took real debugging effort to catch.

FakeAuth's functions are all async — every call needs an await in front of it, exactly like the real Supabase client. Forgetting await is the single most common mistake with any auth API, real or fake.

BONUS OBJECTIVE

Try signing in with an email that was never signed up at all. Read the error message FakeAuth gives back — is it specific ("no account with that email") or vague ("invalid credentials")? ⚠ COMMON MISTAKES

  • Writing your own password hashing instead of using a proven auth provider — a well-known source of serious real-world breaches.
  • Hiding protected content with JavaScript that runs after the page has already displayed it — the user sees a flash of real content first.
  • Checking the session once at page load and never again, so a signed-out user in another tab can still act as if logged in.
  • Returning a specific "no account found" vs "wrong password" error, which tells an attacker which emails are registered.
  • Forgetting await on an auth call and treating the returned Promise as if it were already the result.
