MISSION 8.3: TOOL-USING AGENTS

Giving the Model Hands

Mission 8.2's agent had exactly two tools, used in a fixed order. Real agents choose from several available tools, decide WHICH one fits a given situation, handle a tool that fails without crashing the whole loop, and treat some tools with more caution than others. This mission covers the practical engineering of a real multi-tool agent.

🔴 COMMANDER LEVEL ⏱ ~60 MIN 🛠 BROWSER ONLY
1

Briefing

A tool is only as useful as the model's ability to correctly choose it. Give an agent five vaguely-described, overlapping tools, and it will frequently pick the wrong one, or the right one with the wrong arguments. Give it a small number of clearly-scoped, well-described tools, and tool selection becomes reliable. Good tool design is at least as important as the agent loop itself.

2

Field Manual

Good Tool Design

Each tool should do exactly ONE thing, have a name that says what it does, a description precise enough to distinguish it from every other available tool, and return small, structured data — not a wall of prose the model then has to re-interpret.

JAVASCRIPT
// BAD: vague, does too many things, unclear when to use it
{ name: "do_stuff", description: "handles various tasks" }

// GOOD: one job, clear name, clear description, clear parameters
{
  name: "search_notes",
  description: "Search the user's saved notes by keyword. Returns matching notes only.",
  parameters: { keyword: "string" },
}
WHAT JUST HAPPENED Given several GOOD tools like this, the model can reliably match "find my notes about the trip" to search_notes based on the description alone. Given several tools like do_stuff, it genuinely can't — there's no signal in the description to distinguish which tool applies to which request.

Handling a Tool That Fails

A tool call is still just a function call — it can throw, time out, or return an error, exactly like any other code you've written since Sector 4. A well-built agent catches that failure as an observation (the loop keeps running), not a crash — the next reasoning step can then decide to retry, try a different tool, or give up gracefully.

JAVASCRIPT
async function act(step) {
  try {
    return { ok: true, result: await callTool(step.tool, step.args) };
  } catch (err) {
    // The FAILURE becomes the observation — the loop continues, informed by it.
    return { ok: false, error: err.message };
  }
}
WHAT JUST HAPPENED Notice the try/catch is INSIDE the loop's act step, not around the whole loop — one failed tool call becomes one observation the agent can reason about ("that didn't work, let me try X instead"), rather than an exception that kills the entire agent run.

Read-Only vs Write Tools

Not every tool carries the same risk. A read-only tool (checking the weather, searching notes) is safe to let an agent call speculatively — worst case, it wastes a little time. A write tool (sending an email, deleting a file, charging a card) has real, sometimes irreversible consequences if the agent calls it based on a misunderstanding. Production agent systems often require explicit confirmation, or an extra safety check, before a write tool actually executes — a topic Mission 9.6 (AI Security) covers in depth.

THE HABIT TO BUILD NOW When you design a tool, ask which category it's in. If it's a write tool, treat calling it as a bigger deal than a read tool — log it, consider requiring confirmation, and never let an agent chain multiple write actions together with no human checkpoint at all, especially early in a project.

⚠ COMMON MISTAKES

  • Writing vague, overlapping tool descriptions that make correct tool selection unreliable.
  • Letting one failed tool call crash the entire agent run instead of feeding the failure back as an observation.
  • Treating a write tool (sends an email, charges a card) with the same casual confidence as a read-only tool.
  • Giving an agent too many tools at once "just in case" — more overlapping options generally makes selection worse, not more capable.
