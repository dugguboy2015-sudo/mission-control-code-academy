MISSION 8.6: EVALS

How You Know the AI Actually Works

Sector 8 has spent five missions giving models more autonomy — loops, tools, planning, real system connections. More autonomy makes one question more urgent, not less: how do you actually know it works? A traditional unit test (Sector 9) checks assert(output === "exact string") — which fails constantly against an LLM, since Mission 7.1 established the same input can produce different, differently-worded, equally-correct output. Evals are the AI world's answer.

🔴 COMMANDER LEVEL ⏱ ~55 MIN 🛠 BROWSER ONLY
1

Briefing

An eval is a curated set of test cases — not checking for one exact expected string, but checking a property of the output: does it mention the right fact, is it under a length limit, is it valid JSON with the right fields, does it avoid a specific mistake. Run the whole set every time you change a prompt, a model, or an agent's logic, and you can tell, with real evidence, whether a change actually made things better or quietly broke something that used to work.

2

Field Manual

Why Exact-Match Tests Fail Against AI

Ask a model to summarize a paragraph twice, and you'll likely get two differently-worded, both-correct summaries. A test asserting the exact output string would fail the second run for no real reason. The fix isn't to give up on testing — it's to test a checkable PROPERTY of the output instead of its exact wording.

Types of Eval Checks

JAVASCRIPT
const evalCases = [
  {
    name: "mentions the capital",
    input: "What is the capital of France?",
    check: (output) => output.toLowerCase().includes("paris"),
  },
  {
    name: "stays under length limit",
    input: "Summarize this in one short sentence: ...",
    check: (output) => output.split(" ").length <= 20,
  },
  {
    name: "valid JSON with required field",
    input: "Extract the total as JSON: 'Total: $42'",
    check: (output) => {
      try { return typeof JSON.parse(output).total === "number"; }
      catch { return false; }
    },
  },
];
WHAT JUST HAPPENED None of these checks care about the model's exact wording — they check a fact ("Paris" appears somewhere), a measurable property (word count), or a structural guarantee (valid JSON, correct field type). All three are Mission 7.4's structured-output validation, reused here specifically as a testing tool.

LLM-as-Judge — When a Rule Can't Capture "Good"

Some qualities genuinely resist a simple rule — "is this response polite," "does this summary capture the main point." LLM-as-judge uses a SECOND model call whose only job is grading the first one's output against explicit criteria, returning a pass/fail or a score. It's a real, widely-used technique — and it inherits Mission 7.1's non-determinism, so it's typically used alongside rule-based checks, not as a total replacement for them.

WHY THIS IS STILL USEFUL DESPITE THE CAVEAT A judge model, given clear grading criteria and asked for a structured verdict (Mission 7.4 again), is far more consistent than "read every response by hand." It's not perfect, but it scales in a way manual review never can — which is the whole point of an eval suite.

Running the Suite & Tracking Regressions

The real payoff comes from running the WHOLE test set every time something changes — a new prompt, a different model, an updated agent. A regression is a case that used to pass and now fails; catching it immediately, from a pass-rate number, is dramatically better than discovering it from a confused user report weeks later.

Mission Challenge

▸ HINT

A good eval failure message tells you WHAT was expected and WHAT actually happened — check() returning just true/false is enough to fail the case, but including the actual output in your failure report is what makes debugging it possible later.

BONUS OBJECTIVE

Track pass-rate history: run the suite, store the pass count and timestamp in an array, change the mock model's behavior slightly (edit MOCK_MODEL), re-run, and compare the two pass rates to detect whether your change was a regression or an improvement.

⚠ COMMON MISTAKES

  • Writing exact-string-match tests against AI output, which fail constantly even when the output is perfectly good.
  • Never re-running the eval suite after changing a prompt or model — missing a real regression until a user reports it.
  • Relying entirely on LLM-as-judge for everything, when a simple rule-based check would be faster and more consistent.
  • Testing only "happy path" inputs and never including a case designed to reveal a known weak spot.
