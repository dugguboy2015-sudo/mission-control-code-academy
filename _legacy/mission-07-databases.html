MISSION 07: DATABASES

The Ship's Memory Banks — Data That Survives the Reboot

Every variable you've written so far has been fragile — refresh the page and it's gone, close the terminal and it's forgotten. Real applications need memory that survives: a crew roster that's still there tomorrow, a chat message a second person can actually read, a login that remembers you. That's a database — permanent, structured, searchable storage that lives on a server, separate from any one browser tab or script.

1

Briefing

Picture the ship's records vault: instead of loose notes, everything is organized into labeled manifest sheets. Each sheet is a table — say, a table of crew members. Each row on that sheet is one specific record — one crew member. Each column is a specific piece of information every record has — name, rank, station. This simple grid is the foundation of almost every database on Earth.

Every row needs a way to be uniquely identified, even if two crew members happen to share a name. That's the job of a primary key — usually a simple auto-incrementing number (id 1, id 2, id 3...) that's guaranteed never to repeat. Once rows have unique identities, tables can reference each other: a missions table can say "this mission was led by crew member id 3" instead of copying that crew member's entire record into every mission they've ever led. That link between tables is called a foreign key, and it's what makes databases genuinely powerful instead of just structured spreadsheets.

Real applications don't have your code reach directly into the database file — that would be like letting any visitor climb straight into the records vault unsupervised. Instead, requests go through an API (application programming interface): a controlled front desk that checks permissions and translates requests into database operations.

Your website never touches the database directly — every request passes through an API that checks who's asking and what they're allowed to do.

Field Manual

Tables, Rows, Columns & Keys

Before writing a single query, you design the shape of your data. That means deciding what tables you need and what columns each one has — this is called a schema.

SQL
CREATE TABLE crew (
  id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,
  rank TEXT,
  station TEXT
);
WHAT JUST HAPPENED This defines the crew table's shape before any data exists in it. PRIMARY KEY tells the database to guarantee every id is unique. NOT NULL means that column can never be left empty — the database will reject any row that tries.

CRUD — The Four Things You Do to Data

Nearly every database operation in existence falls into one of four categories: Create, Read, Update, Delete. In SQL, that's INSERT, SELECT, UPDATE, and DELETE.

SQL
-- Create
INSERT INTO crew (name, rank, station) VALUES ('Nova', 'Captain', 'Bridge');

-- Read
SELECT * FROM crew WHERE station = 'Bridge';

-- Update
UPDATE crew SET rank = 'Commander' WHERE name = 'Nova';

-- Delete
DELETE FROM crew WHERE name = 'Nova';
WHAT JUST HAPPENED SELECT * means "give me every column." The WHERE clause filters which rows are affected — it's used identically across SELECT, UPDATE, and DELETE. This is worth memorizing cold: UPDATE or DELETE without a WHERE clause applies to every single row in the table, which has ended real careers. Always double check your WHERE clause before running either one.

Relationships — Linking Tables Together

A foreign key is a column in one table that stores the primary key of a row in another table, creating a link between them.

SQL
CREATE TABLE missions (
  id INTEGER PRIMARY KEY,
  title TEXT,
  leader_id INTEGER REFERENCES crew(id)
);

SELECT missions.title, crew.name
FROM missions
JOIN crew ON missions.leader_id = crew.id;
WHAT JUST HAPPENED leader_id stores a crew member's id rather than duplicating their whole record. The JOIN then stitches the two tables together for a query, matching each mission to its leader's actual name. This is the single most powerful idea in relational databases — data lives in exactly one place, and everything else just points to it.

Introducing Supabase

Writing raw SQL directly against a production database from a public website is risky and complicated. Supabase is a service that gives you a real, full Postgres database (a serious, industry-standard SQL database), plus an instant, secure API in front of it, plus built-in authentication (sign up / log in) — all without you having to build or manage a server yourself.

WHAT SUPABASE ACTUALLY GIVES YOU When you create a new project in the Supabase dashboard, you land on a page with a left sidebar. The Table Editor tab lets you create tables visually — click "New table," add columns with a type dropdown, exactly like the schema you just wrote in SQL, but point-and-click. The SQL Editor tab lets you run raw SQL directly, exactly like the queries above. The Authentication tab manages user sign-ups automatically, without you writing any password-handling code yourself — which is important, because handwritten password systems are a common source of serious security bugs.

Connecting Your Website to Supabase

Once a table exists, your JavaScript talks to it using the supabase-js client library instead of writing raw SQL from the browser.

JAVASCRIPT
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  'https://yourproject.supabase.co',
  'your-public-anon-key'
);

const { data, error } = await supabase
  .from('crew')
  .select('*')
  .eq('station', 'Bridge');
WHAT JUST HAPPENED This JavaScript is doing exactly the same thing as SELECT * FROM crew WHERE station = 'Bridge'; — the supabase-js library translates method calls like .from(), .select(), and .eq() into real SQL behind the scenes and sends it through Supabase's API. The anon key is a public, restricted key — it only allows the specific actions you configure permissions for, so it's safe to include in front-end code.

⚠ COMMON MISTAKES

  • Running UPDATE or DELETE without a WHERE clause — this affects every row in the table, permanently.
  • Forgetting quotes around text values ('Nova') while numbers need none (84).
  • Designing a table with no primary key, making individual rows impossible to reliably reference later.
  • Duplicating data across tables instead of using a foreign key — leads to entries that quietly go out of sync.
  • Putting a real database's secret admin key in public front-end code — only ever expose a properly restricted public key.
