MISSION 06: DEPLOYMENT

Launch Sequence — Taking Your Site from Hangar to Orbit

Every page you've built so far has lived in exactly one place: your own computer. That's the hangar — safe, private, useful for building, but invisible to everyone else in the galaxy. Deployment is the launch sequence that takes your project out of the hangar and puts it somewhere anyone with a link can reach it, 24 hours a day, without your computer even being turned on. Today you ship something real.

🟡 OFFICER LEVEL ⏱ ~50 MIN 🛠 GITHUB ACCOUNT NEEDED
1

Briefing

When you open your HTML file by double-clicking it, your browser is reading it straight off your hard drive — nobody else can see it, because it never left your machine. To make a website reachable by anyone, anywhere, you need a server: a computer that's always on, always connected to the internet, and configured to hand your files to whoever asks for them. Hosting is the service that provides that always-on computer for you.

There are two broad categories of site. A static site is just files — HTML, CSS, JS, images — sent to the browser exactly as they are. A dynamic site runs code on the server itself (often Python, like in Mission 05) to build the page differently depending on who's asking. Everything you've built so far is static, and static sites are dramatically easier to deploy — which is exactly why this mission starts here.

The path from your laptop to a live URL runs through the same tool you already know: Git. You push your code to GitHub, and a hosting service — we'll use GitHub Pages, which is free and built directly into GitHub — watches that repository and automatically publishes it to a real web address.

Deployment moves your files from a machine only you can reach to a server the whole internet can reach.
2

Field Manual

Preparing Your Project for Launch

Hosting services expect a specific structure. The single most important rule: your main page must be named index.html and sit at the top level of your project — that's the file a server hands out by default when someone visits your site's root address.

FOLDER STRUCTURE
my-website/
├── index.html       # the entry point — required
├── style.css
├── script.js
└── images/
    └── logo.png
WHAT JUST HAPPENED Inside index.html, every link to your own files must use relative paths — <link rel="stylesheet" href="style.css">, not a path that only exists on your computer like C:\Users\you\my-website\style.css. Relative paths keep working no matter which server the files end up on.

Pushing Your Code to GitHub

If you completed Mission 01, this part is already familiar — you're using the exact same commands to get your project onto GitHub, which is now also acting as the source hosting reads from.

BASH
git init
git add .
git commit -m "Initial site"
git branch -M main
git remote add origin https://github.com/yourname/my-website.git
git push -u origin main
WHAT JUST HAPPENED Your project now exists in two places: locally on your computer, and on GitHub's servers. git branch -M main makes sure your default branch is named main, which is what GitHub Pages looks for by default. Nothing is live yet — GitHub is just storing the code so far.

Deploying with GitHub Pages

GitHub Pages turns a repository into a live website with a few clicks, no separate hosting account required.

STEPS
1. Open your repository on github.com
2. Click "Settings"
3. Click "Pages" in the left sidebar
4. Under "Branch", select "main" and "/(root)"
5. Click "Save"
6. Wait 1-2 minutes, then refresh for your live URL
WHAT JUST HAPPENED GitHub now watches your main branch. Every time you push a new commit, it automatically rebuilds and republishes your site — this is a small taste of a real CI/CD pipeline (continuous integration / continuous deployment), the same automation pattern professional teams use to ship updates dozens of times a day.
▸ DEEP DIVE: Why does it take a minute or two?

GitHub Pages doesn't serve your files directly out of the repository — it runs a small build step first (even for plain HTML) and then distributes your site across servers in multiple locations so it loads quickly no matter where a visitor is in the world. That distribution network is called a CDN (content delivery network), and the short delay is that propagation happening.

Domains & HTTPS — What's Actually Happening

Your GitHub Pages URL will look like yourname.github.io/my-website. That's a real, permanent, working address — you don't need anything else to have a genuine live site. But it's worth understanding two things happening under the hood.

WHAT'S ACTUALLY HAPPENING A domain name (like github.io) is a human-readable label that a system called DNS translates into the actual numeric address of a server. You can later buy your own custom domain and point it at your GitHub Pages site. HTTPS is the padlock icon in the address bar — it means traffic between the visitor and the server is encrypted. GitHub Pages provides this automatically, for free, with zero configuration.

▸ HINT

If your live site loads but shows a blank page or broken styling, the most common cause is a path issue: GitHub Pages serves your site from a subfolder like /my-website/, so an absolute path like /style.css can break even though it worked locally. Stick to plain relative paths like style.css or ./style.css.

⚠ COMMON MISTAKES

  • Naming the entry file something other than index.html — the server won't know what to serve by default.
  • Using absolute file-system paths instead of relative ones, which only work on your own computer.
  • Forgetting that filenames are case-sensitive on most servers, even if your own computer isn't.
  • Pushing to a branch other than the one configured in GitHub Pages settings, so nothing updates.
  • Panicking when the site doesn't appear instantly — give the build a minute or two before assuming something's broken.
